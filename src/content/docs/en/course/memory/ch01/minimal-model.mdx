The previous section ended with a structural clue: a heap allocation has no built-in cleanup moment of its own, whereas the stack variable managing it does. Whenever a function returns or a block closes (`}`), the exact point where a stack variable leaves scope is fixed at compile time.

Setting real Rust syntax aside, we can turn that clue into a minimal automatic reclamation model—and immediately test it against an everyday assignment (`=`).

## The baseline rule: free the heap when its stack variable leaves scope

Promote that clue into our model's first rule:

**When a stack variable leaves scope (`}`), automatically free the heap allocation it points to.**

Suppose a block requests a heap buffer and manages it through a stack variable `s`:

```text
{
    s = alloc_heap("hello")
    // ... read and write s inside this block ...
}   // ← s leaves scope here; its heap allocation is freed automatically
```

As long as `s` is the sole variable managing that heap buffer from start to finish, this single rule works cleanly:

- Nobody writes `free` by hand, ruling out leaks caused by forgotten cleanup calls.
- Deallocation happens right at `}`, determined at compile time with zero runtime scanning or reference counting.

Now test this model with an ordinary assignment statement, `=`.

## Why a single assignment frees the same block twice

Start with a plain integer on the stack:

```text
{
    a = 1
    b = a
}   // ← b and a leave scope and vanish with the stack frame
```

Evaluating `b = a` copies the stack bytes of `a` bitwise into `b`. Because the integer `1` lives entirely on the stack and owns no heap allocation, `a` and `b` end up holding two independent copies of `1`. At the closing `}`, both variables vanish with the stack frame, no heap cleanup runs, and nothing goes wrong.

Next, run the same test on a dynamic string managing a heap buffer:

```text
{
    s = alloc_heap("hello")
    t = s
}   // ← scope ends: what happens now?
```

As seen in the previous section, this value stores a three-word control header on the stack (`ptr`, `len`, and `cap`), while the character buffer `"hello"` sits on the heap.

Executing `t = s` copies those three machine words bitwise from `s` into `t`. **Because the heap pointer `ptr` is duplicated verbatim, a single assignment leaves two stack variables pointing to the exact same heap buffer rather than giving each variable its own buffer.**

<OneBinding part="share" />

When execution reaches the closing brace `}`, local variables exit in reverse order of declaration—`t` first, then `s`. Our scope-exit rule fires once for each variable:

1. `t` leaves scope and automatically frees the heap buffer it points to.
2. `s` is still in scope, holding a `ptr` that now points to freed memory—a **dangling pointer**.
3. Moments later, `s` leaves scope as well and frees that exact same heap address a second time—triggering a **double free** and undefined behavior.

The failure stems directly from the post-assignment state: whenever two active stack variables manage the same heap block, "free on scope exit" runs twice. That failure forces out a non-negotiable invariant:

**At any given moment, each heap allocation can have only one stack variable responsible for freeing it.**

## Patching the flaw: invalidating the source variable

A single `t = s` broke our baseline model. To preserve correctness without adding a garbage collector or deep-copying heap buffers on every assignment, we have to apply a strict rule patch—since two variables cannot share cleanup responsibility, assigning to a new variable must retire the old one:

**When a value managing a heap allocation is assigned, transfer cleanup responsibility to the new variable and mark the source variable invalid immediately, forbidding any further use.**

<OneBinding part="move" />

With that patch in place, the hole closes: once `t = s` runs, `t` is the only valid variable left. At the closing `}`, `t` frees the heap buffer once while the invalidated `s` does nothing, eliminating the double free. Enforcing source-variable invalidation is what keeps this minimal reclamation model sound.

## From variable invalidation to move semantics

Mathematically, the patch works. From a programmer's perspective, however, it creates an awkward mental split.

Look at the two assignments side by side:

```text
b = a    // after assignment, a remains valid
t = s    // after assignment, s suddenly becomes invalid
```

Both lines use the exact same `=` operator—why does the source variable stay readable in one case and become unusable on the spot in the other?

Framing `=` as "copy the value first, then conditionally penalize and invalidate the old variable" works against human intuition. In everyday programming, copying leaves two usable values behind; forcing yourself to memorize which types trigger an invalidation penalty makes every assignment feel like a trap.

To align the rule with natural intuition, language design reshapes the mental model. Instead of describing `t = s` as "copy, then invalidate," we split `=` into two familiar ways of handing values across variables:

- **Copy semantics**: for values like the integer in `b = a` that carry no heap cleanup responsibility, assignment duplicates the value—one becomes two, `a` keeps its copy intact, and both variables remain usable.
- **Move semantics**: for values like the string in `t = s` tied to exclusive cleanup responsibility, one cannot become two. Assignment **moves** the value—along with responsibility for freeing it—out of `s` and into `t`. Because the value has moved out of `s`, `s` is now empty; reading from `s` again makes no sense, and at scope exit `t` alone returns the resource.

Reframing mechanical invalidation as **move semantics** replaces a negative prohibition with a physical intuition: ask whether the value was copied or moved, and it is immediately clear which variable remains usable and who frees the memory. In this simplified model, values without heap allocations copy, whereas values managing heap allocations move.

## Under the hood: move is a language semantics; hardware only copies bytes

With the intuition of "moving" in place, we need to anchor it back to hardware reality to prevent a widespread misconception: **when we say a value moves from `s` to `t`, does the CPU physically relocate data and wipe `s` clean in memory?**

**No. "Move" is purely a compile-time semantics; hardware memory has no notion of moving bytes.**

Physical memory only reads, copies, or overwrites bytes. Separating **runtime memory** from the **compiler's internal state table** reveals how move semantics actually implements source invalidation underneath:

1. **In physical memory at runtime, the operation is still a bitwise stack copy**:
   - The `"hello"` character buffer on the heap never moves and is never duplicated.
   - Because the stack frame is reclaimed as a single block when the function returns, `s`'s stack slot cannot be freed early on its own, nor does the runtime write any validity flag into memory.
   - In an unoptimized baseline model, the CPU executes `t = s` the exact same way it executes `b = a`—**by copying the 24-byte control header bitwise from `s`'s stack slot into `t`'s**, leaving those same 24 bytes sitting untouched in `s` (and when emitting optimized machine code, the compiler can often elide even that stack copy).
2. **Invalidation and transfer happen entirely inside the compiler's compile-time state table**:
   - While analyzing source code, the compiler maintains a state table tracking whether each variable currently holds a live value and owns cleanup responsibility.
   - Upon seeing `t = s`, the table marks `s` as **uninitialized / moved-from** and reassigns cleanup responsibility to `t`.
   - If a later line tries to read `s`, the compiler checks its table, sees that `s` is no longer live, and **rejects the program at compile time** before an executable is ever produced.
   - At the closing `}`, the compiler consults the same table and emits a heap-free instruction solely for the still-live `t`, emitting nothing at all for `s`.

Keeping both layers distinct lets you switch perspectives cleanly: **when reasoning about program logic, think in moves to trace where values and cleanup duties flow; when reasoning about performance, remember that a move is at most a bitwise copy of a small stack header plus a compile-time state update, with zero runtime tracking overhead.**

## What the minimal model solves—and where it stalls

Together, the two rules derived in this section answer the goal posed in [The hard triangle](/memory/hard-triangle/):

1. **Stack variables automatically free their heap allocations at scope exit**—requiring neither manual `free` calls nor runtime scanning or reference counting.
2. **Values carrying cleanup responsibility follow move semantics on assignment (marking the source variable invalid and transferring duty at compile time)**—guaranteeing a single variable per heap block and ruling out double frees.

Inside a single block, this model is tight and self-contained. Drop it into everyday multi-function code, however, and an immediate obstacle appears: if you pass a string to a helper function solely to print it once, what does move semantics do to the caller's variable?
