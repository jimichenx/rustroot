在[编译单元 crate 与模块封装边界](/architecture/crates-and-modules/)中我们看到，`rustc` 的最小编译单元是一整棵 `crate` 模块树，而包含 `Cargo.toml` 的工程目录叫做 **Package（包）**。当项目从单人练习走向真实生产服务时，立刻会遇到多包拆分、可选功能裁剪、依赖版本锁定与生产编译调优四件事。

## 一、 从单包到 Workspace：为什么中型项目都拆成多包工作空间？

如果把几万行服务端代码全部塞进同一个 `crate` 里，每一次修改内部任意一行代码，`rustc` 都必须以整个 `crate` 为单位重新走一遍前端检查与依赖重连，增量编译耗时迅速拉长。此外，在[过程宏：编译期的代码重写插件](/architecture/procedural-macros/)中我们也看到，一旦项目需要编写自定义过程宏，编译器架构强制要求过程宏必须放在一个标有 `proc-macro = true` 的独立库包中。

但如果你只是新建几个平行文件夹、各自放一份独立的 `Cargo.toml`，又会引发另外两个工程问题：
1. **重复编译与磁盘膨胀**：每个子包都会在各自目录下生成独立的 `target/` 目录，把 `serde`、`tokio` 等上百个第三方依赖重复编译多遍；
2. **依赖版本漂移**：子包 A 用 `serde = "1.0.190"`，子包 B 用 `serde = "1.0.210"`，两边维护各自的 `Cargo.lock`，缺乏统一约束。

为了解决多包协作，Cargo 提供了**工作空间（Workspace）**机制。做法是在仓库最顶层放一份不写 `[package]`、只写 `[workspace]` 的根 `Cargo.toml`：

```toml
# 顶层仓库根目录 Cargo.toml
[workspace]
resolver = "3"
members = ["crates/core-domain", "crates/http-api", "crates/my-macros"]

# 统一版本池：全仓库只在这里维护一份第三方库版本号
[workspace.dependencies]
serde = { version = "1.0", features = ["derive"] }
tokio = { version = "1.40", features = ["rt-multi-thread", "macros"] }
```

随后，在各个子包（如 `crates/http-api/Cargo.toml`）中，只需用 `.workspace = true` 继承顶层配置，并通过 `path` 引用同仓库内的兄弟包：

```toml
# 子包 crates/http-api/Cargo.toml
[package]
name = "http-api"
version = "0.1.0"
edition = "2024"

[dependencies]
core-domain = { path = "../core-domain" }
serde.workspace = true
tokio.workspace = true
```

接入 Workspace 后，整个仓库立刻获得两项确定性保证：**所有成员子包共用顶层唯一一份 `target/` 编译产物缓存**（同一个版本的第三方库全仓只编译一次），且**共用顶层唯一一份 `Cargo.lock` 锁文件**。在根目录下执行 `cargo test --workspace` 或 `cargo run -p http-api`，即可按需调度任意成员包。

## 二、 三类依赖边界与 `Cargo.lock` 的提交准则

在子包的 `Cargo.toml` 中，依赖按参与编译的阶段严格划分为三个独立区块：

| 配置区块 | 参与编译与链接的时机 | 是否进入最终生产二进制 | 典型用途 |
| --- | --- | --- | --- |
| **`[dependencies]`** | 所有构建模式始终参与编译链接 | **是** | 核心运行期依赖（如 `serde`、`tokio`） |
| **`[dev-dependencies]`** | 仅在执行 `cargo test`、`cargo bench` 或编译 `examples/` 时链接 | **否** | 测试断言库、Mock 工具、基准测试框架（关联[三维测试体系](/architecture/testing-system/)） |
| **`[build-dependencies]`** | 仅在编译项目前构建并运行 `build.rs` 脚本时使用 | **否** | C 语言源码编译辅助库 `cc`、Protobuf 代码生成工具 `prost-build` |

### `Cargo.toml` 与 `Cargo.lock` 的分工

在版本管理上，许多有前端 `package-lock.json` 或 Go `go.sum` 经验的开发者常会问：`Cargo.lock` 到底该不该提交进 Git 仓库？

先看两者的物理分工：
- **`Cargo.toml` 声明的是「语义化兼容区间」**：写下 `serde = "1.0"` 时，它等价于 `>=1.0.0, <2.0.0`。只要上游发布了 `1.0.215`，允许在不破坏公开签名的前提下演进；
- **`Cargo.lock` 记录的是「某次解析出的精确版本与哈希快照」**：只要锁文件存在，普通 `cargo build` 就严格按锁文件里的精确版本号构建，不会擅自联网拉取新版（除非你显式执行 `cargo update`）。

由此直接推出版本库管理准则：
1. **所有最终交付运行的可执行程序、后端微服务、CLI 工具与多包 Workspace**：**必须将 `Cargo.lock` 提交进 Git**，并在 CI 流水线中使用 `cargo build --locked`（若锁文件与 `Cargo.toml` 不同步则直接报错中止），确保本地开发机、测试环境与线上生产环境编译出的依赖版本完全一致。
2. **纯对外发布到 `crates.io` 的底层通用库**：下游用户构建自己的应用时，Cargo 会使用下游应用自己的 `Cargo.lock` 重新统一解析依赖版本，忽略库自带的锁文件。不过自 Rust 1.79 起，`cargo new --lib` 也已不再默认把 `Cargo.lock` 写入 `.gitignore`，保留锁文件同样有助于库作者在团队内部复现测试环境。

## 三、 `Features` 条件编译与「加法合并原则」

一个成熟的库往往需要支持可选能力——例如默认只提供轻量级数据结构，只有当调用方显式开启 `json` 特性时才引入 `serde` 序列化实现，或者按操作系统裁剪平台专属的系统调用。

Rust 通过编译期属性 **`#[cfg(...)]`** 与内置宏 **`cfg!(...)`** 实现零运行时开销的**条件编译（Conditional Compilation）**：

1. **条目级裁剪属性 `#[cfg(...)]`**：标注在函数、`struct`、`mod` 或 `impl` 块上方。如果条件不成立，编译器在解析语法树阶段就直接将该条目整块丢弃——未开启的代码不仅不生成机器码，甚至不会参与后续的类型检查，对应的可选依赖包也不会被下载编译。
2. **表达式级布尔宏 `cfg!(...)`**：写在函数体内部，在编译期直接展开为字面量 `true` 或 `false`。注意与 `#[cfg(...)]` 的关键差异：用 `if cfg!(feature = "json") { ... }` 编写的两个分支都会完整走完语法与类型检查，只是未命中的分支会在后端优化时作为死代码消去。

除了自定义 `feature`，`cfg` 还常用于操作系统与架构判断，例如 `#[cfg(target_os = "linux")]`、`#[cfg(unix)]`、`#[cfg(target_pointer_width = "64")]`，以及单元测试专用的 `#[cfg(test)]`。

### 工程核心禁忌：为什么严禁把 `features` 设计成互斥开关？

在设计 `[features]` 时，初学者最常踩的一个架构陷阱是：把两个特性当成「二选一」的互斥单选框来写——例如同时定义 `mysql` 和 `postgres` 两个特性，并在代码里为它们分别导出同名的 `pub type DbConn`：

```rust
// 错误示范：把 Cargo features 当成互斥开关使用
#[cfg(feature = "mysql")]
pub type DbConn = MysqlConnection;

#[cfg(feature = "postgres")]
pub type DbConn = PgConnection; // 一旦两个特性同时开启，当场报重复定义错误 E0428
```

这段代码在单独测试 `--features mysql` 或 `--features postgres` 时看似正常，但一旦放进真实的 Workspace 或大型依赖树就会编译失败。原因在于 Cargo 的**特性合并（Feature Unification）**规则：

假设在一个工作空间里，子包 `order-service` 开启了 `db-core` 的 `postgres` 特性，而另一个子包 `legacy-sync` 开启了同一个 `db-core` 的 `mysql` 特性。当你执行 `cargo build --workspace` 时，Cargo 为了保证同一个版本的 `db-core` 在同一次构建目标下只编译一遍，会对整个依赖树请求的所有特性取**并集（Union）**——即同时传入 `--cfg feature="postgres"` 与 `--cfg feature="mysql"` 来编译 `db-core`。一旦库内部存在互斥定义，编译当场中断。

<Aside type="caution" title="Feature 设计的加法铁律（Additive Rule）">
Cargo 官方规范要求：**所有 `feature` 都必须是纯增量的（Additive）**——开启任意一个特性，只能新增模块、新增公开类型或新增 Trait 实现，不能删除已有项，也不能改变已有公开签名的类型。因此，库作者在 CI 中必须固定运行一条 **`cargo check --all-features`**，专门检验所有特性同时开启时能否正常编译。如果业务上确实需要互斥的底层后端，应当拆分为两个独立的驱动包（如 `db-mysql` 与 `db-postgres`），或者把后端差异收敛为运行期的枚举配置。
</Aside>

## 四、 日常工程护栏与 Release 构建调优速查

### 1. 开发与 CI 常用工具链分工

在日常编码与审查 AI 生成的代码时（关联[设计模式与 AI 时代的编译期护栏](/architecture/patterns-and-ai-rails/)），合理组合以下子命令能显著缩短反馈周期：

| 命令 | 底层行为与工程定位 |
| --- | --- |
| **`cargo check`** | 只执行 `rustc` 前端分析（宏展开、类型推导、借用与生命周期检查），跳过耗时的 LLVM 机器码生成与链接阶段。日常改代码或让 AI 修复编译报错时优先跑它，耗时通常只有 `cargo build` 的几分之一 |
| **`cargo clippy --all-targets -- -D warnings`** | 官方静态分析工具，内置数百条惯用法、性能冗余（如不必要的 `.clone()`、低效集合查找）与安全隐患检查。`-D warnings` 将所有警告升级为硬性编译错误，适合作为 CI 门禁 |
| **`cargo fmt --check`** | 按官方统一排版规则检查代码格式，消除团队代码风格争议 |
| **`cargo tree -i <包名> -e features`** | 反向追踪依赖树，查明到底是哪个上游依赖包引入了某个特定库或开启了它的某项 `feature` |
| **`cargo test --doc`** | 单独抽取并编译运行公开 API 文档注释（`///`）中的示例代码，防止文档示例随代码重构而过期失效 |

### 2. `[profile.release]` 生产编译权衡

需要注意的是，直接运行不带参数的 `cargo build` 默认使用 **`dev` 配置**——为了追求最快的本地编译速度，编译器默认关闭了几乎所有内联与循环优化（`opt-level = 0`），运行速度可能比优化后慢一个数量级。压测性能与线上部署必须使用 **`cargo build --release`**。

若对线上产物的吞吐性能或二进制文件体积有进一步要求，可在顶层 `Cargo.toml` 中按需调整 `[profile.release]`：

```toml
[profile.release]
lto = "thin"       # 开启跨 crate 瘦链接时优化（Link-Time Optimization），允许跨包内联热路径函数
codegen-units = 1  # 将每个 crate 合并为单个代码生成单元交给 LLVM，牺牲并行编译速度换取更充分的全局优化
strip = "symbols"  # 剥离二进制文件中的符号表，显著缩减最终可执行文件体积
```

这三项参数同样遵循没有免费午餐的工程交换：开启 `lto` 与设置 `codegen-units = 1` 会明显延长 Release 打包耗时并增加编译期内存占用，通常只在最终发布流水线中开启，不在本地 `dev` 配置中启用。
