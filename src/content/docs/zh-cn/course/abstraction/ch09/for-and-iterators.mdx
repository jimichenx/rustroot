Rust 取消了易因边界计算失误导致越界的 `for (int i = 0; i < n; i++)` 三段式循环，统一采用 **`for 模式 in 目标表达式`** 语法（如 `for i in 0..3` 遍历左闭右开区间，或 `for s in names` 遍历集合）。

但围绕 `let names = vec![String::from("Rust"), String::from("Root")];` 写几行遍历代码，很快会遇到三处疑问：① 写完 `for s in names` 后再读 `names` 会直接报 `E0382` 移动失效；② 改成 `for s in &names` 后，右边加了 `&`，左边的 `s` 为何也自动变成了 `&String`？③ `s` 前面并未声明 `mut`，为何每轮循环能绑定不同的元素？

解开这三处疑问，先看核心库 `core::iter` 中的两份基础契约。

## `Iterator` 与 `IntoIterator` 契约

语言内核并未内置遍历 `Vec` 或 `HashMap` 的逻辑，所有遍历规则均建立在两个标准库 `Trait` 之上：

```rust
pub trait Iterator {
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}

pub trait IntoIterator {
    type Item;
    type IntoIter: Iterator<Item = Self::Item>;
    fn into_iter(self) -> Self::IntoIter;
}
```

逐项对照前序章节建立的规则：

- **`Iterator`（推进游标的状态机）**：关联类型 `type Item`（见[关联类型 vs 泛型 Trait](/abstraction/associated-types/)）唯一锁定每次产出的元素类型；`next(&mut self)` 要求独占可变借用，因为每取走一个元素都要向前推进内部游标；返回值 `Option<Self::Item>` 将 Java 的 `hasNext()` 与 `next()` 合二为一——有元素返回 `Some(v)`，到末尾返回 `None`；
- **`IntoIterator`（把容器转为游标的入口）**：`into_iter(self)` 按值接手当前目标，产出一个实现了 `Iterator` 的游标实例 `Self::IntoIter`。

<Aside type="note" title="为什么不直接让 Vec<T> 实现 Iterator？">
将「存数据的集合」与「记位置的游标」拆开有两重原因：一是 `Vec<T>` 只有 24 字节 `(ptr, len, cap)`，不遍历时无需白白多存一个游标字段；二是推进游标需要 `&mut self`，若游标直接长在 `Vec` 上，连对同一个数组写双层嵌套只读循环都会因可变借用冲突而无法编译。每次遍历通过 `into_iter` 临时生成独立游标，底层集合即可多处共享只读。
</Aside>

## 极小内核的 4 行机械展开

面对任意 `for x in expr { body }`，编译器内核不检查 `expr` 是否带 `&`，只通过 `#[lang = "into_iter"]` 语言项钩子将其机械展开为 4 行普通代码：

```rust
{
    let mut iter = IntoIterator::into_iter(expr);
    while let Some(x) = iter.next() {
        body
    }
}
```

其中 `while let` 是 `if let`（见[模式匹配与穷尽性检查](/types/pattern-matching/)）的循环形式：命中 `Some(x)` 则绑定 `x` 执行循环体，遇到 `None` 则退出。单看这 4 行展开，第 1 个与第 3 个疑问便直接解开：

1. **为什么 `for s in names` 会移走整个集合**：展开首行 `IntoIterator::into_iter(names)` 是按值传参——在第 1 轮循环开始前，`names` 的所有权就已经整体移交给了 `into_iter`；
2. **为什么循环变量 `x` 不用加 `mut`**：循环期间不断推进状态的是隐藏游标 **`let mut iter`**；而 `x` 是每轮进入 `while let Some(x)` 时全新声明的局部绑定，上一轮的 `x` 已随单轮块结束销毁。

## 三个独立类型打通遍历三件套

再来核对第 2 个核心疑问：既然 `into_iter(self)` 写死了按值接收 `self`，写 `for s in &names` 时为什么没移走 `names`，左边的 `s` 又自动变成了 `&String`？

回扣[类型构造器](/types/type-constructors/)的判断：**`Vec<T>`、`&Vec<T>` 与 `&mut Vec<T>` 是三个互不隶属的独立类型**。标准库直接在库代码中为这三个具体类型分别编写了三份独立的 `impl IntoIterator`：

```rust
impl<T> IntoIterator for Vec<T> {
    type Item = T;
    type IntoIter = std::vec::IntoIter<T>;
    fn into_iter(self) -> Self::IntoIter { /* 接管堆缓冲区 */ }
}

impl<'a, T> IntoIterator for &'a Vec<T> {
    type Item = &'a T;
    type IntoIter = std::slice::Iter<'a, T>;
    fn into_iter(self) -> Self::IntoIter { self.iter() }
}

impl<'a, T> IntoIterator for &'a mut Vec<T> {
    type Item = &'a mut T;
    type IntoIter = std::slice::IterMut<'a, T>;
    fn into_iter(self) -> Self::IntoIter { self.iter_mut() }
}
```

写下 `for s in &names` 时，实参类型为 `&Vec<String>`，匹配第二份实现：此处的 `Self` 就是 `&Vec<String>` 本身，按值传入 `self` 只是按位复制了 8 字节只读引用，原集合 `names` 未发生移动；同时该实现将关联类型锁定为 `type Item = &'a String`，`iter.next()` 返回 `Option<&String>`，解构出的 `s` 自然就是 `&String`。

<ForThreeModes />

| `for` 写法 | 传入 `into_iter` 的 `Self` | 产出的 `s` 类型（`Item`） | 循环后原集合 `names` 状态 |
| --- | --- | --- | --- |
| **`for s in &names`** | `&Vec<String>`（内部调 `.iter()`） | **`&String`**（只读借用） | 继续有效 |
| **`for s in &mut names`** | `&mut Vec<String>`（内部调 `.iter_mut()`） | **`&mut String`**（原地修改） | 继续有效，元素已更新 |
| **`for s in names`** | `Vec<String>`（接管堆缓冲区） | **`String`**（移出所有权） | **已移动失效（再用报 `E0382`）** |

<Aside type="tip" title="反证核对：为什么 HashSet 不支持 for x in &mut set？">
正因为三种遍历依赖三份独立的 `impl`，标准库完全可以按安全约束只实现其中一部分。例如 `HashSet<T>` 仅实现了 `HashSet<T>` 与 `&HashSet<T>` 的 `IntoIterator`，**故意未对 `&mut HashSet<T>` 实现**——防止调用方原地修改元素导致哈希值变化却留在原桶槽位（同理 `&mut HashMap<K, V>` 的 `Item` 被锁定为 `(&K, &mut V)`，键始终只读）。
</Aside>

## 一揽子实现与遍历期借用排他（`E0502`）

标准库还在 `core::iter` 中内置了一条自反一揽子实现 **`impl<I: Iterator> IntoIterator for I`**（`into_iter(self)` 原样返回 `self`），因此现成的迭代器（如 `0..3` 或 `names.iter()`）同样可直接放入 `for` 循环。至于集合为何仍保留 `.iter()` 与 `.iter_mut()` 固有方法：脱离 `for` 语法糖在普通表达式中直接串联方法链时，没人替你隐式调用 `into_iter()`，须手动写 `names.iter().map(...)` 开启游标。

再看只读游标 `slice::Iter<'a, T>` 的内存结构与安全边界：在 64 位平台上它同样占 **16 字节**（存放当前元素指针与末尾边界指针 `(ptr, end)`），并在类型上携带对原集合 `v` 的共享借用：
