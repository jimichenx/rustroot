在上一节中，我们看到 `for` 循环表面上像是一套复杂的控制流特性，剥开外壳后，语言内核其实只做了一次 4 行代码的机械展开，其余能力全由标准库的 `IntoIterator` 与 `Iterator` 契约加上所有权三件套共同承担。

现在，我们用完全相同的视角，来拆解 Rust 中另一个让初学者频频碰壁的核心机制——**闭包（Closure）**。

在 JavaScript、Python 或 Java 里，人们习惯把闭包（或 Lambda 表达式）当成一种「随手定义、随手传递的匿名小函数」。但当你带着这种直觉进入 Rust 时，立刻就会遇到三个怎么想都想不通的现象：
1. **为什么两个代码一模一样的闭包，编译器却说它们不是同一个类型，而且连它们的类型名字都写不出来？**
2. **其他语言里调用函数只有一种方式，为什么 Rust 标准库非要把闭包拆成 `Fn`、`FnMut`、`FnOnce` 三个像绕口令一样的 Trait？**
3. **很多人在闭包前加了一个 `move` 关键字后，以为「`move` 闭包就是把值移走了，所以只能调用一次（`FnOnce`）」，为什么有的 `move` 闭包却能反复调用无数次？**

要一次性打通这三个问题，我们先从闭包的基础语法和一个最底层的物理内存追问开始。

## 第一步：闭包的基础语法与物理内存追问

### 1. 认识闭包的语法：用两条竖线 `|参数|` 替代 `fn(参数)`

在 Rust 中，普通函数用 `fn` 关键字定义，且参数和返回值类型必须显式写出；而**闭包（Closure）**则是可以直接写在函数体内部、赋值给变量或作为参数传递的匿名可调用表达式，参数列表写在两条竖线 `|...|` 之间：

```rust
// 1. 普通函数：必须显式标注参数与返回类型，且不能直接读取外部局部变量
fn add_one_fn(x: i32) -> i32 {
    x + 1
}

// 2. 完整标注的闭包：参数写在 |...| 里
let add_one_full = |x: i32| -> i32 { x + 1 };

// 3. 日常简写闭包：编译器可根据上下文自动推断参数与返回类型；单行表达式可省去花括号 {}
let add_one = |x| x + 1;
```

（注：如果闭包不接收任何参数，两条竖线紧挨着写作 `|| 表达式`，例如 `let say_hi = || println!("hi");`。）

### 2. 第一性原理追问：被「捕获」的外部变量，在内存里到底住在哪？

闭包与普通函数最本质的区别，不在于省去了 `fn` 和类型标注，而在于**闭包可以直接捕获（Capture）定义处所在作用域里的外部局部变量**：

```rust
let base = 10;
let add_base = |x: i32| x + base; // 直接捕获了外面的局部变量 base
println!("{}", add_base(5));      // 输出 15
```

请停下来，顺着我们在第一篇建立的栈与堆物理模型追问一句：
- 普通函数 `add_one_fn` 不依赖任何外部局部变量，它在程序编译完后就是代码段里的一串机器指令，函数指针 `fn(i32) -> i32` 在栈上只是一个 **8 字节的机器码入口地址**；
- 可是上面这个闭包 `add_base` 抓取了外部变量 `base`（甚至我们还可以把这个闭包作为返回值传出当前函数，或者传给另一个函数）。**既然 Rust 没有垃圾回收器（GC）替你在堆上偷偷分配一个隐藏的「闭包环境对象（Environment Object）」，那么被闭包抓进来的外部变量 `base`，在物理内存里到底存放在哪里？**

## 第二步：掀开底牌——闭包根本不是「特殊函数」，而是编译器合成的「匿名 `struct`」

答案直接兑现了我们在[第 3 章 3.1 节](/types/type-entity/)和[第 5 章 5.2 节](/types/structs/)学过的结构体机制：

**在 Rust 语言内核里，根本不存在什么神秘的「闭包运行时环境」。每当你在源码里写下一个闭包表达式 `|x| x + base`，编译器在编译期只做了一件极小的事——当场为你自动定义一个独一无二的「匿名结构体（Anonymous `struct`）」，把闭包体里用到的外部变量作为结构体的字段装进去，再把闭包体里的逻辑生成为挂载在该结构体上的一个调用方法。**

如果把编译器在底层为你自动生成的结构用手写代码还原出来，你写的两行闭包代码完全等价于下面这段普通的 `struct` 定义：

```rust
// 你写的两行代码：
let base = 10;
let add_base = |x: i32| x + base;

// ========== 编译器在底层为你自动合成的等价代码 ==========
// 1. 自动生成一个独一无二的匿名结构体，把捕获的外部变量存成字段：
struct __Closure_1<'a> {
    base: &'a i32, // 因为闭包体只读取了 base，编译器自动在字段里存一个共享引用 &i32
}

// 2. 把闭包体的代码，变成挂载在该匿名结构体上的方法：
impl<'a> __Closure_1<'a> {
    fn call(&self, x: i32) -> i32 {
        x + *(self.base)
    }
}

// 3. 变量 add_base 实际上就是这个匿名结构体的一个普通栈上实例：
let add_base = __Closure_1 { base: &base };
// 当你调用 add_base(5) 时，底层执行的就是 add_base.call(5)
```

一旦看清**「每个闭包在物理上就是一个把捕获变量存作字段的匿名 `struct` 实例」**，前面困扰初学者的第一个谜团以及闭包的内存尺寸就全都可以现场验证了：

1. **闭包的字节大小 = 它捕获的字段大小之和（零额外对象头）**：
   - 如果一个闭包 `|x: i32| x + 1` 没有捕获任何外部变量，编译器生成的就是一个不含任何字段的单元结构体 `struct __Empty;`，它在栈上占 **0 个字节**（零大小类型 ZST）；
   - 如果一个闭包只读借用了两个外部变量 `a: i32` 和 `b: i32`，匿名结构体里就存放两个 `&i32` 引用字段，在 64 位平台上正好占 **16 个字节**（`8 + 8`）；
   - 如果一个闭包把一个 `String` 按值装进了自己的字段里，匿名结构体在栈上就正好占 **24 个字节**（即 `String` 的 `(ptr, len, cap)`，零堆分配包装）。
2. **解开第一惑：为什么两个长相一模一样的闭包不是同一个类型，且类型名字写不出来？**
   因为在第 5 章我们知道，Rust 采用名义类型系统——哪怕你手写两个字段完全相同的 `struct Foo { base: i32 }` 和 `struct Bar { base: i32 }`，它们也是两个截然不同的编译期类型实体。
   每当你在源码里写下一个 `|...| ...` 表达式，编译器就会为这个位置单独生成一个新的匿名结构体（在编译器报错信息里通常显示为 `{closure@src/main.rs:12:14}`）。因为这个名字是编译器内部生成的，你在源码里写不出它的具体类型名，所以当函数需要接收或返回闭包时，就必须通过我们马上要讲的 **Trait 契约** 来约束它。

## 第三步：为什么有 `Fn`、`FnMut`、`FnOnce`？——接收者三件套的精准投射

既然「闭包就是一个装了捕获字段的匿名 `struct`，调用闭包 `f()` 就是调用这个 `struct` 上的方法」，那么现在请你回答一个我们在[第 5 章 5.3 节](/types/methods/)早就滚瓜烂熟的问题：

**在 Rust 里，为一个 `struct` 定义方法时，第一个接收者参数一共有几种写法？**

答案脱口而出：**只有三种——`&self`（只读借用）、`&mut self`（独占可变借用）、`self`（按值接手并消耗）**。

标准库里的 `Fn`、`FnMut`、`FnOnce` 三个 Trait，根本不是凭空发明的新概念，它们就是**结构体方法接收者三件套在闭包调用上的 1:1 投射**（并且与 9.1 节的 `IntoIterator` 一样，通过 `#[lang]` 钩子与 `f(args)` 调用语法直接绑定）：

```rust
// 标准库中三大闭包 Trait 的核心签名概念模型（省略底层元组参数语法细节）：

// 1. FnOnce：接收者是按值传递的 self —— 调用一次就会把闭包 struct 自身消耗掉
pub trait FnOnce<Args> {
    type Output;
    fn call_once(self, args: Args) -> Self::Output;
}

// 2. FnMut：接收者是可变借用 &mut self —— 调用时会修改闭包 struct 内部的字段
pub trait FnMut<Args>: FnOnce<Args> {
    fn call_mut(&mut self, args: Args) -> Self::Output;
}

// 3. Fn：接收者是只读借用 &self —— 调用时只读访问闭包 struct 内部的字段
pub trait Fn<Args>: FnMut<Args> {
    fn call(&self, args: Args) -> Self::Output;
}
```

默认情况下（不写 `move` 时），编译器会检查你在闭包体 `{ ... }` 内部对外部变量做了什么，遵循**「最小权限原则（能只读借就不独占借，能借用就不移动）」**自动合成字段并实现对应的 Trait：

| 级别 | 闭包体对捕获变量做了什么？ | 匿名 `struct` 默认存什么字段？ | 调用方法的接收者 | 实现的最高 Trait | 调用次数与限制 |
| --- | --- | --- | --- | --- | --- |
| **1. 只读级** | 只读取变量（如 `|| text.len()`） | 共享引用 **`&T`** | **`&self`** | **`Fn`**（同时满足 `FnMut`、`FnOnce`） | **可任意多次调用**（且支持多处共享调用） |
| **2. 修改级** | 修改了变量（如 `|| count += 1`） | 可变引用 **`&mut T`** | **`&mut self`** | **`FnMut`**（同时满足 `FnOnce`） | **可多次顺序调用**（闭包变量本身须声明为 `let mut`） |
| **3. 消耗级** | 把非 `Copy` 变量移出或销毁（如 `|| text`） | 按值持有 **`T`** | **`self`** | 仅 **`FnOnce`** | **仅能调用一次**（调完后闭包实例移动失效，再调报 `E0382`） |

### 为什么 `Fn`、`FnMut`、`FnOnce` 是包含关系（子契约层级）？

注意看上面标准库定义中的冒号约束：`trait FnMut: FnOnce` 以及 `trait Fn: FnMut`。这表示它们之间存在单向的包含层级：
> **`Fn` ⊆ `FnMut` ⊆ `FnOnce`**（凡是实现了 `Fn` 的闭包，自动也实现了 `FnMut` 和 `FnOnce`；凡是实现了 `FnMut` 的闭包，自动也实现了 `FnOnce`）。

为什么会有这个包含关系？从接收者三件套来看再自然不过：
- 如果一个函数只要求传入一个「至少能被按值调用一次（`FnOnce`）」的闭包，那么你把一个支持只读调用无数次（`Fn`）或可变调用多次（`FnMut`）的闭包传进去，它当然也能胜任「被调用一次」的任务；
- 反过来则不行：如果一个函数要求传入 `Fn`（要在只读借用 `&self` 下调用多次），你把一个调用一次就会把内部字段拆走消耗掉的 `FnOnce` 闭包传进去，编译器就会当场报 `error[E0525]: expected a closure that implements the Fn trait, but this closure only implements FnOnce`。

## 第四步：核心正交祛魅——「怎么抓进来（`move`）」与「怎么调（`Fn` 家族）」是两件独立的事

现在，我们来攻克初学者最常混淆的第 3 个困惑：**`move` 关键字到底做了什么？为什么 `move` 闭包不等于 `FnOnce`？**

### 1. 为什么需要 `move` 关键字？（脱离当前栈帧存活）

前面看到，当你写下只读闭包 `|target| format!("{prefix}, {target}")` 时，编译器默认在匿名 `struct` 里只存了一个 8 字节的共享引用字段 **`&prefix`**。

只要这个闭包在当前函数内部当场用完销毁，存 `&prefix` 没有任何问题。但如果你想**把这个闭包作为函数的返回值返回给调用方**（或者在第 13 章把它交给一个新的后台线程去运行）：

```rust
fn make_greeter(prefix: String) -> impl Fn(&str) -> String {
    // 若不写 move，匿名 struct 里存的是 &prefix；
    // 函数返回时局部变量 prefix 随栈帧销毁，返回的闭包就会携带悬垂引用（报 E0373）
    move |target: &str| format!("{prefix}, {target}")
}
```

一旦 `make_greeter` 函数执行完毕返回，它的局部栈帧和参数 `prefix` 就会当场销毁。如果返回的闭包结构体里存的还是 `&prefix`，就会立刻变成我们在[第 1 章 1.5 节](/memory/lifetimes/)严防死守的**悬垂引用**（编译器会报 `error[E0373]: closure may outlive the current function, but it borrows prefix`）。

为了解决这个问题，我们需要在闭包参数列表前加上 **`move`** 关键字：
- **`move` 的唯一作用**：强制编译器在生成匿名 `struct` 时，不要存引用 `&prefix`，而是**把捕获的变量按值移动（对于 `Copy` 类型则是按位复制）进匿名 `struct` 的字段里**。
- 这样一来，24 字节的 `prefix: String` 就直接搬家住进了返回的闭包结构体内部，跟随着闭包一起安全地传出函数边界。

### 2. 两轴正交铁律：怎么「进」结构体 ≠ 怎么「出」结构体

很多人在学完 `move` 后会产生一个根深蒂固的误解：「既然 `move` 把外部变量按值移进了闭包，那这个闭包肯定就变成一次性消耗的 `FnOnce` 了。」

请用匿名 `struct` 模型仔细分辨这两根完全正交（互不决定）的坐标轴：

1. **第一根轴（捕获方式 —— 变量怎么「进」匿名 `struct` 的字段）**：
   发生在**创建闭包**的那一刻。由编译器自动推导（存 `&T` / `&mut T` / `T`），或者由你写 **`move`** 强制把变量按值装进匿名 `struct` 的字段里。
2. **第二根轴（调用契约 —— 调用方法时怎么「用」匿名 `struct` 的字段）**：
   发生在**调用闭包 `f()`** 的那一刻。**一个闭包究竟实现 `Fn`、`FnMut` 还是仅实现 `FnOnce`，只取决于闭包体内部代码对字段做了什么，与这个字段当初是用 `&` 借进来的还是用 `move` 搬进来的毫无关系。**

看下面这段一目了然的对照：

```rust
let prefix = String::from("Hello");

// 1. 虽然写了 move 把 prefix（String）按值装进了匿名 struct 的字段里，
//    但闭包体内部每次调用只读取 self.prefix（接收者只需 &self），
//    所以 greet 依然实现了最高级别的 Fn，可以反复调用任意多次
let greet = move |name: &str| format!("{prefix}, {name}");
println!("{}", greet("Rust"));
println!("{}", greet("Root")); // 第二次调用完全合法

// 2. 只有当闭包体内部把字段 self.prefix 的所有权移出或销毁时（接收者必须是 self），
//    它才仅实现 FnOnce，只能调用一次：
let take_out = move || prefix;
```

## 第五步：工程设计與代码审查（Code Review）中的闭包选型判据

在日常工程与审查代码时，如果你需要编写一个接收闭包（回调函数）的接口，或者需要在结构体里保存一个闭包，请按以下两条标尺做裁决：

### 1. 函数参数接收闭包：遵循「就宽不就窄」原则选择 `FnOnce` / `FnMut` / `Fn`

当你定义高阶函数 `fn process<F>(f: F)` 时，因为 `Fn` ⊆ `FnMut` ⊆ `FnOnce`，你在参数约束上写得越宽容，调用方能传进来的闭包种类就越多：

| 你的函数内部打算怎么调用这个闭包 `f`？ | 函数签名应声明的 Trait 约束 | 标准库真实签名印证 | 为什么这样选？ |
| --- | --- | --- | --- |
| **最多只调用一次**（如初始化回调、错误兜底、跨线程任务） | **`F: FnOnce(...)`**（最宽容） | `Option::unwrap_or_else<F: FnOnce() -> T>` | 声明 `FnOnce` 后，调用方无论传 `Fn`、`FnMut` 还是消耗型的 `FnOnce` 都能通过编译 |
| **在循环里顺序调用多次**（或允许调用方在闭包里顺手改状态） | **`F: FnMut(...)`**（居中） | `Iterator::map<B, F: FnMut(Self::Item) -> B>` | 既支持循环多次调用，又允许调用方传入带计数器的可变闭包（同时兼容只读的 `Fn`） |
| **需要通过共享引用 `&F` 并发调用或递归重入调用** | **`F: Fn(...)`**（最严格） | 多线程并发只读处理器 | 仅在确需共享不可变调用时才写 `Fn`，避免不必要地把调用方的 `FnMut` 闭包拦在门外 |

### 2. 泛型闭包 `<F: Fn(...)>` vs 函数指针 `fn(...)` vs 动态 `Box<dyn Fn(...)>`

除了三大 `Fn` Trait 之外，Rust 里还有一个小写开头的原生类型叫**函数指针（Function Pointer，写作 `fn(i32) -> i32`）**。
- **小写 `fn(A) -> B` 是具体的 8 字节指针类型**（不是 Trait）：只有普通 `fn` 函数以及**不捕获任何外部变量的空闭包**才能转成 `fn` 指针；一旦闭包捕获了任何外部变量（匿名 `struct` 大小不再是 0，需要携带环境数据），就无法塞进裸代码指针 `fn` 里。
- **工程选型与反模式拦截**：
  - **绝大多数传参场景 → 选静态泛型 `<F: FnMut(...)>`（或 `impl FnMut(...)`）**：零堆分配、零虚表跳转，编译期单态化后闭包体直接内联进调用方（我们将在 9.3 节验证这一点）；
  - **需要在同一个 `Vec` 里存放多个不同闭包，或在运行时动态替换回调 → 选 `Box<dyn Fn(...)>`**：直接复用我们在[第 8 章 8.2 节](/abstraction/dyn-trait-and-vtable/)学过的 16 字节胖指针动态分发；在代码审查中，若看到普通单次回调参数被写成了 `f: Box<dyn Fn(i32) -> i32>`，应重构为泛型 `F: FnOnce(i32) -> i32` 以消除多余的堆分配与间接寻址。

---

## 小结

1. **闭包的物理本质是匿名 `struct`**：语言内核将每个闭包表达式 `|args| body` 在编译期合成为一个独一无二的匿名结构体类型实体，把捕获的外部变量存为结构体字段，因此闭包的栈尺寸严格等于其捕获字段的大小之和。
2. **方法接收者三件套投射为 `Fn` 家族**：调用闭包就是调用匿名结构体的方法——接收者为 `&self` 对应 **`Fn`**（只读，可任意多次调用），接收者为 `&mut self` 对应 **`FnMut`**（修改字段，可多次顺序调用），接收者为 `self` 对应 **`FnOnce`**（移出或消耗字段，仅能调用一次），三者构成 `Fn` ⊆ `FnMut` ⊆ `FnOnce` 的包含关系。
3. **捕获方式（`move`）与调用能力（`Fn` 家族）正交独立**：`move` 关键字只强制在构造闭包时将捕获变量按值移入匿名结构体字段（使闭包可脱离原栈帧存活）；而该闭包实现 `Fn`、`FnMut` 还是 `FnOnce`，完全取决于闭包体内部代码如何使用这些字段。

至此，9.1 节的**迭代器（`Iterator`）**和本节的**闭包（`FnMut` / `Fn`）**都已经拆解完毕。
在最后一节（9.3 节）中，我们将把这两台机器正式组装到一起——看看日常工程里最高频的 `.iter().filter(|x| ...).map(|x| ...).collect()` 适配器流水线与 `Option` / `Result` 组合子是如何层层嵌套的，以及编译器如何把这一整条函数式链条压成与手写循环完全一致的零成本机器码。

1. **正交轴判断（破除 `move` 迷思）**：阅读下面这段代码，请问闭包 `check` 实现了 `Fn`、`FnMut` 还是仅实现了 `FnOnce`？第 5 行连续调用第二次 `check("admin")` 能否通过编译？它的栈上大小 `size_of_val(&check)` 在 64 位平台上是多少字节？
   ```rust
   let secret = String::from("admin");
   let check = move |input: &str| input == secret;

   println!("{}", check("guest"));
   println!("{}", check("admin"));
   ```
2. **接口签名审查（Code Review）**：同事写了一个带计时功能的辅助函数 `run_timed`，内部只执行传入的任务闭包 `task` **一次**并打印耗时，但他把签名写成了下面这样：
   ```rust
   fn run_timed<F>(task: F)
   where
       F: Fn(),
   {
       task();
   }
   ```
   当另一位调用方尝试传入一个在内部向 `Vec` 追加元素的闭包 `let mut log = vec![]; run_timed(|| log.push(1));` 时，编译器报错拒之门外。请解释报错原因，并给出最合理的签名修改方案。

<summary>点击核对参考答案</summary>

1. **正交轴判断**：
   - **实现了最高级别的 `Fn`（同时满足 `FnMut` 和 `FnOnce`），第 5 行连续第二次调用完全可以通过编译**。原因在于：`move` 只是在创建闭包时把 `secret`（`String`）按值移动进了匿名结构体的字段里；而在闭包体 `input == secret` 中，每次调用只是只读比较字段 `self.secret`（接收者只需 `&self`），并未将 `secret` 移出结构体。
   - **栈上大小是 24 字节**：因为匿名结构体内部直接按值内联持有了 `secret: String`（`ptr` + `len` + `cap` 共 24 字节）。
2. **接口签名审查**：
   - **报错原因**：调用方传入的闭包 `|| log.push(1)` 修改了捕获的外部变量 `log`，因此该闭包只实现了 `FnMut`（及 `FnOnce`），未实现只读的 `Fn`；而 `run_timed` 过度严格地要求了 `F: Fn()`。
   - **修改方案**：因为 `run_timed` 内部只调用 `task` 一次，遵循「API 侧就宽不就窄」原则，应将约束放宽为 **`F: FnOnce()`**（并将参数声明为 `task: F` 直接按值调用一次），这样无论调用方传入 `Fn`、`FnMut` 还是 `FnOnce` 闭包都能顺利通过。
