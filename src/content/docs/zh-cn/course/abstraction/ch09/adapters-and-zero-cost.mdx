前两节分别拆开了两台基础机器：迭代器（`Iterator`）是靠 `next(&mut self)` 推进的栈上游标状态机，闭包（`|x| ...`）是把捕获变量存为字段的栈上匿名结构体。本节将两者组装到一起，核对 `.iter().filter(...).map(...).sum()` 为何既不产生中间数组堆分配、又无多层调用开销，并梳理 `Option` / `Result` 组合子与性能审查边界。

## 惰性适配器与消费者拉取

在 JavaScript 中写 `arr.filter(p).map(f)`，每一步都会立即完整遍历并在堆上分配一个新数组。而在 Rust 中，`Iterator` 上的方法分为**适配器（Adapters）**与**消费者（Consumers）**两类：

运行可见，在打印出 `"pipeline built (stack size = 24B), nothing printed yet"` 之前，`filter` 与 `map` 内的日志一行都未执行。查看标准库中 `Map` 适配器的定义即可看清原因：

```rust
pub struct Map<I, F> {
    iter: I,
    f: F,
}

impl<B, I: Iterator, F: FnMut(I::Item) -> B> Iterator for Map<I, F> {
    type Item = B;
    fn next(&mut self) -> Option<B> {
        match self.iter.next() {
            Some(x) => Some((self.f)(x)),
            None => None,
        }
    }
}
```

调用 `.filter(p)` 和 `.map(f)` 内部没有任何循环，只是把 16 字节游标 `Iter`、8 字节闭包 `p`（借用 `&min_val`）与 0 字节闭包 `f` 按值层层内联包进栈上结构体 **`Map<Filter<Iter, P>, F>`**（共占 **24 字节**）。**只要未调用最外层的 `.next()`，这台惰性（Lazy）状态机就不会读取任何元素。**

真正驱动流水线的是末端的**消费者**（`.sum()`、`.count()`、`.fold(...)`、`.collect()` 及 `for` 循环）：`.sum()` 内部循环调用 `Map::next()`，逐层向内拉取元素，使每个元素像流经管道一样在单次遍历中完成过滤、平方与累加，全程在堆上分配 **0 字节**中间数组。

<Aside type="note" title="为什么 filter(|&&x| ...) 有两层 &，而 map(|&x| ...) 只有一层？">
对 `Vec<i32>` 调用 `nums.iter()` 产出的 `Item` 是 `&i32`。`map` 直接将该 `Item`（`&i32`）按值传给闭包转换；而 `filter` 只能借用检查元素以决定去留（若按值传给闭包，遇到 `String` 等非 `Copy` 元素就会被消耗掉而无法继续向下游传递），因此签名固定传入 `&Self::Item`，叠加后即为 `&&i32`。对 `Copy` 小元素可在 `.iter()` 后接 `.copied()` 先把 `Item` 还原为 `i32`，后续即可直接写 `filter(|&x| ...)` 与 `map(|x| ...)`。
</Aside>

## 单态化与内联：坍缩为寄存器循环

每处理一个元素都要穿过 `sum → Map::next → Filter::next → Iter::next` 四层方法与两个闭包，为何不会带来函数调用开销？这依赖编译期的两段配合：

<IteratorPipelineZeroCost />

1. **泛型单态化消除间接跳转**：`Map<I, F>` 中的游标 `I` 与匿名结构体闭包 `F` 均为编译期静态泛型参数（见[泛型与单态化](/abstraction/generics-and-monomorphization/)），单态化后 `(self.f)(x)` 是地址确定的直接调用，无任何虚表或函数指针查表；
2. **优化器内联消解包装层**：开启优化（`--release`）后，LLVM 将短小的多层 `.next()` 与闭包体全部内联展开进 `.sum()` 同一函数帧内，中间的 `Some(x)` / `None` 判别被常量传播抵消，<span class="rr-keypoint">最终生成的机器码与手写 `while` 裸循环一致。</span>

在消费者中，最通用的收集器是依赖 `FromIterator` 契约的 **`.collect()`**（`fn collect<B: FromIterator<Self::Item>>(self) -> B`）。由于目标容器类型 `B` 仅出现在返回值位置，调用时需通过左侧绑定（`let evens: Vec<_> = ...collect();`）或涡轮鱼语法（`.collect::<Vec<_>>()`）指明目标集合类型。

## `Option` 与 `Result` 组合子

把 `Option<T>` 看作「最多包含 0 或 1 个元素的容器」，它与 `Result<T, E>` 提供了与迭代器同名的闭包转换方法——统称**组合子（Combinators）**。由于内部最多只有一个值、闭包至多调用一次，其签名统一采用最宽的 **`FnOnce`**：

| 组合子 | 闭包约束 | 作用（以 `Option<T>` 为例，`Result` 同理） | 等价 `match` 分支 |
| --- | --- | --- | --- |
| **`.map(f)`** | `FnOnce(T) -> U` | `Some(v)` 时返回 `Some(f(v))`，`None` 保持不变 | `Some(v) => Some(f(v)), None => None` |
| **`.and_then(f)`** | `FnOnce(T) -> Option<U>` | `f` 自身也返回 `Option` 时使用，避免套成双层 `Option<Option<U>>` | `Some(v) => f(v), None => None` |
| **`.unwrap_or_else(f)`** | `FnOnce() -> T` | 仅在 `None` 时才惰性调用 `f()` 计算默认值 | `Some(v) => v, None => f()` |

## 审查迭代器与组合子的三类冗余分配

审查业务代码与 AI 生成的流水线代码时，重点拦截三类破坏零成本特性的高频反模式：

1. **链条中途调用 `.collect::<Vec<_>>()` 落盘**：如先写 `let step1: Vec<_> = lines.iter().filter(...).collect();` 紧接着又写 `step1.iter().map(...).sum()`，凭空制造了中间堆分配；应保持惰性适配器链不断开，留到最后一步由单一消费者驱动。
2. **在只读非 `Copy` 链条上前置 `.cloned()`**：对 `words: &[String]` 写 `words.iter().cloned().filter(|w| w.starts_with("ERR:")).count()`，会把即将被 `filter` 丢弃的字符串也逐个深复制并释放；应去掉 `.cloned()` 全程保持 `&String` 借用流转（若只需找首条匹配并复制返回，改用 `words.iter().find(...).cloned()` 短路查找后仅克隆那一项）。
3. **把堆分配或重计算塞进急切求值的 `.unwrap_or(...)`**：`.unwrap_or(default_code.to_string())` 的实参在进入函数前无条件提前求值，即便原值是 `Some` 也会每次白白分配并丢弃一个 `String`；常量标量用 `.unwrap_or(0)`，含分配或函数调用的回退值一律改用惰性的 **`.unwrap_or_else(|| default_code.to_string())`**。
