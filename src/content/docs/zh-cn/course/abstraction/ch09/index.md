在其他主流编程语言里，`for` 循环是第一章花五分钟就能翻过去的基础语法，闭包（Lambda 表达式）也往往被当成黑盒语法糖来使用。但在本指南中，我们特意把它们留到第三篇的收官章才正式拆解。

因为一旦你在 Rust 里真正动手写 `for` 循环和闭包，立刻就会遇到一连串靠死记硬背无法解释的现象：为什么写 `for x in v` 会把整个集合吃掉，而写 `for x in &v` 时左边的 `x` 会自动变成引用 `&T`？为什么一个看起来像函数的闭包，居然区分出了 `FnOnce`、`FnMut`、`Fn` 三种不同的契约？

当你掀开底牌就会发现：**Rust 的语言内核为 `for` 循环和闭包所做的事情极小。** 它们之所以呈现出如此严密的行为，是因为前八章建立的所有核心机制——**独立编译期类型实体、所有权与接收者三件套（`self` / `&self` / `&mut self`）、和类型 `Option<T>`、Trait 关联类型、一揽子实现与编译期单态化**——在这里完成了第一次工程大合流。

本章按三步推进：

1. **剥开 `for` 循环语法糖（`IntoIterator`、`Iterator` 与遍历三件套）**：从 `for` 的基础语法与初学者的碰壁现象出发，认识标准库的 `IntoIterator` 与 `Iterator` 两大契约，看清为什么 `for x in &v` 无需任何编译器特殊规则就能让 `x` 自动变成 `&T`，以及为什么遍历期间修改集合会在编译期直接报 `E0502`。
2. **祛魅闭包（匿名捕获 `struct` 与 `FnOnce` / `FnMut` / `Fn` 三大 Trait）**：还原闭包的物理真相——编译器在编译期自动生成的**匿名结构体类型实体**；看清捕获方式（`&T` / `&mut T` / `T` 及 `move` 关键字）与调用能力（`Fn` / `FnMut` / `FnOnce`）这两根正交轴是如何由结构体字段与方法接收者三件套自然推导出来的。
3. **迭代器适配器链、`Option` / `Result` 组合子与零成本抽象**：将迭代器与闭包串联成 `.iter().filter(...).map(...).collect()` 流水线，验证「泛型单态化 + 优化器内联」两段配合如何将多层嵌套的惰性状态机编译成与手写循环一致的机器码，并掌握代码审查（Code Review）中拦截冗余 `.collect()` 与 `.cloned()` 的工程判据。

## 读完本章，检验自己的四个问题

- 标准库中 `IntoIterator::into_iter(self)` 的接收者明明写死了按值接收 `self`，为什么写 `for x in &v` 时既没有移动原集合 `v`，又让循环变量 `x` 自动变成了引用类型 `&T`？
- 为什么需要 `IntoIterator`（生成游标）和 `Iterator`（推进游标）两个独立的 Trait，直接让集合 `Vec<T>` 实现 `Iterator` 会遇到什么障碍？
- 写下一个闭包 `|x| x + base` 时，编译器在底层生成了什么数据结构？为什么使用了 `move` 关键字按值捕获变量的闭包，仍然可能实现支持多次只读调用的 `Fn` 契约？
- 为什么一长串 `.iter().filter(...).map(...).sum()` 在运行时不会产生每一步的中间数组，也不会发生每次调用的函数指针跳转？
