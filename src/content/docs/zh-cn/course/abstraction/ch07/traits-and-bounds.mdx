在上一节末尾，我们遇到了一个边界：在未加任何附加说明的泛型函数 `fn add_values<T>(a: T, b: T) -> T` 中，编译器必须在**单态化展开之前**就对函数体完成静态检查，而未知的 `T` 除了移动、借用与释放外，没有向编译器承诺任何额外能力。

要让不同的具体类型走进同一个泛型函数并调用共同方法，我们需要引入 Rust 表达跨类型抽象的机制：**Trait（契约）**。

## 基础语法三步曲：定义契约、实现契约与调用

在[方法接收者三件套与自动解引用](/types/methods/)中，我们已经学过用 `impl Article { ... }` 为单个结构体定义固有方法。当多个不同的类型（如文章 `Article` 和监控指标 `Metric`）需要对外承诺同一项能力时，就要通过 **Trait** 分三步完成：

**第一步：用 `trait` 定义契约（只写方法签名，以分号 `;` 结尾）**

```rust
trait Summary {
    fn summarize(&self) -> String;
}
```

**第二步：用 `impl Trait名 for 类型名` 为具体类型签下契约**

注意对比固有实现 `impl Article` 与这里的 **`impl Summary for Article`**：

```rust
struct Article {
    title: String,
    author: String,
}

struct Metric {
    name: &'static str,
    value: u64,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("{} by {}", self.title, self.author)
    }
}

impl Summary for Metric {
    fn summarize(&self) -> String {
        format!("{} = {}", self.name, self.value)
    }
}
```

**第三步：像调用普通方法一样用 `.` 调用**

实现该 Trait 后（且 `Summary` 处于当前作用域内），即可直接在实例上调用 `.summarize()`：

```rust
let post = Article { title: String::from("Rust Root"), author: String::from("Ferris") };
println!("{}", post.summarize()); // 输出：Rust Root by Ferris
```

## 为什么不能直接写 `item: Summary`？

契约定义好之后，我们要写一个通用的通知函数 `notify`，接收任何实现了 `Summary` 的数据并打印摘要。有 Java、Go 或 TypeScript 背景的开发者，第一反应往往是直接拿 `Summary` 当作函数参数的类型：

```rust
fn bad_notify(item: Summary) {
    println!("{}", item.summarize());
}
```

这行代码在 Rust 里会编译失败：

<small class="code-source">编译器诊断摘要（<code>examples/types/traits/src/bin/trait-not-type.rs</code>）</small>
```text
error[E0277]: the size for values of type `(dyn Summary + 'static)` cannot be known at compilation time
  --> src/bin/trait-not-type.rs:32:21
   |
32 | fn bad_notify(item: Summary) {}
   |                     ^^^^^^^ doesn't have a size known at compile-time
```

回到[编译期类型实体](/types/type-entity/)确立的基础规则：**类型 = 内存表示（物理字节大小与布局）+ 约束**。
1. **为什么 Java 的 `interface` 能直接当变量类型？** 因为 Java 对象一律分配在堆上，栈上的变量 `Summary item` 存放的并非对象本身，而是固定字长的对象引用。
2. **Rust 变量默认按值内联在栈上，而 `Summary` 只有行为约束、没有内存表示**：满足 `Summary` 的既可能是 48 字节的 `Article`，也可能是 24 字节的 `Metric`。写下 `item: Summary` 时，编译器无法算出该为栈帧槽位预留多少字节。

因此要先立稳一个核心判断：**在 Rust 中，Trait 本身不是具体值类型，而是筛选类型的编译期契约。**

正确的做法是拿它去**约束泛型类型参数 `<T>`**，写成 **`<T: Summary>`**：

```rust
fn notify<T: Summary>(item: &T) {
    println!("[notify] {}", item.summarize());
}
```

这里充当参数类型的依然是具体的泛型引用 `&T`（在单态化阶段分别展开为 `&Article` 和 `&Metric` 两份机器码），而 `: Summary` 是挂在 `T` 上的准入条件。（若运行时确实需要抹去具体类型实现动态多态，则须显式构造 16 字节胖指针 `&dyn Summary`，我们将在[dyn Trait 与 vtable](/abstraction/dyn-trait-and-vtable/)专门拆解。）

## 泛型约束（Trait Bound）：单态化前的双向检查

写在泛型参数后面的 `<T: Summary>` 称为**泛型约束（Trait Bound）**。需要同时满足多份契约时用 `+` 号叠加，约束较长时也可用 `where` 子句移到签名末尾：

```rust
fn log_and_notify<T: Summary + std::fmt::Debug>(item: &T) { /* ... */ }

fn log_and_notify_where<T>(item: &T)
where
    T: Summary + std::fmt::Debug,
{ /* ... */ }
```

在编译器的检查流水线中，`<T: Summary>` 承担双向检查：

1. **对函数体内部的限制（单态化前只查一次模板）**：签名写下 `<T: Summary>` 后，函数体内获准调用 `item.summarize()`，但也**只能调用 `Summary` 契约声明过的方法**。哪怕你清楚稍后只传入带 `.value` 字段的 `Metric`，只要在 `notify` 内写下 `item.value`，编译器就会当场报 `error[E0609]: no field value on type &T`。
2. **对函数调用点的准入核对（每次调用核对一次）**：在调用点传入未实现 `Summary` 的结构体 `Unregistered` 时，编译器立即拒绝放行，报出高频错误码 **`error[E0277]: the trait bound Unregistered: Summary is not satisfied`**。

### 默认方法与前置父契约（Supertraits）

Trait 契约自身还支持两项常用的组合语法：

1. **默认方法（Default Methods）**：Trait 方法可以直接写出带 `{ ... }` 的默认方法体，并在内部调用同一契约中尚未实现的其他方法：
   ```rust
   trait Summary {
       fn summarize(&self) -> String;
       fn headline(&self) -> String {
           format!("[Breaking] {}", self.summarize())
       }
   }
   ```
   具体类型只需实现 `summarize`，即可自动获得 `.headline()`。
2. **前置父契约约束（Supertraits，如 `trait Printable: Summary`）**：要求任何想实现 `Printable` 的类型必须先实现 `Summary`，从而允许 `Printable` 的默认方法直接调用 `self.summarize()`。注意这不是面向对象的类继承，而是对实现者类型 `Self` 施加的前置约束。

## 数据与行为分离：为外部类型事后挂载本地契约

除了默认走编译期单态化外，Rust 的 Trait 与 Java / C# 的 `interface` 还有一个结构性差异：**数据类型的定义与能力契约的挂载彼此独立**。

在 Java 中，一个类实现哪些接口必须在声明 `class` 时写死；你定义了一个新接口 `Shout`，无法让标准库早已编译好的 `String` 去实现它。而在 Rust 中，`impl Trait for Type` 独立于类型定义之外。只要在当前包（`crate`）里定义了新契约 `Shout`，就能直接为标准库的 `String` 事后挂上这项能力：

## 小结

1. **Trait 是编译期契约而非值类型**：Trait 不规定栈内存大小，不能直接写成 `x: Summary`；静态多态下用它约束泛型参数 `<T: Summary>`。
2. **双向静态检查**：`<T: Trait>` 在单态化前限制函数体只能调用契约内的方法（越界报 `E0609`），在调用点核对实参是否已实现该契约（未实现报 `E0277`）。
3. **事后能力扩展**：`impl Trait for Type` 将数据布局与行为契约解耦，支持在不修改原类型定义的前提下为已有类型扩展本地契约（更多与面向对象 `class` 的结构对照见[附录：没有 class 的对象感](/appendix/comparisons/oop/)）。

本节见过的 `Summary` 和 `Shout`，方法签名里的类型都是固定的。如果一份契约自身还需要涉及另一个待定的类型（如「从某种源类型 `T` 转换过来」或「每次迭代产出某种元素 `Item`」），为什么标准库有时写成尖括号 `trait From<T>`，有时却写成花括号里的 `type Item;`？下一节，我们拆解这对设计分岔。

### 动手核对与小练习

阅读下面这段代码，指出 `process` 函数体内部哪一行会编译失败、`main` 函数中哪一行调用会编译失败，并说明对应错误码的成因：

```rust
trait Measurable {
    fn size_bytes(&self) -> usize;
}

struct Packet {
    payload_len: usize,
    retry_count: u8,
}

impl Measurable for Packet {
    fn size_bytes(&self) -> usize {
        self.payload_len
    }
}

fn process<T: Measurable>(item: &T) -> usize {
    let _retries = item.retry_count; // 位置 A
    item.size_bytes()
}

fn main() {
    let pkt = Packet { payload_len: 128, retry_count: 3 };
    println!("{}", process(&pkt));
    println!("{}", process(&100u64)); // 位置 B
}
```

<details>
<summary>点击核对参考答案</summary>

- **位置 A 编译失败（`error[E0609]: no field retry_count on type &T`）**：`process` 签名仅声明了 `T: Measurable`，编译器在单态化前检查模板时，只允许调用 `Measurable` 契约内的 `size_bytes()`，禁止访问具体结构体 `Packet` 私有的字段 `retry_count`。
- **位置 B 编译失败（`error[E0277]: the trait bound u64: Measurable is not satisfied`）**：标准库的 `u64` 未实现 `Measurable`，在调用点准入核对时被拦截。

</details>
