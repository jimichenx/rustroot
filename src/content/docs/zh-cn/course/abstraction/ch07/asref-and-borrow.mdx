上一节的 `<T: Into<Endpoint>>` 适用于函数需要接管所有权或构造新实例的场景。而在日常更高频的**只读操作**中——例如编写检查文件扩展名是否为 `.toml` 的 `has_toml_ext`，调用方手里可能是 `"Cargo.toml"`（`&str`）、`String`、`&Path` 或 `PathBuf`：若写成 `Into<PathBuf>`，每次传字面量都要无谓分配堆内存；若写死 `path: &Path`，调用方传 `"Cargo.toml"` 又得手动包一层 `Path::new(...)`。

要在**零堆分配、不移走原变量**的前提下兼容多种只读参数载体，标准库提供了借用视图契约 **`AsRef<T>`** 与 **`Borrow<T>`**。

## 零分配视图 `AsRef<T>` 与多载体兼容

`core::convert::AsRef`（可变版本为 **`AsMut<T>`**）的定义只有三行：

```rust
pub trait AsRef<T: ?Sized> {
    fn as_ref(&self) -> &T;
}
```

对比 `Into<U>`，这里有两处关键设计：一是输入 `&self`、输出 `&T`，只从原数据提取一层只读引用（瘦指针或胖指针），零堆分配；二是 `T: ?Sized` 放宽了编译期定长限制，允许目标 `T` 直接填入 `str`、`[u8]` 或路径切片 `Path` 等动态大小类型。标准库已为 `str`、`String`、`Path`、`PathBuf` 实现了 `AsRef<Path>`，这正是 `std::fs::File::open<P: AsRef<Path>>(path: P)` 能同时接收 `"Cargo.toml"` 与 `&PathBuf` 的原因。

除单参外，`AsRef` 还能化解**切片元素多载体兼容**问题。若将拼接主机名的函数写死为 `fn join_hosts(hosts: &[&str])`，调用方手里的 `Vec<String>` 无法直接传入（堆上连续排列的 24 字节 `String` 控制头与 16 字节 `&str` 胖指针布局不同）；改写为泛型切片 `hosts: &[S]`（`S: AsRef<str>`）后，`&[&str]`（`S = &str`）与 `&Vec<String>`（`S = String`）即可零分配共用同一入口。

1. **后续仍需使用的拥有者传参要加 `&`**：`has_toml_ext<P: AsRef<Path>>(path: P)` 按值声明了形参 `P`。由于标准库内置了引用桥接实现 `impl<T: ?Sized, U: ?Sized> AsRef<U> for &T where T: AsRef<U>`，传 `&owned_path` 时 `P` 推导为可复制的 `&PathBuf`，原变量继续有效；**一旦漏写 `&` 写成 `has_toml_ext(owned_path)`，`P` 就会推导为 `PathBuf`，原变量被按值移入函数并在返回时当场释放**（再用报 `E0382`）。
2. **用「泛型薄壳 + 非泛型内层」消除代码膨胀**：若 `has_toml_ext` 内含数十行解析逻辑，直接写在泛型函数体内会随 `&str`、`String`、`&Path`、`PathBuf` 四种调用重复单态化出四份机器码。标准库惯用法如上所示：公开泛型外壳只留一行 `has_toml_ext_inner(path.as_ref())`（优化时直接内联），核心逻辑集中在非泛型的 `has_toml_ext_inner(path: &Path)` 中，全程序只生成一份机器码。
3. **普通单字符串参数直接写 `&str`**：若函数只需单个字符串切片，按[字符串：`str`、`&str` 与 `String`](/types/strings/)的选型准则直接写 `fn parse(s: &str)` 即可——传入 `&String` 时编译器会自动转为 `&str`（机制见[`Deref Coercion` 与接口设计边界](/pointers/deref-coercion/)），仅在跨无包含关系类型（如转 `&Path`）或切片元素兼容（`&[S]`）时才动用 `AsRef`。

## 为什么还需要签名相同的 `Borrow<T>`

`core::borrow::Borrow` 定义为 `fn borrow(&self) -> &Borrowed;`，方法签名与 `AsRef` 相同，但承担着不同的语义承诺：

| 对比维度 | `AsRef<T>`（物理视图提取） | `Borrow<T>`（语义等价借用） |
| --- | --- | --- |
| **哈希与相等性承诺** | **无额外承诺**（`String` 可同时实现 `AsRef<str>`、`AsRef<[u8]>`、`AsRef<Path>`） | **严格一致**：<span class="rr-keypoint">借出的 `&T` 计算出的 `Hash`、`Eq`、`Ord` 必须与原类型一致</span> |
| **自反一揽子实现** | 无 `impl<T> AsRef<T> for T`（仅提供 `&T` 桥接实现） | **内置 `impl<T: ?Sized> Borrow<T> for T`**（任意类型可借用为自身） |
| **典型工程用途** | 路径、字节片等多载体只读入参（`File::open`） | 关联容器的跨类型键值查询（`HashMap::get`）与 `ToOwned` |

这就解释了[键值容器：`HashMap<K, V>`](/types/hashmaps/)留下的现象：为什么 `HashMap<String, u16>` 查询时能直接写 `ports.get("gateway")` 传入 `&str`？若 `get` 用 `AsRef` 约束，一旦某自定义键类型的字节视图与自身哈希算法不同，查询就会算错桶槽位；改用 `K: Borrow<Q>` 后，既可传 `&String`（走自反实现），又可传 `"gateway"`（走 `String: Borrow<str>` 且保证哈希结果相等）：
