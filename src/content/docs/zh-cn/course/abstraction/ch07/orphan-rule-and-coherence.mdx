前几节展示了 `Trait` 体系的高自由度：既能事后为标准库的 `String` 挂载本地契约 `Shout`，又能编写对泛型 `T` 批量生效的一揽子实现。当众多第三方包被组装进同一个程序时，如果尝试给标准库的 `Vec<i32>` 实现标准库的 `std::fmt::Display`，编译器会立即报出 **`error[E0117]`**：

```text
error[E0117]: only traits defined in the current crate can be implemented for types defined outside of the crate
 --> src/main.rs:1:1
  |
1 | impl std::fmt::Display for Vec<i32> {
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^--------
  |                            |
  |                            `Vec` is not defined in the current crate
  = note: define and implement a trait or new type instead
```

这条限制及其在泛型下的变体，均由底层的**全局一致性（Coherence）**直接推出。

## 全局一致性与 `crate` 边界

全局一致性要求：**在整个编译后的程序里，任意一个具体类型对于同一个具体 `Trait`，最多只能存在唯一一份实现。** 若放任不同模块对同一组（`Trait`, `Type`）各写一份实现，会引发两类事故：

1. **单态化符号歧义**：若依赖包 `crate_a` 与 `crate_b` 各自实现了 `Display for Vec<i32>`，主程序调用 `println!("{v}")` 时编译器无法抉择跳转到哪一份机器码；
2. **破坏容器逻辑不变量**：若 `crate_a` 按忽略大小写为 `UserKey` 实现了 `Hash` 与 `Eq`，构造出 `HashMap<UserKey, Account>` 传给 `crate_b`，而 `crate_b` 内生效着区分大小写的另一份 `Hash` 实现，`map.get(&key)` 就会算出错误的桶槽位而查不到已有数据。

由于 `rustc` 的最小独立编译单元是 **`crate`**（完整编译模型见[编译单元 `crate` 与模块封装边界](/architecture/crates-and-modules/)），编译上游包时无法预知未来有哪些下游包会同时引入它。要在不做全网扫描的前提下仅凭局部检查保证全局唯一，就必须执行**孤儿规则（Orphan Rule）**：<span class="rr-keypoint">编写 `impl Trait for Type` 时，`Trait` 或关联的类型中至少有一方必须定义在当前 `crate` 内。</span>

## 泛型下的裸露参数规则

本地契约配外部类型（`impl Shout for String`）与外部契约配本地类型（`impl Display for Article`）均合法。常被混淆的是带有泛型参数的情形——为当前包定义的 `struct LocalId(u8)` 编写以下两份实现时，结果截然相反：

两者都包含本地类型 `LocalId`，为何 `impl From<LocalId> for Vec<u8>` 通过，而取消注释后的 `impl fmt::Display for Vec<LocalId>` 报 `E0117`？

- **`Vec<LocalId>` 中本地类型被外部容器包裹**：如果未来标准库为自己的 `Vec<T>` 新增合理的一揽子实现 `impl<T: Display> Display for Vec<T>`，一旦当前包也定义了 `Display for Vec<LocalId>`（且 `LocalId: Display`），两份实现就会冲突，导致标准库常规升级破坏下游编译；
- **`From<LocalId>` 中本地类型裸露在参数顶层**：`LocalId` 未被任何外部类型构造器包裹，外部标准库不认识私有包里的 `LocalId`，不可能写出与之重叠的特定实现。

因此，泛型下的孤儿规则要求 **`impl` 涉及的契约参数与目标类型序列中，必须至少有一个未被外部构造器包裹的本地类型**（标准库的 `&T` 与 `Box<T>` 带有编译器 `#[fundamental]` 标记，属允许直接穿透的特例）。

## 一揽子实现的内部冲突（`E0119`）

即便在当前 `crate` 内部编写一揽子实现，也常遇到两类 **`error[E0119]: conflicting implementations`**：

1. **与标准库自反实现重叠**：若业务错误 `MyError` 自身实现了 `fmt::Display`，再写 `impl<T: fmt::Display> From<T> for MyError`，当 `T = MyError` 时便会与标准库内置的 `impl<T> From<T> for T` 重叠；
2. **保留上游演进空间**：若先写了 `impl<T: fmt::Display> Summary for T`，又想给尚未实现 `Display` 的 `Vec<i32>` 单独写 `impl Summary for Vec<i32>`，编译器仍会报 `E0119`（`upstream crates may add a new impl of trait Display for type Vec<i32> in future versions`），防止上游日后补充实现时击穿下游代码。

| 工程诉求 | 标准解法 | 原理与成本 |
| --- | --- | --- |
| **让外部容器接入外部契约**（如为 `Vec<LocalId>` 实现 `Display`） | **本地元组结构体包装（Newtype）**：`struct IdList(Vec<LocalId>);` | `IdList` 归属当前 `crate`，栈大小与原 `Vec` 相同、零额外堆分配（详查[`Newtype` 模式](/architecture/newtype-and-parse/)） |
| **为外部类型补充点号方法**（如为 `&[i32]` 增加 `.join_arrow()`） | **扩展契约模式（Extension Trait）**：定义本地 `trait JoinArrowExt` 并对 `[i32]` 实现 | 契约归属当前 `crate`；调用方引入该 `Trait` 即可直接点出方法 |
| **归并多种底层错误**（避免 `impl<T: Error> From<T>` 报 `E0119`） | **按具体源错误变体逐一实现 `From`** | 明确列出已知底层错误分支，不与自反实现重叠 |
