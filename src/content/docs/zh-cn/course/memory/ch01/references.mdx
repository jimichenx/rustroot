上一节建立的最简模型共有两条规则：栈变量离开作用域（`}`）时自动释放它管理的堆；承担释放责任的值在赋值时走移动语义，值与释放责任一并移交给新变量，原变量不再可用。现在把这套规则放进日常的函数调用里检验一下。

## 按值传参的困境：只读一次，实参就被移走

假设写一个只读函数 `print_it`，什么都不修改，只把动态字符串 `s` 传进去打印一行，随后在调用方继续打印 `s`：

```text
fn print_it(msg) {
    print(msg)
}   // ← msg 在这里离开作用域

{
    s = alloc_heap("hello")
    print_it(s)
    print(s)   // ← 还能使用吗？
}
```

顺着上一节的规则逐步推演，调用 `print_it(s)` 会依次发生四件事：

1. **传参就是赋值**：调用 `print_it(s)`，相当于把实参 `s` 赋值给函数的形参 `msg`（`msg = s`）；
2. **触发移动**：字符串管理着堆资源，走移动语义，`msg = s` 当场把值与释放责任转移给函数内的形参 `msg`，外层的变量 `s` 随之失效；
3. **函数返回时释放堆内存**：`print_it` 打印完毕返回，`msg` 离开函数作用域，当场把堆上的 `"hello"` 释放给分配器；
4. **调用方无法继续使用**：回到外层代码块，不仅 `s` 已经失效，堆上的字符缓冲区也已经被 `print_it` 销毁。

如果在不修改模型的前提下，硬要让调用方在 `print_it` 返回后继续使用这份字符串，只能让函数在末尾把参数重新 `return` 回来，再由调用方重新接住：

```text
fn print_it(msg) {
    print(msg)
    return msg   // ← 读完还必须把值移回去
}

{
    s = alloc_heap("hello")
    s = print_it(s)   // ← 每次调函数都得重新接住返回值
    print(s)
}
```

倘若一个函数只想读取 3 个字符串并返回一个计算结果，就得传入 3 个参数，再返回一个四元组 `(result, s1, s2, s3)` 供调用方逐个拆解。只靠移动语义，无法支持日常的函数协作。

症结在于「读取数据」和「承担释放责任」被捆在了一起：要让 `print_it` 读到字符串，就必须把完整的三格控制结构传给形参，释放责任也随之移交。怎么让函数既能找到数据，又不用搬动原变量 `s`？

## 传地址的直觉：为什么不能直接照搬 C 的裸指针

顺着[栈与堆](/memory/stack-and-heap/)的内存布局想，最自然的物理方案现成就有：**不传 `s` 那三格控制结构，只取变量 `s` 在栈上的内存地址（8 字节）传给函数。**

在计算机底层，这种保存另一处内存地址的值，广义上就是**指针（Pointer）**。函数拿到这 8 字节地址后，先顺着它定位栈上的 `s`，再顺着 `s` 里的堆指针 `ptr` 就能读到堆上的 `"hello"`，原变量 `s` 原地不动。

既然物理上需要的就是一个地址，为什么不能直接照搬 C 语言里现成的指针？

因为 C 语言的指针是一种狭义的**裸指针**：在硬件层面，只要拿到了 `s` 的栈地址，顺藤摸瓜就能触碰里面的一切字节；而裸指针是一串没有任何规则约束的纯地址，物理上能做到的事，语言全部放行：

1. **释放责任失控**：裸指针不区分「谁拥有这份资源、谁只是临时读取」。函数拿到指向 `s` 的裸指针后，既可以顺着它直接读取里面的堆地址并调用 `free` 提前释放堆内存，也可以把三格控制头按位复制出来另起炉灶——上一节刚立起的「唯一释放责任」当场被击穿，双重释放重新出现；
2. **地址与读写失控**：裸指针允许保存空地址（`NULL`），允许随意加减整数偏移指向未知区域，也允许在别处正顺着地址读取数据时原地改写内容、触发堆缓冲区扩容重分配，使原有的堆地址作废。

可见，「传递 8 字节内存地址」这个硬件机制本身没有错；真正破坏模型的，是裸指针缺少编译期的职责边界。

## 给指针立下规则：剥离释放责任的「引用」

站在模型设计者的角度，解法随之清晰：**在运行时的物理表示上，依然保留指针的高效形态（栈上 1 个机器字、8 字节内存地址）；但在编译期的模型规则上，收回裸指针的越权能力。**

对照配图，原变量 `s` 与受限地址 `&s` 在物理形态和职责上各司其职：

- **原变量 `s`**：在栈上持有完整的三格控制结构（`ptr`、`len`、`cap`），离开作用域时**承担唯一的释放责任**；
- **受限地址 `&s`**：在栈上只占 **1 个机器字（8 字节）**，里面存放变量 `s` 的栈地址。顺着它读取数据需要经过两跳：先找到栈上的 `s`，再顺着 `s` 里的 `ptr` 读到堆上的 `"hello"`。同时，模型在编译期给它加上了明确的限制：**剥离释放责任，且只开放读取权限**——既不允许拿着它去释放内存，也不允许顺着地址把 `s` 持有的值移走，更不允许随意做地址加减偏移；当持有 `&s` 的变量离开作用域时，只随栈帧收回栈上那 8 字节地址，不去触碰堆资源。

释放责任留在原来的变量 `s` 上——**地址给你用，责任还在我。**

为了与 C 语言那种毫无约束的狭义裸指针区分开，我们把这种**物理上保存内存地址、规则上剥离了释放责任的受限指针**，称为**引用（Reference）**。

## 不承担释放责任，所以只读引用走复制语义

一旦把引用定性为「栈上 8 字节地址，且规则上不承担释放责任」，上一节的规则就会直接推出它的赋值语义。

回顾上一节区分复制与移动的原因：同一块堆同一时刻只能释放一次，因此**承担释放责任**的值赋值时必须走移动语义；而像普通整数那样**不承担堆释放责任**的值，赋值时走复制语义，「一变二」后两边各自有效。

现在看引用 `&s`：它在栈上只有 8 字节地址，且已经被剥离了释放责任。哪怕把 `&s` 按位复制出一百份，等到这一百个引用变量离开各自的作用域时，它们都只是随栈帧收回栈上的 8 字节地址，没有任何一个会触发堆释放，不会产生双重释放。

因此，在本模型中，**只读引用天然走复制语义**——与普通整数一样，无论赋给多少个变量、传给多少个函数，都只是复制那 8 字节地址，原变量和各处引用全部继续有效。

用引用重写开头的例子，函数传参的阻碍随之解开：

```text
fn print_it(msg) {     // ← 接收引用，不接手释放责任
    print(msg)
}   // ← msg 离开作用域，只收回 8 字节栈地址，堆数据保留

{
    s = alloc_heap("hello")
    print_it(&s)       // ← 只把 s 的受限地址传给函数
    r1 = &s            // ← 复制 8 字节地址，复制语义
    r2 = &s            // ← 再次复制地址，多个只读引用同时并存
    print(s)           // ← s 从未移走，继续正常读取
}   // ← 只有原变量 s 在此处离开作用域时，释放一次堆资源
```

<Aside type="note" title="为什么这里只开放「读取」权限？">
本节设计的引用只允许顺着地址**读取**数据，不允许修改数据。多处代码同时只读同一份内存互不干扰；如果允许通过引用修改数据（例如向动态字符串追加内容触发堆扩容搬迁，导致旧堆地址作废），就会引入新的读写冲突——支持修改的引用需要怎样的排他约束，留待后续[引用与可变引用](/types/reference-constructors/)专门推导。
</Aside>

## 留下的隐患：它的物理本质依然是地址

引入引用之后，我们的自动回收模型同时具备了两项能力：

1. **释放责任唯一且时机确定**：每块堆资源只归原变量（如 `s`）负责，离开 `{}` 时自动释放，无需 GC 也不会双重释放；
2. **数据支持不复制堆数据的读取与多处共享**：只使用数据时传递引用 `&s`，按复制语义传递 8 字节地址，原变量不会被移走。

不过，剥离释放责任只管住了引用「不去越权释放别人的内存」。别忘了，**引用在运行时的物理本质依然只是一个保存着栈地址的 8 字节指针**，目标数据何时释放完全听原变量 `s` 的。顺着这一点往下想一步，马上会露出最后一道安全缺口：如果负责释放的原变量和拿着地址的引用不在同一个作用域里——**万一原变量先一步离开作用域把数据释放了，而外层的引用变量手里还留着那个旧地址，会发生什么？**
