上一节我们从传递内存地址（指针）的物理思路出发，设计出了剥离释放责任的**引用**：真正负责释放堆内存的是原变量 `s`，而引用 `&s` 只在栈上保存 `s` 的 8 字节地址，离开作用域时不释放堆。

上一节末尾留下了一个边界问题：如果负责释放的原变量先一步离开作用域，而外层还留着指向它的引用，会发生什么？

## 原变量先离开作用域：地址指向失效内存

不需要复杂的函数调用，只要嵌套一个内层代码块 `{}`，就能复现这个问题：

```text
{
    r;   // 外层先声明变量 r，准备存放引用
    {
        x = alloc_heap("hello")
        r = &x   // 把内层变量 x 的栈地址赋给外层的 r
    }   // ← 内层结束，x 在这里离开作用域
    print(r)     // ← 顺着 r 保存的地址读取，会发生什么？
}
```

按已有规则逐步推演这段代码的执行过程：

1. 内层代码块里，变量 `x` 申请了堆上的 `"hello"`，并承担在离开内层 `{}` 时释放它的责任；
2. `r = &x` 把 `x` 的栈地址复制给外层变量 `r`，释放责任仍留在 `x` 身上；
3. 走到内层 `}` 闭合：`x` 离开作用域失效——它管理的堆缓冲区 `"hello"` 当场归还给分配器，`x` 原本占用的栈槽位也随之作废（后续随时可能被其他变量复用；即便 `x` 只是纯栈上的整数，离开 `{}` 后指向该槽位的地址同样不再有效）；
4. 回到外层代码块：变量 `r` 仍在作用域内，栈上的 8 个字节里原封不动留着 `x` 的旧地址。下一行 `print(r)` 顺着这个地址读取，访问到的已经是失效的内存。

<ShorterBorrow part="dangle" />

这种「引用本身仍在作用域内，但所指数据已经释放失效」的错误，称为**悬垂引用（Dangling Reference）**。

注意它与[复制与移动](/memory/minimal-model/)中「移动后继续读取原变量」的区别：移动之后，原变量里的值已经移走，原变量自身处于已失效状态；而悬垂引用中，引用变量 `r` 自身仍然有效，**已经释放退场的是它指向的目标变量 `x`**。

## 为什么不能留到运行时拦截

面对 `print(r)` 这一行即将发生的非法读取，程序能否在**运行时**顺着 `r` 发现异常并拦住它？

回到 `r` 在内存里的物理表示：**在运行时，引用 `r` 在栈上只是一个 8 字节的内存地址。** 这 8 个字节只记录目标位置，没有任何比特位记录「目标变量 `x` 此刻是否仍然存活」。CPU 执行到 `print(r)` 时只管按地址取字节，无从分辨目标内存有效还是已经失效。

如果强行在**运行时**阻止这次非法访问，只剩两条老路：

1. **因为 `r` 还指着，推迟 `x` 的释放时机**：等所有引用都不再使用时再回收内存——这等于把释放时机的裁决交回给运行时（追踪式 GC 或引用计数），直接推翻了[困难三角](/memory/hard-triangle/)确立的「非 GC」前提；
2. **在运行时额外维护内存有效状态表**：每次解引用读取前先查表校验目标地址是否仍有效——这意味着每一次普通内存访问都要增加额外的运行时检查指令与存储成本，同样违背零开销目标。

既不能延后释放，又不能给每次读取附加运行时检查，运行时的路全部走不通。

## 修补模型缺口：在编译期识别风险并拒绝编译

既然运行时无法兜底，要弥补引用带来的这道安全缺口、守住整个内存回收模型的安全与正确性，就只剩唯一一条出路——把防线前移到程序运行之前，为模型补上第三条硬性规则：

**凡是存在悬垂风险的引用代码，编译器必须在编译期识别出来，直接报错并拒绝编译通过，绝不让它生成可执行文件。**

在 C 语言里，编译器会放行开头的悬垂代码，把内存访问错误留到程序上线运行时才爆发；而在我们的模型里，「不让问题代码通过编译」本身就是内存安全机制的核心一环——既然运行时只留零开销的 8 字节裸地址，所有安全证明就必须在编译期做完。

那么，程序还没有真正跑起来，编译器凭什么能在编译期提前算准一个引用会不会悬垂？

## 编译器怎么算：比对两段有效区间

其实不需要运行程序，编译器只要顺着源码的静态结构算出两段区间，做一次包含关系比对就够了：

- **原变量 `x` 的存活区间**：从 `x` 初始化生效开始，到它所在作用域闭合的 `}` 释放为止；
- **引用 `r` 的有效区间**：从 `r = &x` 取得地址开始，到源码中最后一次使用 `r`（即 `print(r)`）的那一行为止。

把两段区间画成时间轴横条，合法与悬垂的边界一目了然：

<ShorterBorrow part="span" />

- **左图（合法）**：引用 `r` 的有效区间完全落在原变量 `x` 的存活区间之内——只要代码还在使用 `r`，`x` 就尚未离开作用域，顺着地址读取始终安全；
- **右图（悬垂）**：引用 `r` 的有效区间超出了原变量 `x` 的存活终点——`x` 在内层 `}` 处已经释放退场，后面却还要读取 `r`，编译器直接在编译期报错拦截。

规则浓缩为一句话：**引用的有效区间不能超出被引用数据的存活区间（引用活不过它指向的原变量）。**

给这段区间起个名字：引用有效的这段区间，就称为**生命周期（Lifetime）**。这项机制有两个直接的工程特征：

1. **零运行时开销**：区间推算与比对全部在编译期完成；检查通过后生成机器码时，区间信息被擦除，运行时引用依然只是一个纯粹的 8 字节地址。
2. **函数内部自动推算**：在日常函数体内，编译器会自动按变量作用域与引用最后一次使用的位置完成比对，不需要手写额外标注；只有当引用跨越函数签名或装进自定义数据结构时，才需要显式声明来源关系。

## 三条防线合拢

补上编译期的有效区间比对之后，我们从[困难三角](/memory/hard-triangle/)出发搭起的这套自动内存回收模型，已经合拢了全部三条核心防线：

1. **栈变量离开作用域（`}`）时自动释放管理的堆资源**——无需手写 `free`，无需运行时 GC，防止常规路径遗漏释放；
2. **承担释放责任的值赋值走移动语义**——值与释放责任一并移交给新变量，原变量不可再用，保证同一块堆同一时刻只由唯一变量负责释放；
3. **引入剥离释放责任的引用，并在编译期核对有效区间（生命周期）**——支持按复制语义共享读取而不复制堆数据，同时在编译期拦截悬垂引用。
