title: 从自动释放到所有权
description: 不引入语法负担，从栈与堆的物理事实一步步推导出一套不靠 GC、也不靠人手写 free 函数的自动内存回收模型。
id: ownership
---

这一章要解决一个看似矛盾的问题：**如果不靠人手写每一次 `free` 函数，也不靠垃圾回收（Garbage Collection，GC）在运行时扫描或计数，程序怎样既自动回收内存，又保证内存安全？**

为了不受语法细节干扰，本章六节是一场连续的第一性原理推演——前五节不写实际的 Rust 语法，也不预先搬出「所有权」「借用」这些顶层条文，而是站在模型设计者的视角，顺着每次遇到的安全缺口一步步把规则逼出来，等具体机制落定后再给它起名；最后一节再将整套机制与 Rust 的标准术语完整对位。

六节分三段推进：

- **第一段：摆出问题与内存底图。** 从编程语言的困难三角确立「自动回收、但非 GC」的切入方向，再看清栈帧与堆块不同的存续方式，找到决定堆释放时机的静态线索。
- **第二段：从旧变量失效到移动语义。** 先立起「栈变量离开作用域就释放堆」的最简规则，再用一行赋值暴露双重释放冲突，看清语言如何将「旧变量失效」重塑为移动语义，以及它背后的物理真相。
- **第三段：从受限指针到自动插入 `free` 函数。** 为解开按值传参移走实参的阻碍，顺着传递内存地址的思路设计出受限指针（引用）并在编译期比对有效区间（生命周期），最后对位所有权与借用，收束于「在正确的位置自动插入 `free` 函数」。

读完这一章，不需要背诵任何语法条文，你应该能自己推清楚三件事：

1. 为什么栈上的局部变量随函数返回自动收回，而堆资源必须有人负责归还？
2. 为什么同样是一行赋值 `=`，整数走复制语义，管理堆资源的动态字符串却走移动语义，而硬件底层并没有搬走数据？
3. 为什么物理上同样是 8 字节地址的引用可以自由复制共享，却必须由编译器在编译期限制它的有效区间？
