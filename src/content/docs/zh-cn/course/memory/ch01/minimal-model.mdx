上一节末尾找到了自动释放的线索：堆上的资源自己没有确定的释放时刻，但管理它的栈变量有——函数返回或代码块闭合（`}`）时，栈变量离开作用域的位置在编译期一清二楚。

这一节先不引入 Rust 语法，顺着这条线索搭出一套最简自动回收模型，再用日常的赋值语句 `=` 检验它。

## 最简规则：栈变量离开作用域时释放堆

把上一节的线索立为模型的第一条规则：

**栈上的变量离开作用域（`}`）时，自动释放它指向的堆资源。**

假设在一个代码块里申请一块堆内存，用栈变量 `s` 管理它：

```text
{
    s = alloc_heap("hello")
    // ... 在当前代码块内读写 s ...
}   // ← s 在这里离开作用域，它指向的堆资源自动释放
```

只要从头到尾只有 `s` 这一个变量管理这块堆内存，这套规则就能跑通：

- 不需要手写 `free`，不会因为遗漏释放而造成内存泄漏；
- 释放时机就在 `}` 这一行，编译期完全确定，运行时不需要扫描或计数。

接下来，用一行普通的赋值语句 `=` 测试这套模型。

## 一行赋值，为什么会释放两次

先测试栈上的普通整数：

```text
{
    a = 1
    b = a
}   // ← b、a 离开作用域，随栈帧直接收回
```

赋值 `b = a` 把 `a` 在栈上的字节按位复制一份给 `b`。整数 `1` 的字节全部在栈上，没有申请任何堆资源，复制完成后 `a` 和 `b` 各自持有一份独立的 `1`。走到 `}` 闭合时，两个栈变量随栈帧收回，不触发任何堆释放，平安无事。

再测试管理堆资源的动态字符串：

```text
{
    s = alloc_heap("hello")
    t = s
}   // ← 作用域结束，会发生什么？
```

上一节看过，这类值在栈上存着三个机器字的控制头（堆指针 `ptr`、长度 `len`、容量 `cap`），字符缓冲区 `"hello"` 在堆上。

执行 `t = s` 时，同样把 `s` 栈上的三个机器字按位复制给 `t`。**堆指针 `ptr` 也被原样复制了一份，一行赋值把两个栈变量压到了同一块堆上，而不是各自拥有一份字符缓冲区。**

<OneBinding part="share" />

走到代码块结尾的 `}` 时，局部变量按声明的相反次序退场，`t` 先走，`s` 后走。「离开作用域就释放堆」的规则会对两个变量各执行一次：

1. `t` 离开作用域，自动释放它指向的那块堆资源；
2. `s` 尚未退场，手里的 `ptr` 已经指向被释放的堆内存——产生**悬垂指针**；
3. 紧接着 `s` 也离开作用域，对着同一块堆地址再执行一次释放——触发**双重释放**，导致未定义行为。

症结出在赋值之后的局面：只要两个栈变量同时管理同一块堆，「离开作用域自动释放」就会执行两次。由此逼出一条必须守住的约束：

**每一块堆资源，同一时刻只能由一个栈变量负责释放。**

## 修补模型缺陷：强制规定旧变量失效

最简模型被一行 `t = s` 击穿了。要想在不引入 GC、也不深层复制堆数据的前提下保住模型的正确性，我们不得不给模型打上一条硬性补丁——既然同一块堆不能同时由两个变量负责释放，赋值之后就强行废掉原来的那一个：

**带着堆资源的值在赋值时，把释放责任交给新变量，并规定旧变量当场失效、后续禁止再使用。**

<OneBinding part="move" />

打上这条补丁之后，模型缺口立刻合拢了：`t = s` 执行完，有效的变量只剩 `t` 一个；走到代码块末尾的 `}` 时，只有有效的 `t` 会释放堆资源，已经失效的 `s` 不再触发释放，双重释放随之消除。只有强制让旧变量失效，最简自动回收模型的正确性才能守住。

## 从「旧变量失效」到「移动语义」

模型在数学上算准了，但站在写代码的人眼里，这条补丁却带来了一个非常别扭的割裂感。

把刚才两段代码里的赋值放在一起看：

```text
b = a    // 赋值后，旧变量 a 依然有效
t = s    // 赋值后，旧变量 s 突然失效
```

明明写下的是完全相同的赋值语法 `=`，凭什么有时候旧变量还能继续读，有时候旧变量就当场作废了？

如果一门语言把 `=` 解释成「先复制一份，再按条件处罚并废掉旧变量」，对人类的思维是极不友好的——在程序员的习惯里，复制完的东西理应两边都在；要求大脑时刻背诵「哪些类型赋值后会触发作废禁令」，写每一行代码都像在踩暗雷。

为了让这套机制顺应人类的直觉思维，语言设计上做了一次关键的**心智模型重塑**——不再把 `t = s` 描述成「复制后把旧变量作废」，而是把同一个 `=` 拆成两种符合日常直觉的交接动作：

- **复制（Copy）语义**：像整数 `b = a` 这样不牵涉堆释放责任的值，赋值是「一变二」的**复制**——给 `b` 抄了一份，`a` 手里原封不动，两边自然都能继续用；
- **移动（Move）语义**：像字符串 `t = s` 这样绑定着唯一释放责任的值，不能「一变二」，赋值是把值连同释放责任从 `s` 手里整体**移动**到 `t` 手里——既然东西已经从 `s` 移走了，`s` 里面自然就空了，当然不能再从 `s` 读取，退场时也只有握着东西的 `t` 负责归还。

把机械的「旧变量失效规则」改造为**移动语义**之后，你再也不需要死记「某变量被强行作废」的负向禁令，只要顺着「值复制了，还是移走了」去想，谁有效、谁负责释放便一目了然。在这个最简模型里，不带堆资源的值走复制语义，带着堆资源的值走移动语义。

## 掀开移动的物理底牌：移动只是语义，硬件只做复制

立稳了「移动」这层直觉模型，最后必须把根扎回物理事实，防住一个最常见的误解：**当我们说值从 `s`「移动」到了 `t` 时，计算机的物理内存里真的发生了把数据搬走、把 `s` 掏空的动作吗？**

**没有。「移动」纯粹是编译期建立的语言层语义，硬件底层从来没有「移动」这回事。**

硬件内存里的字节只能被读取、复制或覆盖。把**运行时的物理内存**与**编译器的内部状态表**拆开对照，就能看清「移动语义」在底层到底是怎么落地刚才那条「旧变量失效」规则的：

1. **在运行时的物理内存里，发生的依然只是栈字节的按位复制**：
   - 堆上的字符缓冲区 `"hello"` 原地不动，没有发生堆数据复制；
   - 局部变量所在的栈帧要等函数返回时才整块收回，无法半路单独释放 `s` 的栈槽位，内存里也没有打上任何表示「失效」的物理标记位（flag）；
   - 在未优化的基础模型里，CPU 执行 `t = s` 做的物理动作和整数 `b = a` 完全一样——**只是把 `s` 栈槽位里的 24 字节控制头按位复制了一份给 `t`**，`s` 原来的栈槽位里依然留着那 24 字节（生成最终机器码时，编译器甚至可以直接优化掉这次栈复制）。
2. **「移走 / 失效」的效果，全部记录在编译器的编译期状态表里**：
   - 编译器分析源码时，在内部维护一张状态表，追踪每个变量当前是否有效、归不归它负责释放；
   - 扫描到 `t = s` 时，状态表把 `s` 改记为**已失效（已移出）**，把释放责任转记到 `t` 名下；
   - 如果后续代码还试图读取 `s`，编译器查表发现 `s` 已失效，直接在**编译期报错**拦下，拒绝生成可执行文件；
   - 编译到代码块末尾的 `}` 时，编译器按状态表只为仍然有效的 `t` 生成一条释放堆内存的机器指令，对已失效的 `s` 什么指令都不生成。

理解这一层分野之后，我们就能在两个层面自如切换：**分析代码逻辑时，用「移动语义」一眼看清值和责任流向了谁；分析运行开销时，清楚底层只是栈控制头的按位复制加编译期的静态状态切换，没有任何运行时额外负担。**

## 最简模型解决了什么，又卡在哪里

把本节推出来的两条规则合在一起，已经正面回应了[困难三角](/memory/hard-triangle/)的目标：

1. **栈变量离开作用域时自动释放堆资源**——不靠手写 `free`，也不依赖运行时扫描或计数；
2. **承担释放责任的值在赋值时走移动语义（编译期将旧变量记为失效并移交责任）**——保证同一块堆同一时刻只由一个变量负责释放，排除了双重释放。

这套模型在单个代码块内已经严密自洽，但放进日常编程场景一试就会露出明显的阻碍：写程序离不开函数调用，如果只是把一个字符串传给函数打印一次，按移动语义会发生什么？调用方还能继续使用原来的变量吗？
