前五节没有写一行实际的 Rust 语法，只顺着栈与堆的物理事实，一步步逼出了一套「既不靠手写 `free`、也不靠运行时 GC」的自动内存回收模型。

到了本章收束处，我们把 Rust 官方教程里的标准术语端出来，与你亲手推演出的机制逐一对上号。

## 对照官方教程的「所有权三条规则」

翻开 Rust 官方教程（*The Book*）讲所有权的开篇，迎面看到的就是**所有权三条规则（Ownership Rules）**：

> 1. Rust 中的每一个值都有一个**所有者（Owner）**。
> 2. 同一时刻，一个值**只能有一个所有者**。
> 3. 当所有者离开**作用域（Scope）**时，这个值将被**释放（Dropped）**。

脱离底层内存直接背诵这三条条文，往往会把它们当成语言强加的生硬禁令。现在回头对照[复制与移动](/memory/minimal-model/)的推演，每一句话都对应着明确的物理原因：

- **第 1 条与第 3 条（谁来释放、何时释放）**：堆上的资源自己不知道何时回收，但持有控制结构的栈变量有确定的作用域终点（`}`）。把这个栈变量定为**所有者**，规定它离开 `{}` 时自动触发**释放（Drop）**，就省去了手写 `free`。
- **第 2 条（为什么同一时刻只能有一个所有者）**：如果 `t = s` 让两个有效变量同时管理同一块堆，离开 `{}` 时就会触发双重释放。为了守住「只释放一次」的安全底线，承担释放责任的值在赋值时必须把值与责任一并移交给新变量（旧变量在编译期失效，运行时只按位复制栈控制头）——这就是**移动（Move）**；不承担堆释放责任的值，按位复制后两边各自有效——这就是**复制（Copy）**。

## 对照「借用」与「生命周期」

只靠上面三条所有权规则，连调用一个只读函数 `print_it(s)` 都会把实参移走并提前释放堆内存。为了解决日常协作与指针安全问题，我们在[引用](/memory/references/)和[悬垂引用](/memory/lifetimes/)中又推出了两组配套概念：

- **引用（Reference）与借用（Borrowing）**：物理上保存目标地址、规则上剥离了释放责任的受限指针称为**引用**；创建引用、把地址交给别处读取而不让出所有权的动作称为**借用**（「地址给你用，责任还在我」）。
- **生命周期（Lifetime）与借用检查器（Borrow Checker）**：引用自身不管释放，一旦所有者先离开作用域释放了数据，就会产生悬垂引用。编译器内部负责在编译期追踪变量状态、拦截「移动后继续使用」并核对「引用有效区间（**生命周期**）不超出所有者存活区间」的静态分析模块，就是**借用检查器**。

按前五节「遇到什么问题 → 推出什么规则 → 对应什么术语」的推演链，整章脉络可以收拢为一张表：

| 推演中遇到的问题 | 本章推出的模型规则 | Rust 核心术语 |
| --- | --- | --- |
| 栈帧返回后堆数据留在原地，漏还即内存泄漏 | 绑定唯一栈变量，离开作用域 `{}` 时自动释放堆 | **所有权（Ownership） / 释放（Drop）** |
| `t = s` 按位复制控制头，导致同一块堆释放两次 | 承担释放责任的值赋值时移交责任、旧变量失效 | **移动（Move）** vs **复制（Copy）** |
| 按值传参会把实参移走，读一次数据就销毁堆 | 传递剥离了释放责任的 8 字节栈地址（只读） | **引用（Reference） / 借用（Borrowing）** |
| 原变量先离开 `{}` 释放数据，外层引用地址失效 | 编译期比对引用有效区间不超出原变量存活区间 | **生命周期（Lifetime） / 借用检查器** |

## 剥开术语外壳：在正确的位置自动插入 `free` 函数

初次看到「所有权、移动、借用、生命周期」这一串专有名词，不少人会误以为 Rust 在运行时维护了一套复杂的内存管理引擎。

回到[困难三角](/memory/hard-triangle/)的起点看，向分配器动态申请的堆内存，终归要调一次类似 C 语言 `free` 的函数归还回去。单看本章的内存回收问题，剥开所有术语和方案，整套机制完成的任务其实只有一件：**让编译器代替程序员，在编译期算准唯一正确的位置，自动插入那一行 `free` 调用（在 Rust 中统一称为 `drop`）**——所有权决定把这行调用插在哪个 `{}` 处，移动保证同一块堆不会被 `free` 两次，借用与生命周期保证 `free` 执行之后不再有任何指针去读它。

一旦借用检查器在编译期核对通过、把释放调用静态写进机器码，所有权、借用和生命周期这些概念在最终的可执行文件里就全部擦除了。到了运行时，既没有垃圾回收器扫描，也没有额外的计数开销，执行过程就和手写得严丝合缝的 C 代码一样直接。

## 综合推演：为配置加载设计传参方式

先不用写完整的 Rust 语法，直接用本章建立的模型做一次设计裁决。

假设主代码块从磁盘读入了一段配置文本 `config`（字符缓冲区存放在堆上），随后依次执行三步操作：

1. 调用 `validate(config)` 检查配置格式是否合法（只读取 `config`）；
2. 调用 `print_banner(config)` 打印启动摘要（只读取 `config`）；
3. 调用 `start_server(config)` 将配置交给后台服务长期持有，主代码块后续不再使用 `config`。

请顺着模型回答三个问题：

1. **选择传参方式**：在 `validate`、`print_banner` 和 `start_server` 三次调用中，哪几次应该传**引用（`&config`）**，哪一次应该直接传**值（`config`，触发移动）**？为什么？
2. **诊断错误返回**：如果有人编写 `validate` 时，试图在函数内部构造一个局部临时字符串 `temp`，并把它的引用 `&temp` 作为返回值交给调用方使用，借用检查器会依据哪条规则拒绝编译？它违反了什么物理事实？
3. **追踪释放位置**：按第 1 题选定的方案，`config` 管理的堆缓冲区最终会在哪个函数或代码块闭合的 `}` 处被释放？

<details>
<summary>点击核对推演答案</summary>

1. **传参方式选型**：
   - `validate(&config)` 与 `print_banner(&config)` 应传**引用（借用）**。这两个函数只需读取内容，且调用返回后主代码块还要继续使用 `config`；若按值传入，第一次调用 `validate(config)` 就会触发移动使 `config` 失效，并在 `validate` 返回时把堆缓冲区提前释放。
   - `start_server(config)` 应直接传**值（移动）**。主代码块此后不再使用 `config`，而服务需要接手这块堆内存的唯一所有权与后续释放责任。
2. **错误返回诊断**：
   - 借用检查器会依据**生命周期**规则拒绝编译。
   - 物理事实：局部变量 `temp` 位于 `validate` 的栈帧中，当 `validate` 返回（遇到 `}`）时，`temp` 离开作用域并当场释放它管理的堆内存，栈帧也随之收回。若将 `&temp` 返回给外部调用方，引用的有效区间超出了所有者 `temp` 的存活区间，必然变成**悬垂引用**。
3. **最终释放位置**：
   - 前两次调用只是借用（不转移释放责任），第三次调用 `start_server(config)` 将所有权移动给了 `start_server` 的参数（或内部接管它的字段），因此这块堆内存最终在 `start_server` 一侧持有它的所有者离开作用域（`}`）时释放。

</details>
