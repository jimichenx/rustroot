上一节的每一个 `=` 左侧都带有 `let`，用于在声明新变量时建立初始绑定。如果变量已经声明，后续**不写 `let`**、直接写 `x = ...` 更新该变量，需要理清两个问题：默认不可变的绑定限制了什么，以及新值换入时原有的旧值去了哪里。

## 默认不可变与 `let mut` 的两项权限

在 Rust 中，直接用 `let` 声明的变量默认是**不可变绑定**。对普通所有者变量而言，不可变绑定同时限制了**两项不同的修改权限**。

### 1. 第一项权限：重新赋值（`x = ...`）

下面这段程序中，`n` 初始化为 `7`，注释行试图将它改为 `8`：

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/immutable.rs</code></small>
<Code code={immutable} lang="rust" />

取消 `// n = 8;` 的注释后，编译器拒绝编译：

<small class="code-source">编译器输出（取消 immutable.rs 中注释行后）</small>
```text
error[E0384]: cannot assign twice to immutable variable `n`
```

`error[E0384]` 拦截的是**重新赋值（Reassignment）**。若要向已有变量换入新值，声明时须加上 `mut`，写成 `let mut n = 7;`。

需要注意，`let mut` 允许更新值，但**不允许改变变量的类型**：

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/type-mismatch.rs</code></small>
<Code code={mismatch} lang="rust" />

取消 `// n = String::from("hello");` 的注释会触发类型不匹配（`error[E0308]: mismatched types`，预期 `i32`，实际为 `String`）。`n` 在声明时已固定为栈上 4 字节的 `i32`，`mut` 只允许向该槽位写入新的 `i32`，不能将它改成占 24 字节控制头且带释放责任的 `String`。

### 2. 第二项权限：修改内部数据

再看第二项权限。声明不可变绑定 `let s = String::from("hello");`，后续不执行 `s = ...` 重新赋值，只调用 `s.push_str("!")` 向堆缓冲区末尾追加字符：

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/mutate-content.rs</code></small>
<Code code={mutateContent} lang="rust" />

取消 `// s.push_str("!");` 的注释后，编译器报出另一条错误：

<small class="code-source">编译器输出（取消 mutate-content.rs 中注释行后）</small>
```text
error[E0596]: cannot borrow `s` as mutable, as it is not declared as mutable
```

`s.push_str("!")` 会更新栈上控制头的长度 `len` 并改写堆缓冲区。对普通所有者变量，未声明 `let mut` 时，编译器既禁止给变量重新赋值（`E0384`），也禁止经由该变量取得可变访问去修改内部数据（`E0596`）；写成 `let mut s = String::from("hello");` 才同时放开这两项权限（至于编译器如何仅凭 `push_str` 的方法签名识别出这次调用需要可变借用，将在[方法接收者三件套与自动解引用](/types/methods/)中展开）。

与移动失效一样，**可变与不可变仅记录在编译器的编译期状态表中，运行时内存没有任何附加标记位**。无论写 `let n = 7;` 还是 `let mut n = 7;`，运行时栈帧上存放的都是同样的 4 个整数字节；编译器在编译阶段查表核对权限，检查通过后生成普通的机器指令。

<Aside type="note" title="与 Java final 的边界差异">
Java 的 `final` 引用变量（或 JavaScript 的 `const`）不等同于 Rust 普通所有者的不可变绑定：

<small class="code-source">源文件：<code>examples/memory/variables/java/FinalReference.java</code></small>
<Code code={javaFinal} lang="java" />

这段 Java 程序能正常编译并输出 `hello!`：`final StringBuilder s` 只禁止重新赋值（不能写 `s = new StringBuilder("bye")` 改指其他对象），仍允许调用 `s.append("!")` 修改堆上对象的内容；而 Rust 的 `let s = String::from("hello")` 将重新赋值与修改内部数据一并禁止。
</Aside>

## 重新赋值的三种状态：旧值去了哪里

明确权限规则后，回到赋值语句 `x = new_val;` 本身：当新值写入变量 `x` 时，`x` 原先持有的值如何处理？

对 `i32` 这类实现了 `Copy` 的类型，重新赋值直接覆盖栈上的 4 个字节，不涉及堆内存释放。而对 **`String` 这类承担独占释放责任的移动类型**，编译器会根据赋值前状态表里记录的变量状态（持有有效值、值已移出、尚未初始化），采取不同的处理方式。

### 1. 持有有效值：当场释放旧值

上一章建立的基础规则是「所有者离开作用域（`}`）时释放堆资源」。如果还没走到 `}`，持有有效字符串的变量 `target` 半路执行 `target = source;` 换入新值，原值会在何时释放？

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/replace.rs</code></small>
<Code code={replace} lang="rust" />

运行程序，依次输出 `old new` 与 `new`。

执行 `target = source;` 前，`target` 负责释放 `"old"`，`source` 负责释放 `"new"`。当 `"new"` 的控制头即将写入 `target` 的栈槽位时：

- 若直接覆盖 `target` 的控制头而不处理 `"old"`，栈上将不再保存 `"old"` 的堆地址，造成内存泄漏；
- 若等到 `main` 结尾的 `}` 再处理，届时 `target` 槽位里存放的已经是 `"new"`。

因此，**当给当前持有有效值的移动类型变量重新赋值时，编译器会在 `=` 这一行先当场释放该变量原先持有的旧值，再将右侧新值的控制头移入该变量**。

<ReassignDrop />

按执行顺序追踪两块堆缓冲区的状态与责任：

| 执行时刻 | `"old"` 堆缓冲区 | `"new"` 堆缓冲区 |
| --- | --- | --- |
| `target = source;` **之前** | 由 `target` 持有并负责释放 | 由 `source` 持有并负责释放 |
| `target = source;` **当行** | **在覆盖前当场释放** | 控制头移入 `target`（`source` 失效），改由 `target` 负责 |
| `main` 结尾 `}` **之时** | 已在赋值行释放，不再处理 | 由 `target` 离开作用域时释放 |

这补全了上一章的释放时机：**唯一所有者的释放责任不仅在离开作用域（`}`）时触发，也在有效旧值被重新赋值覆盖的那一行当场触发。**

### 2. 值已移出：直接写入空置槽位

如果移动类型变量 `s` 原本有值，但在重新赋值之前，它的值已经移动给了另一个变量：

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/reinitialize.rs</code></small>
<Code code={reinitialize} lang="rust" />

运行默认源码，输出 `world hello`。对照栈帧与编译期状态表追踪这三步：

1. `let mut s = String::from("hello");`：栈帧留出 24 字节槽位，状态表将 `s` 记为**持有有效值**（负责释放 `"hello"`）；
2. `let t = s;`：控制头按位复制给 `t`，状态表将 `"hello"` 的释放责任转归 `t`，并把 `s` 改记为**值已移出**（此时若取消 `// println!("{s}");` 的注释会报 `E0382`），但 **`s` 在栈帧上的 24 字节槽位仍留在原地**；
3. `s = String::from("world");`：编译器查状态表确认 `s` 处于「值已移出」状态，此处**不生成任何释放旧值的指令**，直接将 `"world"` 的控制头写入 `s` 原有的栈槽位，并在状态表中将 `s` 恢复为**持有有效值**。

<ReinitMove />

堆上的 `"world"` 与 `"hello"` 两块字符缓冲区同时存活，直到 `main` 结尾的 `}` 闭合时，分别由 `s` 和 `t` 各自释放。

### 3. 尚未初始化：延迟初始化

如果把变量声明与首次放入值拆成两行书写（适用于所有类型）：

<small class="code-source">源文件：<code>examples/memory/variables/src/bin/delayed-init.rs</code></small>
<Code code={delayed} lang="rust" />

运行默认源码，正常输出 `7`；若取消 `// println!("{n}");` 的注释，在赋值前读取会触发未初始化错误：

<small class="code-source">编译器输出（取消 delayed-init.rs 中注释行后）</small>
```text
error[E0381]: used binding `n` is possibly-uninitialized
```

注意这里声明写的是 `let n: i32;`，并未加 `mut`，后续的 `n = 7;` 依然合法。原因是 `let n: i32;` 只完成了声明，状态表记为**尚未初始化**；随后的 `n = 7;` 是首次放入值的**初始化（Initialization）**，并非替换已有值的重新赋值，因此既没有旧值需要释放，也不要求声明 `let mut`。

## 三种赋值状态对照与核对

将三种不带 `let` 的 `x = ...` 按编译期状态表汇总对照：

| 赋值前 `x` 的静态状态 | 典型写法 | 执行 `x = 新值;` 时的动作 | 是否需要 `let mut` |
| --- | --- | --- | --- |
| **持有有效值**（已初始化且未移出） | `let mut target = ...;`<br/>`target = source;` | 对移动类型，**先在 `=` 当行释放旧值**，再接手新值 | **需要** |
| **值已移出**（曾初始化，已移动给其他变量） | `let mut s = ...;`<br/>`let t = s;`<br/>`s = new_s;` | 旧值已归 `t` 负责，**此处不释放**；写入新值并恢复 `s` 有效状态 | **需要** |
| **尚未初始化**（仅声明，尚未放入值） | `let n: i32;`<br/>`n = 7;` | 首次**初始化**，无旧值释放；写入初值后变为有效（此前读取报 `E0381`） | **不需要** |

### 动手核对

在 `replace.rs` 中，将 `target = source;` 改为 `target = String::from("third");`，其余代码保持不变。运行前先推演两个问题：

1. 改写后，`source` 能否在最后一行正常打印？
2. 程序创建的 `"old"`、`"new"`、`"third"` 三块堆缓冲区，分别在哪一行释放？

核对结果：`source` 未发生移动，保持有效并可正常打印。三块堆缓冲区中，`"old"` 在 `target = String::from("third");` 那一行被当场替换释放；`"new"` 与 `"third"` 分别由 `source` 和 `target` 持有，在 `main` 结尾的 `}` 处释放。

本节讨论的 `x = ...` 均不带 `let`，始终在同一个变量槽位上操作。在 Rust 代码中还会频繁见到另一种写法：对同一个名字再写一次 `let`（如先写 `let s = String::from("hello");`，随后写 `let s = 7;`）。被同名新变量盖住的旧字符串，是否也会在那一刻当场释放？下一节拆解同名遮蔽与作用域。
