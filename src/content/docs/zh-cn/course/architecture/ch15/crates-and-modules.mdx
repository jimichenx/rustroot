很多从 Java、Go 或 Python 转向 Rust 的开发者，在刚接触 Rust 的项目组织时都会经历一次明显的认知错位：
- 在 Java 里，我们习惯把 `crate` 当成 `.jar` 包，把 `mod` 当成与磁盘文件夹一一对应的 `package`；
- 在目录里新建了一个 `helper.rs` 文件，满心以为旁边的代码直接就能用，结果编译器却像完全瞎了一样，对新建的文件视而不见。

之所以会觉得别扭，是因为许多教程一上来就教你怎么建文件夹、怎么区分 `foo.rs` 和 `foo/mod.rs`，让你误以为 `mod` 是一套文件系统规则。

要真正看清 Rust 的代码组织方式，最好的办法是**先把磁盘上的文件和文件夹彻底忘掉**。我们直接在一个单独的 `.rs` 文件里，从概念上看看 **`mod`** 和 **`crate`** 到底是什么。

## 先忘掉文件夹：`mod` 是一棵装代码的容器树

在概念上，**模块（`mod`，Module）就是一个实实在在用来装代码的容器**。你可以在这个容器里放函数、`struct`、`enum`、`Trait`、常量，也可以在容器里面再套小容器（子模块）。

我们不需要创建任何新文件，直接在同一个源码文件里就能用花括号 `{}` 搭出一棵三层模块树：

```rust
// 当前整个源码文件自身，就是这棵模块树的「根容器（Root Module）」，名字固定叫 crate
mod network {
    // 子容器 http：标了 pub，允许父容器及外部看见它
    pub mod http {
        pub fn get_status() -> u16 { 200 }
    }

    // 子容器 tcp：未标 pub，仅在父容器 network 内部可见
    mod tcp {
        pub fn connect() {}
    }
}
```

看着这段写在同一个文件里的代码，请你建立起关于模块树的三个核心直觉：

1. **整棵树只有一个总根，它的名字就叫 `crate`**：
   你交给编译器编译的那个入口文件本身，就是最外层的根模块（Root Module）。在代码里写的 `crate::network::http`，意思就是「从当前这棵树的根部 `crate` 出发，一层层往下找 `network` 里的 `http`」。
2. **父子与兄弟关系，直接决定了谁能看见谁（可见性规则）**：
   在这棵树里，`network` 是父模块，`http` 和 `tcp` 是它的两个子模块（互为兄弟）。Rust 的可见性规则完全顺着这棵父子树的物理包含关系来定：
   - **儿子看老子：无条件全透明**。子模块（如 `tcp`）本来就装在父模块（`network`）的肚子里，属于父模块的内部实现细节。因此，**子模块天然有权直接访问父模块（以及爷爷模块、根模块）里的一切私有函数和私有字段**，根本不需要父模块标 `pub`；
   - **老子看儿子（以及兄弟互看）：默认全封闭**。反过来，子模块 `tcp` 的肚子对父模块 `network` 和兄弟模块 `http` 默认是锁上的。父模块要想调用子模块里的函数，子模块及该函数必须显式标上 **`pub`**。

子模块看得见父模块里的私有项。父模块看子模块、兄弟互相看，默认看不见，要标 `pub`。

## 从单文件到多文件：`;` 只是把 `{ ... }` 抽出去存放

既然在单个文件里用 `mod network { ... }` 就能搭出整棵模块树，那磁盘上的多个 `.rs` 文件和文件夹又是怎么回事？

答案非常直白：当 `mod network { ... }` 花括号里的代码写了几百行、放在一个文件里太挤时，你可以**把花括号 `{ ... }` 换成一个分号 `;`**，写成一行声明：

```rust
// 把花括号换成 `;`，告诉编译器：
// 「这个容器还在树上的原位置，请去旁边找同名文件把里面的代码填进这里」
mod network;
```

编译器看到 `mod network;` 时，会自动去当前目录下寻找对应的源码文件，把文件内容原封不动地挂载到模块树的 `network` 节点上。支持的文件存放形式只有两种（效果 100% 等价）：

1. **现代推荐形式（Rust 2018+）**：
   - `src/network.rs`（存放 `network` 容器自身的代码；如果它内部还有一行 `pub mod http;`，再去建子目录文件 `src/network/http.rs`）；
2. **传统目录形式**：
   - `src/network/mod.rs`（当 `network` 下有很多子模块时，把 `network` 自身的代码写在文件夹内的 `mod.rs` 里，子模块写在同目录的 `src/network/http.rs` 里）。

你看，无论你是把所有代码写在一个文件里的 `mod network { pub mod http {} }`，还是拆成 `network.rs` 和 `network/http.rs` 两个文件，**在编译器脑子里拼出来的，自始至终都是同一棵一模一样的内存模块树**。

这也彻底解释了为什么你在磁盘上新建一个 `helper.rs` 时编译器会对它视而不见：
- 在 Java 里，文件夹就是 `package`，你只要往文件夹里扔一个 `.java` 文件，它就自动挤进了包里；
- 而在 Rust 里，**模块树是由父模块通过 `mod xxx;` 从上往下显式装配出来的**。只要树根或某个父模块没有写下 `mod helper;` 把它挂上树，磁盘上的 `helper.rs` 就只是一份无人认领的孤立文本，绝不会参与编译。

## 最小编译单元 `crate` 与 Cargo 的目录约定

理解了「整棵模块树的根就叫 `crate`」，我们就能彻底纠正「把 Rust 的 `crate` 等同于 Java 的 `.jar` 包」的误区了。

### 1. `crate` 是编译器的最小编译单元

在 Java 或 C++ 中，编译器的最小编译单元是**单个源文件**（`javac Foo.java` 单独编译出 `Foo.class`）。
而在 Rust 中，编译器 `rustc` 的最小编译单元是**一整棵 `crate` 模块树**。

当你编译一个 `crate` 时，你只向编译器提供一个**树根文件（Crate Root）**。编译器从这个树根出发，顺着里面的 `mod xxx;` 把所有挂载的子模块文件全部读入内存，拼成一棵完整的语法树，然后**以整个 `crate` 为单位**，一次性完成我们在前五篇学过的全部编译期检查（包括第 7 章讲过的「孤儿规则」——为什么孤儿规则要求 Trait 或类型必须属于当前 `crate`，就是因为编译器一次只编译并核对一棵 `crate` 树）。

按编译产物的形态，`crate` 只有两种：
- **二进制可执行 Crate（Binary Crate）**：有 `fn main()` 入口，编译后生成可直接运行的二进制程序；
- **库 Crate（Library Crate）**：没有 `main` 函数，编译后产出供其他 Crate 调用的公开类型与函数。

### 2. `main.rs`、`lib.rs` 与 `Package` 是 Cargo 的工程约定

对于底层的 `rustc` 编译器来说，树根文件叫什么名字都行（比如 `rustc foo.rs`）。但为了全生态项目结构统一，构建工具 **Cargo** 定下了两条零配置的目录约定：

- 只要 Cargo 看到 **`src/lib.rs`**，就自动把它当作同名**库 Crate（Library Crate）**的树根；
- 只要 Cargo 看到 **`src/main.rs`**，就自动把它当作同名**二进制可执行 Crate（Binary Crate）**的树根（如果还有 `src/bin/*.rs`，每个文件各自成为一个独立的二进制 Crate 树根）。

而最外层那个包含 `Cargo.toml` 配置文件的工程目录，在术语上叫做 **Package（包）**。一个常见的工业级 Package 里，往往同时包含一个 `src/lib.rs`（存放全部核心业务逻辑的库 Crate）和一个很薄的 `src/main.rs`（只负责解析命令行参数并调用库 Crate 的二进制入口；关于多包 Workspace 组织、Features 条件编译与 `Cargo.lock` 准则，可按需查阅[附录：Cargo 工程化与条件编译](/appendix/engineering/cargo-and-features/)）。

## 点号 `.` 与双冒号 `::` 的严格分工

在穿越模块树调用函数或访问数据时，Rust 做了一个与 Java、Python 截然不同的语法设计：**把路径分隔符 `::` 和成员访问符 `.` 彻底分开了**。

在 Java 或 Python 里，万事万物都用点号 `.` 连接：当你看到 `a.b.c()` 时，如果不去翻定义，你根本分不清 `a` 和 `b` 到底是包名、类名、静态字段，还是某个运行时存活的对象实例。

而在 Rust 中，这两个符号的职责没有一丝一毫的重叠，你只看一眼代码符号就能判断底层发生了什么：

1. **双冒号 `::`（编译期命名空间路径寻址）**：
   左边永远是**模块名、类型名（`struct` / `enum`）或 Trait 名**。它不涉及任何运行时内存读写，纯粹是在编译期顺着容器树寻找某个条目——例如模块路径 `std::collections::HashMap`、枚举变体 `Poll::Ready`、或者类型名下的关联函数 `String::from("hi")` 与 `Vec::new()`。
2. **点号 `.`（运行时值实例的字段访问与方法调用）**：
   左边永远是一个**实实在在存活在栈或堆上的值实例（变量或表达式）**。比如 `user.name` 是按偏移量读取结构体字段，`order.amount_cents()` 是将 `order` 作为 `self`（或通过第 10 章的 `Deref` 自动解引用）传入方法。

虽然敲键盘时输入两个冒号 `::` 比敲一个点号繁琐一点，但它换来的是极高的代码可读性：看到 `PaymentOrder::try_new(1001, 500).unwrap()`，你一秒钟就能切分出前半段 `PaymentOrder::try_new(...)` 是在调用类型命名空间下的静态构造函数，而后半段 `.unwrap()` 是在它返回的 `Result` 实例上调用方法。

## 为什么封装边界画在 `mod` 上，以及为什么开源项目目录这么扁平？

如果你去阅读 `tokio`、`serde` 等主流 Rust 开源库的源码，会发现一个非常舒适的现象：相比于 Java 开源项目动辄七八层深的文件夹嵌套和满屏零碎的小文件，Rust 项目的目录层级通常非常平坦、紧凑。

这背后源自 Rust 模块系统的两项核心工程机制：**以 `mod` 为单位的私有边界**，以及 **`pub use` 门面重导出（Re-export）**。

### 1. 封装边界画在 `mod` 上，而不是 `struct` 上

在 Java 中，封装的基本单位是 `class`，而且语法强制规定每个 `public class` 必须独占一个 `.java` 文件。

而在 Rust 中，**封装（Privacy）的物理边界是模块 `mod`，而不是 `struct`**：
- **同一个 `mod` 内部是一家人**：在同一个模块（同一个 `.rs` 文件）内部，哪怕结构体 `PaymentOrder` 的字段 `amount_cents` 是私有的（没有标 `pub`），同一个文件里的其他辅助结构体、自由函数和子模块依然可以直接读写 `order.amount_cents`。因此，在 Rust 里你完全可以把三四个紧密协作的结构体、枚举和辅助函数大方地写在同一个模块文件里，根本不需要像 Java 那样机械地拆成十几个碎文件；
- **跨出 `mod` 边界立即触发字段锁死**：一旦跨出 `billing` 模块，哪怕 `pub struct PaymentOrder` 这个结构体本身是公开的，只要它内部有一个字段 `amount_cents` 没有标 `pub`，模块外的任何代码就**既不能直接读取该字段，也绝对不能用 `PaymentOrder { order_id: 1, amount_cents: 0 }` 字面量语法绕过构造函数直接拼装实例（编译器会当场报 `E0451` 错误）**。

这条规则至关重要——我们将在 `15.3` 节看到，正是因为模块外无法直接用字面量拼装含有私有字段的结构体，我们才能把业务校验牢牢锁死在 `PaymentOrder::try_new` 这唯一一个公开入口上。

### 2. 四级可见性刻度与 `pub use` 扁平门面重导出

当项目规模变大，我们在内部拆分出多个子模块（如 `mod billing;`、`mod audit;`）后，难道外部用户在调用时也得跟着写出冗长的内部模块路径 `my_crate::billing::audit::is_high_value` 吗？

完全不需要。Rust 为模块设计了精细的可见性刻度与**重导出（`pub use`）**机制：

| 可见性写法 | 允许访问的范围 | 典型工程用途 |
| --- | --- | --- |
| 默认（不写 `pub`） | 仅限**当前模块 `mod` 及其后代子模块**内部 | 隐藏结构体敏感字段与模块内部辅助函数 |
| **`pub(super)`** | 向**上一级父模块**公开 | 子模块向直接父模块暴露内部协作接口 |
| **`pub(crate)`** | 在**当前整棵 `crate` 树内部**公开，但对外部依赖方隐藏 | 跨内部模块的公共工具函数，绝不污染对外公开 API |
| **`pub`** | 完全公开（若从根模块一路可达，则外部其他 crate 也可访问） | 正式对外承诺的公开 API |

在此基础上，库作者可以在顶层树根（`lib.rs` 或 `main.rs`）中使用 **`pub use`**，把深层子模块里的核心类型直接「提拔」挂到顶层门面上：

```rust
mod billing; // 注意：内部模块 billing 甚至不需要对外标 pub！

// 用 pub use 将深层类型重导出到顶层门面：
pub use billing::PaymentOrder;
pub use billing::audit::is_high_value;
```

这样做实现了**「内部组织结构」与「外部调用体验」的彻底解耦**：
- **对内（维护者视角）**：你可以按职责把代码清晰地拆进 `billing`、`audit` 等内部子模块，并用 `pub(crate)` 让它们在内部互相配合；
- **对外（使用者视角）**：外部用户根本不需要关心你内部建了几个文件夹，直接写一行扁平清爽的 `use my_crate::{PaymentOrder, is_high_value};` 就能拿到所有核心功能。

## 小结

顺着本节的梳理，关于 Rust 工程组织最核心的骨架已经立稳了：

1. **`mod` 是显式挂载的容器树，不是松散的文件夹标签**：整棵树以 `crate`（`main.rs` 或 `lib.rs`）为唯一树根；子模块看父模块无条件全透明，父模块看子模块及兄弟互看必须标 `pub`；`mod foo;` 只是把 `{ ... }` 里的代码抽到单独文件中存放；
2. **`crate` 是编译器的最小编译单元**：编译器以整棵 `crate` 模块树为单位执行类型检查与孤儿规则核对；
3. **`::` 与 `.` 泾渭分明**：双冒号 `::` 专管编译期命名空间与类型路径寻址，点号 `.` 专管运行时值实例的字段读写与方法调用；
4. **以 `mod` 划定封装边界，以 `pub use` 塑造扁平门面**：利用模块私有字段封死外部直接用字面量拼装非法结构体的后门，对内用 `pub(crate)` 共享实现，对外用 `pub use` 导出扁平干净的顶层 API。

现在，请仔细回味一下我们在开头总结的那条父子可见性铁律：**「子模块属于父模块的内部实现，天然有权直接访问父模块里的一切私有函数和私有字段。」**

如果我们在一个业务模块文件的最底部，顺手写一个叫 **`mod tests { ... }`** 的子模块呢？
