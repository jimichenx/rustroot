在前五篇的代码实验里，我们的代码大多写在一个单独的 `.rs` 文件中。但当你开始搭建一个真实的工业级 Rust 工程时，在动手写任何精巧的领域模型之前，首先要把整座工程的**物理骨架**立起来：

- 几万行代码怎么拆进不同的模块文件，谁对谁可见，怎么把内部敏感字段锁起来不让外人乱改？
- 当单个包越来越大（或者后续需要拆出独立的过程宏包、公共基础库与多个微服务二进制入口）时，怎么在同一个仓库里组织多个包而不发生重复编译和依赖版本漂移？
- 写好的私有内部算法和对外公开 API 门面，怎么用工具链自动化守住质量且零生产二进制残留？

本章分三节，顺着从内到外的物理层级搭好这套工程组织与验证底座：

1. **编译单元 `crate` 与模块封装边界**：打破从 Java / Python 带过来的目录包惯性，先从单文件内的 `mod` 容器树理解父子可见性、多文件拆分、`::` 与 `.` 的符号分工，看清为什么 Rust 把封装边界画在 `mod` 而不是 `struct` 上，并掌握 `pub(crate)` 与 `pub use` 扁平门面重导出。
2. **多包工作空间（Workspace）、`Features` 条件编译与依赖治理**：将视野从单个 `crate` 推向多包协作，拆解 Cargo `[workspace]` 共享唯一 `target/` 缓存与统一版本池、`Cargo.lock` 锁定准则、为什么因特性并集（Feature Unification）严禁把 `features` 设计成互斥开关，以及日常检查与 Release 编译调优。
3. **三维测试体系（单元测试、集成测试与文档测试）**：顺着前两节立好的 `mod` 与 `crate` 边界，理解为什么同文件底部的子模块 `mod tests` 能白盒测试私有实现、为什么 `tests/` 目录下的每个文件都是独立的外部黑盒 crate，以及 `///` 文档测试如何根除注释示例过期腐烂的顽疾。

## 读完本章，检验自己的三个问题

- 为什么说 `crate` 是编译器的最小编译单元，而且它本身就是整棵 `mod` 树的树根？为什么子模块可以无条件访问父模块的私有项，而父模块访问子模块却必须标 `pub`？
- 为什么中型 Rust 仓库普遍采用 Cargo `[workspace]` 多包架构？在设计 `[features]` 条件编译开关时，为什么必须遵守「纯增量加法原则」而绝不能设计互斥开关？
- 为什么 Rust 惯例把单元测试写在业务源码同一个文件的底部（`#[cfg(test)] mod tests`），而把集成测试放在项目根目录的 `tests/` 文件夹下？
