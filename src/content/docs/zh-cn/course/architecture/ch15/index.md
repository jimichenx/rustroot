在前五篇的代码实验里，我们的代码大多写在一个单独的 `.rs` 文件中。但在真实的工业级工程里，你会面对成百上千个类型与函数，以及多人协作（或人类与 AI 协作）下的架构维护难题：

- 如果任何一个外部调用方都能直接用 `{ id: 1, amount: 0 }` 拼装出一个金额为 `0` 的非法订单结构体，你在业务函数里写再多 `if amount == 0` 的防御性检查也总会有漏网之鱼；
- 如果一个网络连接在还没有完成身份认证（`login`）之前，编译器就允许调用方直接对它调用 `.send_query()`，那这个状态顺序错误就只能等到线上运行时报错才能暴露。

**怎样在编译期就不给非法数据和非法状态留出任何拼装与调用的入口？**

答案需要两块基石的配合：第一块是**模块的物理封装边界（`mod` 与私有字段）**，用来收走外部随意构造和篡改内部状态的后门；第二块是建立在封装边界之上的**类型驱动设计模式（Type-Driven Design）**，用不同的编译期类型实体来锁定业务不变量与状态流转。

本章分七节由浅入深地搭建起这套工业级工程架构体系：

1. **编译单元 `crate` 与模块封装边界**：打破从 Java / Python 带过来的目录包惯性，先从单文件内的 `mod` 容器树理解父子可见性、多文件拆分、`::` 与 `.` 的符号分工，看清为什么 Rust 把封装边界画在 `mod` 而不是 `struct` 上，并掌握 `pub(crate)` 与 `pub use` 扁平门面导出。
2. **测试体系（单元测试、集成测试与文档测试）**：顺着上一节的 `mod` 与 `crate` 边界，理解为什么同文件底部的子模块 `mod tests` 能直接测试私有实现、为什么 `tests/` 目录下的每个文件都是独立的外部黑盒 crate，以及 `///` 文档测试如何根除注释示例过时腐烂的顽疾。
3. **`Newtype` 模式与「解析而非校验（Parse, don't validate）」**：对比 `type` 类型别名与零内存开销的 `Newtype`（`struct UserId(u64);`），配合模块私有字段把数据合法性校验锁死在唯一的构造入口处。
4. **灵活 API 签名设计与 `Builder` 模式**：从双向类型推断推导为什么 Rust 拒绝同名函数重载与默认参数，掌握具名关联构造、转换契约泛型、`..Default::default()` 与链式 `Builder` 的分层选型。
5. **`Typestate` 模式（编译期类型状态机）**：利用零大小状态类型参数（`PhantomData`）与按值消费 `self` 将合法的业务调用顺序编码进编译期签名，并厘清编译期 `Typestate` 与运行时 `enum` 状态机的选型边界。
6. **写时复制智能指针 `Cow<'a, B>`**：填平第 10 章智能指针全景表的最后一块拼图，拆解 `Borrowed` / `Owned` 双变体枚举与 `Deref` 机制，在读多写少场景中消灭防御性 `.to_string()` 克隆。
7. **经典设计模式的 Rust 重塑与 AI 时代的「签名即铁轨」**：对照传统 GoF 设计模式在 Rust 中的降维替代方案，总结全指南的核心工程方法论——人类架构师如何用类型签名铺设不可出轨的铁轨，让编译器充当 AI 代码的形式化验收官。

## 读完本章，检验自己的五个问题

- 为什么说 `crate` 是编译器的最小编译单元，而且它本身就是整棵 `mod` 树的树根？为什么在 Rust 里子模块可以无条件访问父模块的私有项，而父模块访问子模块却必须标 `pub`？
- Rust 中路径分隔符 `::` 和点号 `.` 各自负责什么场景？为什么 Rust 开源项目的目录结构通常比 Java 项目平坦得多（`pub use` 重导出在其中起了什么作用）？
- 为什么 Rust 惯例把单元测试写在业务源码同一个文件的底部（`#[cfg(test)] mod tests`），而把集成测试放在项目根目录的 `tests/` 文件夹下？
- `type UserId = u64;` 和 `struct UserId(u64);` 在运行时内存大小和编译期类型检查上有什么区别？什么是「解析而非校验（Parse, don't validate）」？
- 当你要防止调用方在「未认证的连接」上调用发送数据方法时，编译期的 `Typestate` 模式和运行时的 `enum` 状态机各自适用于什么边界？
