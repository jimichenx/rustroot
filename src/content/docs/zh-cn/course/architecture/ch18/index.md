在前十七章里，我们一直待在 **Safe Rust（安全 Rust）** 的保护伞下：只要你的代码能通过 `rustc` 编译，编译器就向你承诺——程序里绝不会出现悬垂指针、双重释放或跨线程数据竞争。

走到全指南的最后一章，每位爱刨根问底的开发者心里都会浮现出两个终极疑问：
1. **既然借用检查器连同时存在两个可变引用都严令禁止，那标准库自己到底是用什么办法写出 `Vec<T>`、`Rc<T>`、`Arc<T>` 以及把同一个可变切片一分为二的 `split_at_mut` 的？**
2. **当我们的 Rust 程序需要直接读写硬件寄存器、调用 Linux / Windows 操作系统内核接口，或者与外部的 C / Python 代码互相调用时，编译器管不到的外部世界该怎么对接？**

要回答这两个问题，我们就必须掀开安全 Rust 脚下的最后一层物理基础——走近 **`unsafe` Rust、安全抽象契约与外部函数接口（FFI）**。

本章分四节，完成整部指南的压轴收官：

1. **为什么需要 `unsafe`（证明边界、裸指针与五项特权）**：从「测试用例穷举 vs 编译期逻辑证明」的视角出发，理解为什么任何自动逻辑推理机都必然需要人工提交安全公理的入口（`unsafe`）；破除「`unsafe` 会关掉借用检查器」的误解，零基础掌握裸指针 `*const T` / `*mut T` 与 `unsafe` 解锁的五项特权。
2. **安全抽象与红线（如何把 `unsafe` 关进笼子里？）**：亲手复刻标准库的 `split_at_mut`，看懂标准库如何用安全前置检查 + 极小范围 `unsafe` 对外提供 100% 安全的函数签名，理解为什么安全抽象的真实审查边界是整个 `mod` 模块，并划清触碰不得的未定义行为（UB）高压线与 `Miri` 检测工具。
3. **跨越语言边界（从零看懂 FFI 与 C ABI）**：揭开跨语言二进制调用约定（C ABI）的面纱，掌握 Rust 调用外部 C 函数与将 Rust 导出给 Python / Node.js / C 调用的双向规范，以及用 `#[repr(C)]` 对齐跨语言结构体内存布局。
4. **全指南总收束（从物理内存到编译期类型实体）**：回望从第 1 章「栈与堆的释放责任」到第 18 章「安全抽象公理基础」的完整认知链条，首尾呼应困难三角，为你合上本指南后的工业级实战送出最后一份心法地图。

## 读完本章，检验自己的四个问题

- 为什么说 Safe Rust 代码本身是一份逻辑证明，而 `unsafe {}` 不是「关掉借用检查器」，而是程序员向推理机提交的一份「人工安全公理证明」？为什么创建裸指针是安全的，而解引用裸指针必须是 `unsafe`？
- 标准库在实现 `split_at_mut` 或 `Vec<T>` 时，是如何做到「内部使用了 `unsafe` 裸指针，对外暴露的函数签名却不带 `unsafe` 且 100% 安全」的？为什么说审查 `unsafe` 时必须审查它所在的整个 `mod` 模块？
- 什么是二进制调用约定（C ABI）？为什么跨语言传递结构体时必须在头顶加上 `#[repr(C)]`？
- 回顾整部指南，Rust 是如何用「编译期类型实体」这一核心武器，把释放责任、空值与错误、多态行为、生命周期、多线程并发、异步状态机与业务不变量全部统一起来的？
