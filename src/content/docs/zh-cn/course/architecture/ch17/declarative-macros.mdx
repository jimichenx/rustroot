在上一节看清宏的编译期展开位置后，很多人的第一反应是发怵：一翻开标准库源码看到满屏的 `$`、`=>`、`*` 和 `+`，总觉得 `macro_rules!` 像一套晦涩的天书密码。

其实你早就学过它的核心逻辑了。
如果把第 6 章的 **`match` 表达式**搬到编译期，把匹配对象从「运行时的枚举值」换成「源码里的语法片段」，它就是 **`macro_rules!`**。

## 把 `macro_rules!` 还原成编译期的 `match`

我们先并排对比一下你早已熟悉的运行时 `match`，以及编译期的 `macro_rules!`：

```rust
// 运行时 match：匹配「数据值」形状 => 执行对应计算表达式
match input_val {
    0 => 100,
    x => x + 1,
}
```

```rust
// 编译期 macro_rules!：匹配「代码片段」形状 => 展开为目标 Rust 代码
macro_rules! compute {
    () => { 100 };
    ($x:expr) => { $x + 1 };
}
```

对照这两段结构，声明宏的骨架一目了然：
- 每个分支（Arm）同样由 **`匹配模式 => { 展开模板 };`** 组成（注意分支末尾用分号 `;` 分隔），编译器从上往下依次尝试匹配；
- 当你在代码里写下 `compute!()` 时，命中第 1 个分支，编译器原地把它替换成 `100`；写下 `compute!(40 + 1)` 时，命中第 2 个分支，替换成 `40 + 1 + 1`。

### 认识 `$名字:分类符`：告诉编译器你要抓什么语法零件

在上面的第 2 个分支里，为什么不能像普通变量那样光写 `x`，而要写成带美元符号和冒号的 **`$x:expr`**？

因为在编译早期，塞进宏括号里的可以是千奇百怪的源码词条——可能是一个算式 `1 + 2`，可能是一个类型名 `Vec<u8>`，也可能是一个新建结构体的标识符 `UserId`。定义宏时，你必须用 **`$捕获名:片段分类符（Fragment Specifier）`** 明确告诉编译器应该按哪种语法规则去切分输入：

在日常开发中，95% 的声明宏只会用到以下 **3 种最核心的分类符**：
1. **`expr`（表达式 Expression）**：匹配任何会算出一个值的代码片段，如 `42`、`a + b`、`user.name()`；
2. **`ident`（标识符 Identifier）**：匹配一个变量名、函数名或类型名字本身，如 `x`、`UserId`、`OrderId`；
3. **`ty`（类型 Type）**：匹配任何合法的 Rust 类型写法，如 `u64`、`&str`、`Result<T, Error>`。

*(补充：标准库还提供了匹配模式的 `pat`、匹配顶层定义项的 `item`、匹配代码块 `{ ... }` 的 `block` 以及匹配单个任意语法词条的 `tt`，用到时查阅文档即可，无需死记硬背。)*

## 实战一：突破固定参数个数，亲手写出 `my_vec!`

搞懂了单分支匹配，我们立刻解决上一节提出的第一个函数死穴：**普通函数签名写不出可变参数个数的 `vec![10, 20, 30]`，用 `macro_rules!` 怎么一步步搭出来？**

### 第一步：处理空参数 `my_vec![]`

*（顺带一提：在 Rust 中调用同一个宏时，写圆括号 `my_vec!()`、方括号 `my_vec![]` 或花括号 `my_vec!{}` 对编译器来说完全等价，只是社区习惯给 `vec!` 配方括号。）*

最基础的情况是一个元素都不传，直接展开为 `Vec::new()`：

```rust
macro_rules! my_vec {
    () => { Vec::new() };
}
```

### 第二步：用重复匹配 `$(...),+` 接收任意个元素

如果调用方传入了 1 个、3 个甚至 50 个由逗号隔开的表达式（如 `my_vec![10, 20, 30]`），怎么在一个分支里全部接住？
`macro_rules!` 提供了一对类似正则表达式的重复包络符号 **`$( ... )`**：

```rust
// 在匹配侧（=> 左边）：匹配 1 个或多个以逗号分隔的表达式
($($elem:expr),+) => {{
    let mut temp_vec = Vec::new();
    // 在展开侧（=> 右边）：捕获到了几个 $elem，就把花括号里的这行代码重复展开几次
    $( temp_vec.push($elem); )+
    temp_vec
}};
```

请看清这短短 6 行里的三处关键细节：
1. **匹配侧的 `$( $elem:expr ),+`**：中间的 `,` 表示输入元素之间用逗号分隔；末尾的 `+` 表示「至少出现 1 次」（如果允许出现 0 次或多次则写 `*`，允许出现 0 次或 1 次则写 `?`）。为了让多行列表末尾多打一个逗号（如 `my_vec![10, 20,]`）也能通过编译，通常还会在末尾顺手加上 **`$(,)?`**（匹配一个可选的尾随逗号）；
2. **展开侧的同步重复 `$( temp_vec.push($elem); )+`**：编译器在左边抓到了 3 个表达式（`10`、`20`、`30`），在右边就会自动把这行 `push` 连续复制展开 3 遍；
3. **为什么要写双层花括号 `{{ ... }}`？**
   最外层的那对 `{ ... }` 只是 `macro_rules!` 语法本身的边框，展开时会被剥掉。如果我们只写单层花括号，展开后就会变成散落在外面的多条语句，没法赋值给 `let nums = my_vec![10, 20];`。多套一层内层花括号 `{ let mut temp_vec = ...; temp_vec }`，展开出来就是一个合法的**代码块表达式**，执行完所有 `push` 后把填好的 `temp_vec` 作为整个块的值交出去。

## 调试利器：怎么亲眼看见宏展开后的代码？

由于宏在幕后生成的代码并不直接显示在你的 `.rs` 源文件里，一旦宏写错了或者展开后的代码触发了借用检查报错，凭空脑补往往很吃力。

在工程开发中，有两个现成的工具可以让你随时把宏的「底牌」翻开来看：

1. **编辑器一键展开（最快）**：在安装了 `rust-analyzer` 插件的 VS Code 或 Cursor 中，把光标停在任何宏调用（如 `println!`、`my_vec!` 或 `define_id_newtypes!`）上，打开命令面板执行 **`rust-analyzer: Expand macro recursively at caret`**，侧边栏就会当场弹出它展开后的完整 Rust 源码；
2. **命令行全景展开（`cargo expand`）**：安装社区标准工具 `cargo install cargo-expand` 后，在项目目录下运行 `cargo expand --bin declarative-macros`，它会把整个文件里所有的声明宏和 `#[derive]` 全部展开并格式化打印出来。

## `macro_rules!` 的能力边界在哪里？

看到这里，`macro_rules!` 似乎已经能应付不少场合了。为什么 Rust 还要大费周章地设计第二套宏体系——**过程宏（Procedural Macros）**？

答案藏在一个致命的语法限制里：**`macro_rules!` 只是一套死板的「填空替换模板」，它没法主动去拆解和检查一段现成的结构体或函数内部长什么样。**

设想你想实现像 `#[derive(Debug)]` 或 `#[derive(Serialize)]` 那样的功能：
调用方只想干干净净地写一个普通的 Rust 结构体：

```rust
struct Order {
    id: u64,
    buyer: String,
    paid: bool,
}
```

你希望挂一个标签上去，就能自动遍历 `Order` 里的所有字段名（`id`、`buyer`、`paid`）生成序列化代码，而且如果某个字段上面标了 `#[serde(rename = "order_id")]` 就自动改名。
面对这种需求，纯靠模式匹配填空的 `macro_rules!` 就彻底力不从心了——它既不能作为 `#[derive(...)]` 挂在普通结构体头顶，也没法在编译期写 `for` 循环和 `if-else` 去精细解析复杂的泛型约束与字段属性。

要想在编译期像操作普通数据结构一样自由读取、分析并改写任意 Rust 语法树，我们就必须进入下一节——揭开**过程宏**的真面目。
