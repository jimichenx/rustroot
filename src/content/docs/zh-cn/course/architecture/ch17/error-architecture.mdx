在[错误即数据：`Result<T, E>` 与 `?` 短路传播](/types/result-and-try/)与[转换契约与一揽子实现](/abstraction/conversions-and-from/)中，我们已经打通了 Rust 错误处理的语言机制：用和类型 `Result<T, E>` 把失败写进签名，用 `impl From<SubError> for TopError` 配合 `?` 运算符向上归并错误。

但当你真正动手编写一个包含数据库、缓存、外部网关与参数校验的中大型工程时，如果全靠纯手写标准库代码，很快就会遇到两处明显的工程摩擦：

1. **样板代码膨胀**：每定义一个包含五六个变体的业务错误 `enum`，为了符合生态规范，你都要手写几十行重复的 `fmt::Display` 格式化分支、`std::error::Error` 实现以及各个底层错误的 `From` 转换；
2. **顶层组装冗余**：在 HTTP 路由入口或 CLI 的 `main` 函数里，调用方其实根本不打算按具体错误变体写 `match` 分支恢复——无论是配置文件缺了、SQL 超时了还是 JSON 格式错了，顶层做的事情都一样：**附加上当前正在处理哪个用户、哪笔订单的业务上下文，记录一条完整错误链并返回失败响应**。为了这种不需要分支匹配的顶层函数专门去维护一个大杂烩枚举，投入产出比极低。

正是为了解决这两类截然不同的工程诉求，Rust 社区形成了以标准库 **`std::error::Error`** 为共同协议底座、以 **`thiserror`** 与 **`anyhow`** 为左右手的工业级错误处理标准架构。

## 一、 先看清底座：标准库的 `std::error::Error` 与 `Box<dyn Error>`

在引入第三方库之前，先看标准库（位于 `core::error::Error`）为全生态所有错误类型定下的公共契约长什么样：

<small class="code-source">标准库源码结构示意（<code>core::error::Error</code>）</small>
```rust
pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        None
    }
}
```

这个契约非常精炼，只规定了两件事：
1. **双视角可读（`: Debug + Display`）**：任何合规的错误类型，必须同时支持面向开发者的调试输出 `{:?}`（`Debug`）和面向终端或日志摘要的自然语言描述 `{}`（`Display`）；
2. **保留底层起因链（`fn source`）**：当高层错误包裹了一个底层错误（比如「订单扣款失败」是由底层的「TCP 连接超时」引起的）时，通过覆写 `.source()` 返回内层错误的动态引用 `&dyn Error`，顶层排障工具就能顺着链表把整串起因一层层打印出来。

### 用第 8 章的 `Box<dyn Error>` 擦除具体错误类型

既然标准库里的 `io::Error`、`ParseIntError` 乃至所有第三方库的错误都实现了 `Error` Trait，如果我们不关心具体是哪种错误，能不能直接用[动态分发胖指针](/abstraction/dyn-trait-and-vtable/)把它们装进同一个盒子里？

完全可以。标准库内置了一条从任意具体错误 `E: Error` 转换到 **`Box<dyn Error>`**（多线程与异步下写作 `Box<dyn Error + Send + Sync>`）的 `From` 实现。因此在小型脚本中，你可以直接把 `main` 或顶层函数的签名写成：

```rust
fn run_script() -> Result<(), Box<dyn std::error::Error>> {
    let raw = std::fs::read_to_string("port.txt")?; // io::Error 自动装箱擦除
    let _port: u16 = raw.trim().parse()?;           // ParseIntError 自动装箱擦除
    Ok(())
}
```

这行签名揭示了动态错误处理的物理模型：把大小各异的具体错误结构体搬到堆上，栈上统一返回 16 字节的虚表胖指针。但裸用 `Box<dyn Error>` 在大型生产服务里仍有三处短板：它默认不带 `Send + Sync`（进不了 `tokio::spawn`）、不支持在 `?` 传播途中顺手挂载「读取哪个文件失败」的业务上下文字符串，也不便于携带调用栈快照（Backtrace）。

看清了这个底座，再看 `thiserror` 与 `anyhow` 各自补齐了哪一半，就一目了然了。

## 二、 第一性原理分工：为什么需要 `thiserror` 和 `anyhow` 两个库？

初学工程实战的开发者最常问的问题是：「`thiserror` 和 `anyhow` 都是处理错误的，我选哪一个装进项目？」

答案是：**在绝大多数真实服务端项目里，两个都会装，因为它们分别对应着我们在[多态选型](/abstraction/polymorphism-choice/)中确立的两类完全正交的架构场景**。

| 决策维度 | **`thiserror`**（面向库与核心领域模块） | **`anyhow`**（面向应用组装与顶层边界） |
| --- | --- | --- |
| **对应的第 8 章模型** | **闭合集合：`enum`（代数数据类型）** | **开放集合：类型擦除容器**（精装版 `Box<dyn Error + Send + Sync>`） |
| **调用方需要做什么？** | **需要编写代码 `match` 区分具体失败原因**（例如：余额不足引导充值，网关超时触发退避重试） | **不需要按变体分支恢复**，只需把任意底层错误统一归拢、附加业务现场上下文，最终上报日志或返回 HTTP 500 |
| **核心底层机制** | 第 16 章**派生过程宏 `#[derive(Error)]`**，在编译期零开销生成 `Display`、`Error::source` 与 `From` 代码 | 窄指针动态错误句柄 **`anyhow::Error`**，支持 `.context()` 串联多层错误原因链与捕获 `Backtrace` |

一句话记住这条黄金分界线：**如果你关心调用方怎么用代码分支去处理这个错误，用 `thiserror` 造具体枚举；如果你只关心人类工程师在日志里怎么看懂这次失败，用 `anyhow` 擦除类型并挂上下文。**

结合我们在[过程宏祛魅](/architecture/procedural-macros/)中学过的派生宏规则，`#[derive(Debug, Error)]` 不会篡改 `BillingError` 枚举自身的内存布局，只会在它下方自动追加三份标准库契约实现：

1. **`#[error("...")]` 自动生成 `fmt::Display`**：支持直接引用结构体变体字段（如 `{balance}`）或元组变体下标（如 `{0}`），省去手写几十行 `write!(f, ...)`；
2. **`#[from]` 一箭双雕生成 `From` 与 `Error::source`**：在 `GatewayIo(#[from] io::Error)` 上标一个 `#[from]`，宏不仅自动生成 `impl From<io::Error> for BillingError` 让函数体内的 `?` 直接畅通，还会自动把该字段注册为 `Error::source(&self)` 的底层起因，确保错误链不断裂。（若有两个变体包装了同一种底层 `io::Error`，不能同时标 `#[from]`，此时改标 **`#[source]`** 保留起因链并手写构造即可。）

注意一个关键事实：`thiserror` 只在编译期帮你生成标准库 `std::error::Error` 的实现代码，它**不会出现在你的公开类型签名里**——外部调用方看到的就是一个纯正的普通 Rust `enum`，完全不感知你内部用了 `thiserror`。

## 四、 应用顶层实战：用 `anyhow` 汇聚错误并挂载业务案发现场

现在来到外层的业务编排层（如 HTTP 接口控制器 `handle_checkout`）。在这里，我们需要先拦住未登录的匿名请求，再调用刚才的 `billing::charge`：如果遇到可恢复的 `InsufficientFunds` 就走业务降级；如果遇到网关故障，就挂上「哪个用户、哪笔订单扣款失败」的现场信息向上汇报。

在这段代码里，重点掌握 `anyhow` 日常出镜率最高的三件工具：

1. **返回类型简写 `anyhow::Result<T>`**：等价于 `std::result::Result<T, anyhow::Error>`。任何实现了标准库 `std::error::Error + Send + Sync + 'static` 的错误（包括我们刚用 `thiserror` 造出来的 `BillingError`），都能直接通过 `?` 自动转入 `anyhow::Error`；
2. **给裸错误穿上业务上下文外衣：`.context(...)` 与 `.with_context(|| ...)`**：
   如果底层只抛上来一句光秃秃的 `"No such file or directory (os error 2)"` 或 `"tcp connect timeout"`，线上排障根本不知道是读哪份配置、处理哪笔订单出了问题。导入 `anyhow::Context` Trait 后：
   - 静态固定文案用 `.context("读取网关证书失败")?`；
   - 需要动态拼接变量（如 `format!("... user #{user_id}")`）时，**务必使用接收闭包的 `.with_context(|| format!(...))?`**——遵循我们在第 6 章讲过的惰性求值原则，正常成功路径占 99.9%，闭包完全不会执行，做到**成功路径零 `String` 堆内存分配**；
3. **快速早退宏 `ensure!` 与 `bail!`**：
   `ensure!(条件, "错误说明")` 等价于 `if !条件 { return Err(anyhow!(...)); }`（类似不会导致线程崩溃的受检版 `assert!`）；而 `bail!("错误说明")` 则直接当场构造错误并 `return Err`。

运行完整实验代码，看看顶层捕获错误后遍历 `.chain()` 打印出的三层完整因果链：

<small class="code-source">运行输出</small>
```text
order #1001 downgraded to unpaid draft (500 < 800)
top error: checkout failed for user #42, order #1002
  cause[0]: checkout failed for user #42, order #1002
  cause[1]: payment gateway I/O failure
  cause[2]: tcp connect timeout
```

看最后四行输出：从最外层的业务动作（用户 #42 的订单 #1002 下单扣款失败），到中间层的模块归属（支付网关 I/O 故障），再到最底层的操作系统报错（TCP 连接超时），整条故障证据链严丝合缝，没有任何一层信息丢失。

*(补充：如果线上偶发深层错误需要查看完整的函数调用栈帧，无需修改代码，只需在启动服务时设置环境变量 `RUST_BACKTRACE=1`，`anyhow::Error` 就会在构造底层错误的第一现场自动捕获调用栈快照。)*

<Aside type="caution" title="Code Review 红线：不要在公共库的公开签名里暴露 anyhow::Error">
如果在底层通用库或核心领域模块的公开函数上偷懒全写 `-> anyhow::Result<T>`，一旦上游业务方需要针对「唯一键冲突」或「余额不足」做专门的分支恢复，就会因为具体枚举类型已被擦除而束手无策（只能被迫做脆弱的运行时向下转型 `.downcast_ref::<BillingError>()` 甚至匹配报错字符串）。守住**「内层模块对外用 `thiserror` 立契约，顶层应用入口用 `anyhow` 收口并补上下文」**，架构边界才会干净。
</Aside>

## 小结

1. **统一底座**：标准库 `std::error::Error` 用 `Display + Debug + source()` 定下了跨库互通的错误链协议；
2. **领域与库层用 `thiserror`**：通过派生宏零成本生成强类型错误 `enum`，把「可能发生哪几种业务失败」写进编译期类型契约供调用方 `match`；
3. **应用组装层用 `anyhow`**：通过 `anyhow::Result<T>` 统一接纳异构错误，在 `?` 传播沿途用惰性的 `.with_context(|| ...)` 挂载业务参数，保留完整的故障因果链。

现在，当携带了三层因果链的 `anyhow::Error` 一路冒泡抵达最顶层的接口边界时，我们该把它写到哪里去？在高并发异步服务里，又该如何像 Java 的 `Log4j2 + MDC` 那样把同一个请求途经的所有日志串联起来？
