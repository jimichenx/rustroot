从第 2 章写下第一行 `println!` 开始，到第 4 章的 `vec![1, 2, 3]`、第 5 章的 `#[derive(Debug, Clone)]`、第 14 章的 `#[tokio::main]` / `tokio::join!`，再到第 15 章的 `#[test]` 与 `assert_eq!`，我们已经和**宏（Macro）**打了整整十六章的交道。

走到这里，只要你试着把前十六章学过的底层规则串联起来，心里就会冒出两个绕不开的疑问：

1. **为什么 `println!("{}", s)` 看起来像按值传参，却没有把 `String` 变量 `s` 的所有权移走？**
2. **我们在前文反复确认过，Rust 的结构体没有对象头，编译后连字段名都会擦除，运行时根本不存在反射（Reflection）。那社区里的序列化库 `serde`、命令行解析库 `clap`，究竟是怎么「认识」你定义的结构体字段并自动完成转换的？**

这一章我们就掀开编译期元编程的底牌——看清那些带感叹号 `!` 和方括号 `#[...]` 的语法结构，如何在进入类型检查之前把代码展开成普通 Rust 源码。

本章分四节推进：

1. **为什么需要宏（从 `println!` 破案到编译期代码生成）**：拆开 `println!` 在幕后自动借用的展开结果，看清感叹号 `!` 的警示作用；对比 Java / Go 运行时反射与 Rust 编译期展开的成本取舍，厘清宏在编译流水线中的位置与词法作用域隔离（即文献中常说的「卫生性」）。
2. **声明宏 `macro_rules!`（针对代码片段的模式匹配）**：把声明宏还原为编译期的 `match` 表达式，亲手编写支持可变参数的 `my_vec!` 与批量生成 `Newtype` 的消除样板宏，掌握查看宏展开结果的工具。
3. **过程宏祛魅（`#[derive]`、属性宏与函数式宏）**：理解运行在编译器里的 `TokenStream -> TokenStream` 函数及独立 `proc-macro` 编译单元要求，彻底拆开一路用过来的 `#[derive(Debug)]`、`#[tokio::main]` 与 `#[test]`。
4. **生态全景与工程边界（社区用宏做什么，何时该克制）**：巡礼 Rust 生态五大核心宏应用场景，直面编译速度、IDE 补全与报错可读性代价，立下日常开发与 Code Review 的选型准则。

## 读完本章，检验自己的四个问题

- 为什么把 `String` 变量直接写进 `println!("{}", s)` 或 `assert_eq!(a, b)` 不会触发所有权移动？调用名末尾的感叹号 `!` 在向读代码的人提醒什么？
- 没有对象头和运行时反射的 Rust，是如何通过编译期展开实现 `#[derive(Serialize)]` 等零运行时开销特性的？宏展开发生在借用检查之前还是之后？
- 声明宏 `macro_rules!` 与过程宏（`#[derive]` / 属性宏）在能力边界与编译单元组织上有什么区别？为什么说 Rust 宏具备词法作用域隔离，不会像 C 语言 `#define` 那样污染同名局部变量？
- 在真实工程中，哪些场景应当果断复用社区成熟宏或编写简短声明宏，哪些场景应当克制写宏、退回普通函数与泛型？
