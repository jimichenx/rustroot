前两节的 `Newtype` 与 `Builder` 解决的是**对象在构造那一刻的数据合法性与传参灵活性**。

但在网络协议、硬件驱动、事务句柄等系统组件中，还有一类跨越对象整个存活期的架构难题：**严格的业务调用先后顺序**。

假设你正在编写一个数据库客户端 `DbClient`。按照底层通信协议，它的状态流转必须严格遵守这条单行铁轨：
`Disconnected（初始未连接）` → `Connected（已建立 TCP 连接）` → `Authenticated（已完成身份认证，允许发 SQL）` → `close（关闭销毁，禁止再次访问）`。

---

## 一、 传统运行时状态字段的两处遗憾

在传统面向对象语言中，常规写法是在 `DbClient` 类内部放一个运行时的状态枚举字段 `private State state;`。每次调用方执行 `client.executeQuery(sql)` 时，方法开头都得先写一句运行时防御分支：

```text
if (this.state != State.AUTHENTICATED) {
    throw new IllegalStateException("尚未完成认证，禁止查询");
}
```

把协议先后顺序交给运行时字段去防守，有两处无法回避的工程代价：
1. **错误暴露太晚**：如果某个业务分支漏调了 `authenticate()` 就直接调 `executeQuery()`，代码依然能顺利编译通过，只有等线上流量真的走到那条分支时才会抛出异常崩溃；
2. **无法在编译期根除「关闭后继续使用（Use-After-Close）」**：调用完 `client.close()` 之后，变量 `client` 依然留在当前作用域里，后续代码依然能对它调用查询方法。

在 Rust 中，我们可以调动**泛型类型构造器**与第 1 章的 **Move 所有权转移机制**，把这几个阶段直接提升为互不相容的**编译期类型实体**——这就是 **`Typestate`（类型状态机模式）**。

### 3. 用按值接收 `self`（Move）销毁旧状态

请特别留意状态跃迁方法的第一个参数：`connect(self)`、`authenticate(self, ...)` 以及最后的 `close(self)`，接收的全都是**按值移动的 `self`**（而不是借用 `&mut self`）。

这一下就把第 1 章的所有权规则发挥到了极致：
1. **乱序调用在编译期根本不存在**：刚调用 `new` 拿到的 `raw` 类型是 `DbClient<Disconnected>`。如果直接对它写 `raw.execute_query("SELECT 1")`，编译器当场报出 **`error[E0599]`**：
   ```text
   error[E0599]: no method named `execute_query` found for struct `DbClient<Disconnected>` in the current scope
   ```
   无需任何运行时 `if` 判断，因为在未认证的类型实体上，连 `execute_query` 这个方法名都不存在；
2. **旧状态自动失效，彻底封死 Use-After-Close**：当你执行 `let connected = raw.connect();` 时，`raw` 的所有权被按值移走并当场失效，你不可能再拿着旧的 `raw` 重复发起第二次连接；当你最后调用 `authed.close();` 时，`authed` 被按值消费释放，后续若再写 `authed.execute_query(...)`，直接被第 1 章的 **`error[E0382]`（移动后使用）** 拦截。

*(工程延伸：如果在上一节的 `Builder` 模式中也叠加 `Typestate`——例如令 `Builder<MissingHost>` 只有在调用 `.host(...)` 转变为 `Builder<HasHost>` 后才暴露 `.build()` 方法，就能做出连必填项缺失都在编译期报错的「类型安全 Builder」。)*

## 三、 架构裁决边界：何时用 `Typestate`，何时用 `enum`？

初见 `Typestate` 时，不少开发者会产生一种冲动：试图把项目里所有的业务状态（比如电商订单的「待支付 / 已支付 / 已发货」）全都改写成泛型 `Order<Unpaid>`、`Order<Paid>`。

在真实工程中，这里有一条必须守住的分界线。**编译期 `Typestate` 与第 6 章的运行时 `enum` 状态机各司其职，不能互相替代**：

| 决策维度 | 编译期类型状态机（`Typestate`：`Client<State>`） | 运行时枚举状态机（`enum OrderState`） |
| --- | --- | --- |
| **状态由谁决定？** | 由**源码中的调用顺序**静态决定（写代码时就明确第 1 步连接、第 2 步认证、第 3 步查询） | 由**运行期的外部输入**动态决定（从数据库查出一批历史订单，或收到随机网络事件，运行前未知） |
| **同构集合存储** | `Client<Connected>` 与 `Client<Authenticated>` 是**不同类型**，无法直接装进同一个 `Vec` | 所有变体同属**唯一一个 `OrderState` 类型**，可直接装进 `Vec<OrderState>` 批量遍历 |
| **典型适用场景** | 网络握手协议、HTTP 响应构造（先写 Header 再写 Body）、读写权限句柄、必填项 `Builder` | 业务工单/订单流转、UI 交互状态、解析器词法状态、编译器生成的 `async fn` 状态机 |

一句话收束这条架构判据：**调用顺序在写代码时是确定单行道的，用 `Typestate` 在编译期锁死；状态在运行期随外部输入动态分叉或需要放进同一个集合管理的，用闭合 `enum` + `match` 穷尽检查。**

## 小结

1. **`Typestate` 三要素**：零字节状态单元结构体（配合 `PhantomData<State>` 零内存开销）+ 按状态参数分别编写的 `impl` 块 + 按值接收 `self` 销毁旧状态的状态转换签名；
2. **恪守动静边界**：静态源码调用序列用 `Typestate` 消除运行时状态检查与 `Use-After-Close`；动态外部数据驱动的状态流转用 `enum`。
