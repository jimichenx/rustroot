在上一章搭好模块边界（`mod` / `crate`）、多包工作空间与自动化测试骨架之后，本章进入代码内部的**接口与领域建模核心**。

在多人协作（或人类与 AI 协作）的大型工程里，最消耗审查精力的往往是两类隐蔽的业务漏洞：

- 如果任何一个外部调用方都能直接用字面量 `{ id: 1, amount: 0 }` 拼装出一个金额为 `0` 的非法订单结构体，或者手滑把 `order_id` 和 `user_id` 两个 `u64` 参数传反，你在下游写再多防御性 `if` 检查也总会有漏网之鱼；
- 如果一个网络连接在还没有完成身份认证（`authenticate`）之前，编译器就允许调用方直接对它调用 `.execute_query()`，那这个协议顺序错误就只能等到线上运行时报错才能暴露。

**怎样在编译期就不给非法参数和非法状态留出任何拼装与调用的入口？**

答案正是把上一章立住的**模块私有封装边界**，与前四篇建立的**编译期类型实体、泛型与所有权移动**组合起来——形成零运行时开销的**类型驱动设计（Type-Driven Design）**。

本章按「单个参数值 → 多参数构造 → 对象全生命周期状态 → 读写性能边界 → 架构总纲」五步层层推进：

1. **`Newtype` 模式与「解析而非校验（Parse, don't validate）」**：对比形同虚设的 `type` 类型别名与零内存开销的 `Newtype`（`struct UserId(u64);`），配合模块私有字段把数据合法性校验锁死在唯一的构造入口处。
2. **灵活 API 签名设计与 `Builder` 模式**：从双向类型推断推导为什么 Rust 拒绝同名函数重载与默认参数，掌握具名关联构造、转换契约泛型、`..Default::default()` 与链式 `Builder` 的分层选型。
3. **`Typestate` 模式（编译期类型状态机）**：利用零大小状态类型参数（`PhantomData`）与按值消费 `self` 将合法的业务调用顺序编码进编译期签名，并厘清编译期 `Typestate` 与运行时 `enum` 状态机的选型边界。
4. **写时复制智能指针 `Cow<'a, B>`**：填平第 10 章智能指针全景表的最后一块拼图，拆解 `Borrowed` / `Owned` 双变体枚举与 `Deref` 机制，在读多写少场景中消灭防御性 `.to_string()` 克隆。
5. **经典设计模式的 Rust 重塑与 AI 时代的「签名即铁轨」**：回到 1994 年 GoF 设计模式的历史成因完成架构思维迁移，总结全指南的核心工程方法论——人类架构师如何用类型签名铺设不可出轨的铁轨，让编译器充当 AI 代码的形式化验收官。

## 读完本章，检验自己的四个问题

- `type UserId = u64;` 和 `struct UserId(u64);` 在运行时内存大小和编译期类型检查上有什么区别？什么是「解析而非校验（Parse, don't validate）」？
- 为什么拥有双向类型推断（如 `.into()`）的语言不能支持同名函数重载？在面对多可选参数结构体时，公开字段配合 `..Default::default()` 与私有字段配合 `Builder` 模式该如何取舍？
- 当你要防止调用方在「未认证的连接」上调用查询方法或防止「关闭后继续使用」时，编译期的 `Typestate` 模式是如何做到零字节运行时开销的？它与运行时的 `enum` 状态机各自适用于什么边界？
- 为什么说许多传统 OOP 设计模式（如访问者、策略、装饰器）在 Rust 中被原生语言机制直接消解了？在与 AI 协同开发时，如何运用本章武器落地「先写类型铁轨，再填函数实现」？
