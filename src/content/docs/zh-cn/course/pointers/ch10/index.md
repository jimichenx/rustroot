在前面的章节里，我们已经反复与两类保存内存地址的类型打过交道：一类是 `&T` 与 `&mut T` 这样的**引用（Reference）**；另一类是 `Vec<T>`、`String` 以及第 8 章用来返回动态多态对象的 `Box<dyn Trait>`。

在物理内存里，它们栈上存放的核心信息其实全都是**指向另一处内存的地址（指针）**。但为什么 Rust 把前者称为「引用」，而把后者（连同后续章节的 `Rc<T>`、`Arc<T>`、`MutexGuard<T>`）统称为**智能指针（Smart Pointers）**？为什么智能指针的数据明明住在堆上，用起来却能像普通引用一样直接解引用或自动脱壳转换，并在离开作用域的那一刻自动完成清理？

本章分五步拆解这套机制：

1. **指针家族全景（引用、智能指针与裸指针）**：从广义物理指针概念出发，看清 Rust 如何把同一个 8 字节内存地址按编译期约束拆分为引用（`&T` / `&mut T`）、智能指针（`struct` + `Deref` + `Drop`）与裸指针（`*const T` / `*mut T`）三大家族，点醒 `String` 与 `Vec<T>` 的智能指针身份，并建立标准库 5 类智能指针的全局地图。
2. **单一所有权的堆智能指针 `Box<T>`**：从类型构造器视角认识结构最精简的智能指针 `Box<T>`（对比 Java 的 `new` 对象句柄与 Rust 的唯一所有权约束），并通过 `Box<[T]>`、`Box<dyn Trait>`、巨型栈数据搬迁与递归类型（`E0072`）掌握它的三大工程使命。
3. **解引用的两层底座（内建 `*` 锚点与 `Deref` / `DerefMut` Trait）**：打破「所有 `*` 都走 Trait」的误解，区分编译器对内建引用 `&T` 的硬编码解引用与对智能指针的 `*(x.deref())` 两步展开，解开「为什么 `impl Deref for &T` 不会死循环」的疑团。
4. **跨类型借用转换（Deref Coercion、方法解析链与接口设计）**：看清编译器如何在参数位置自动把 `&Box<String>` → `&String` → `&str` 逐层脱壳，区分调用点自动解引用与三大不转换禁区，并立下「禁止用 `Deref` 模拟 OOP 继承」的工程铁律。
5. **`Drop` Trait（确定性析构、逆序释放与 RAII 资源守卫）**：拆解编译器在作用域终点自动插入 `Drop::drop(&mut self)` 的逆序释放规则，理解为什么禁止直接调用 `x.drop()`（`E0040`）而必须使用 `std::mem::drop(x)`，并掌握 RAII 资源守卫模式。

## 读完本章，检验自己的五个问题

- 在 64 位平台上，`&i32`、`*const i32` 和 `Box<i32>` 在栈上都只占 8 字节且存着相同的内存地址，它们在编译期类型实体上的核心约束差异是什么？为什么说第 4 章学过的 `String` 和 `Vec<T>` 其实也是智能指针？
- 为什么 `Box<[i32]>` 在栈上占 16 字节，而 `Vec<i32>` 占 24 字节？在递归枚举 `enum List` 中套一层 `Box<List>` 为什么就能解决 `E0072` 无限大小报错？
- 既然标准库为普通引用也实现了 `impl<T: ?Sized> Deref for &T`，为什么执行 `*&x` 时编译器不会陷入无限递归调用？
- 为什么把 `&String` 传给 `fn foo(s: &str)` 能自动转换，但把 `&mut String` 和 `&String` 搞混方向时，编译器只允许 `&mut T -> &U` 而严禁 `&T -> &mut U`？
- `Drop::drop(&mut self)` 的签名为什么接收的是 `&mut self` 而不是按值接收 `self`？如果允许程序员在代码里直接写 `x.drop()` 会引发什么内存安全事故？
