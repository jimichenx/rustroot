在第 13 章里，我们掌握了多核操作系统的多线程并发（`std::thread`、`Arc`、`Channel`、`Mutex` 与 `Send` / `Sync`）。当你的程序需要同时跑满 8 个 CPU 核心做密集型计算时，操作系统线程是最直接的工具。

但现代后端服务、网络网关与 AI 基础设施面临的往往是另一种完全不同的场景：**高并发 I/O 等待**。
一台服务器可能需要同时保持 **5 万个客户端网络连接**，而每个连接 99% 的时间其实都在静静等待网卡收发数据或等待数据库返回结果。如果你为这 5 万个连接创建 5 万个操作系统线程，光每个线程预留的数 MB 独立调用栈就会瞬间耗尽上百 GB 内存，频繁的内核态上下文切换也会把 CPU 彻底拖垮。

**如何在只开启少数几个操作系统线程（比如 8 核机器只开 8 个线程）的前提下，同时并发处理成千上万个连接？**

本章作为第五篇《共享、并发与异步》的收官之章，分四节由浅入深地揭开 Rust 异步并发的全貌：

1. **异步编程全景（从线程等待、Callback 地狱到状态机与运行时）**：先建立宏观视野——要想不浪费线程，任务在等待 I/O 时必须能**主动退出线程占用**；回顾早期用回调函数（Callback）让出线程导致的「回调地狱」，看清现代语言（如 Kotlin 协程与 Rust `async / await`）如何用「表面顺序编写 + 底层编译器展开为状态机 + 背后异步运行时（线程池与 Event Loop）驱动」完美破局，并理解为什么 Rust 语言本身不内置运行时。
2. **`Future` 契约与工作原理（状态机是如何被推动的？）**：掀开状态机与异步运行时握手的标准库契约 `std::future::Future`，拆解工作线程如何通过 `poll` 方法推进状态机、遇到未就绪 I/O 时返回 `Poll::Pending` 让出线程，以及操作系统事件循环如何通过门铃唤醒器 `Waker` 精准唤醒就绪任务。
3. **`async / await` 实战与并发避坑**：掌握在工业级运行时（以 `tokio` 为代表）中顺序等待（`.await`）、并发分支汇合（`join!`）与派生后台任务（`spawn`）的用法，并在 Code Review 中重点拦截「在 `async` 中调用阻塞休眠/同步 I/O」与「持标准库 `MutexGuard` 跨过 `.await`」两大并发事故。
4. **自引用状态机与 `Pin<P>`**：接回第 10.1 与 11.5 节埋下的终极伏笔——当 `async fn` 内部的局部引用跨过 `.await` 挂起点时，编译器生成的状态机结构体为什么必然变成**自引用结构体**？看清智能指针包装器 `Pin<P>` 与 `Unpin` 如何从类型层面锁死内存地址，完成全篇收束。

## 读完本章，检验自己的四个问题

- 为什么在海量 I/O 等待场景下操作系统线程太重？从 Callback 回调地狱演进到 `async / await` 状态机解决了什么痛点？像 `tokio` 这样的异步运行时（永动机）底层是由哪两大部件构成的？
- 写下一行 `let fut = fetch_data();`（不加 `.await`）时，`fetch_data` 函数体里的代码执行了吗？`Future::poll` 返回 `Poll::Pending` 后，运行时是怎么知道什么时候该再来 `poll` 一次的？
- 为什么在 `async fn` 里面绝对不能调用 `std::thread::sleep`，也不能拿着第 13 章的标准库 `std::sync::MutexGuard` 跨过 `.await` 挂起点？
- 为什么 Kotlin / JavaScript 的异步状态机不需要程序员操心 `Pin`，而 Rust 的 `async fn` 状态机一旦跨 `.await` 借用局部变量，就必须用 `Pin<P>` 锁死在内存原地上？
