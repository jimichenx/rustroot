## 操作系统线程的等待浪费

我们来看一个再普通不过的后端业务函数：根据用户名 `username` 先去用户服务查出 `user_id`，再拿着 `user_id` 去订单服务查出他的历史订单：

```rust
// 传统同步阻塞写法：每一步网络请求都会把当前线程死死卡住
fn process_order_blocking(username: String) -> String {
    let user_id = fetch_user_blocking(&username); // 耗时 25 毫秒等待网络返回
    let orders = fetch_orders_blocking(user_id);  // 耗时 25 毫秒等待网络返回
    format!("用户 #{} 的订单: {}", user_id, orders)
}
```

我们拿着秒表，算一算执行这个函数总共花了多少时间：
1. CPU 花 **1 微秒** 把查用户的网络包发出去；
2. 接下来整整 **25 毫秒（25,000 微秒）**，线程什么都干不了，只能在原地干等远程服务器把 `user_id` 传回来；
3. 拿到 `user_id` 后，CPU 花 **1 微秒** 发起第二步查订单请求，然后又是整整 **25 毫秒** 的干等；
4. 最后花 **2 微秒** 拼接字符串返回。

你看，在整个 50 毫秒的生命周期里，CPU 真正干活的时间加起来只有 **4 微秒**，其余 **99.99% 的时间全在干等网卡数据**。

如果沿用第 13 章「一个请求分配一个操作系统线程」的做法，同时处理 5 万个这样的请求，服务器当场就会被两笔物理开销压垮：
- **内存被独立栈撑爆**：操作系统无法预知你的函数会调用多深，默认给每个线程预留 **2MB ～ 8MB** 的独立调用栈。5 万个线程光是空栈就要吃掉 **`50,000 × 2MB = 100GB` 内存**；
- **CPU 被上下文切换拖垮**：操作系统内核要在 5 万个频繁睡着、频繁醒来的线程之间不停地保存寄存器、切换页表、刷新缓存，CPU 的算力全耗在了调度内耗上。

## 核心矛盾：让出线程与保存现场

怎么打破这种浪费？方向其实只有一个：
既然机器只有 8 个 CPU 核心，那我们全场就**只开 8 个操作系统工作线程**。当某个工作线程执行 `process_order` 发起第一步网络请求、需要等待 25 毫秒时，**当前任务必须立刻退出对这个工作线程的占用（把线程让出来）**，让工作线程马上转身去执行其他已经准备好的任务；等 25 毫秒后 `user_id` 从网卡传回来了，再找一个工作线程接着跑下半场。

想法听起来很顺，但一旦落到计算机底层的调用栈上，我们立刻撞上了一个致命的物理死结：

**在 CPU 和操作系统眼里，一个正在线程上运行的函数，要想把当前线程让给别的函数用，唯一的办法就是执行 `return` 从当前函数返回。可是一旦函数 `return` 返回了，这个函数的栈帧（Stack Frame）就会当场被销毁——你在前半场算出来的局部变量（比如 `username`、`user_id`），以及「下次该从第几行代码接着跑」的位置信息，全都随着栈帧灰飞烟灭了。**

等 25 毫秒后网卡数据到了，你想接着跑下半场，可之前的栈帧早就没了，你去哪儿找上半场留下的局部变量？

你看，这就是所有异步编程技术都在解决的同一个底层问题：
> **当一个任务在中途主动 `return` 让出线程时，怎么在栈帧之外，把它的「执行阶段」和「跨阶段局部变量」安全地保存下来？**

为了解开这个死结，工程师们先后走过了两代方案。

## 早期方案：Callback 与回调地狱

在早期没有编译器特殊支持的年代（如早期 Node.js、Java NIO 或 C 事件框架），既然函数 `return` 退栈会弄丢下半场的代码和变量，程序员只能亲自动手，**把一个原本完整的函数强行劈成好几截，把下半场要干的活包进一个匿名回调函数（Callback）里**：

```javascript
// 早期 Callback 写法：程序员手动把一个顺序函数劈成三截嵌套的回调函数
fetchUser("alice", function(userId) {
    // 25ms 后网卡收到 userId，事件循环调用这第一层回调：
    fetchOrders(userId, function(orders) {
        // 又过了 25ms 收到 orders，再调用这第二层回调：
        sendNotification(userId, orders, function(status) {
            console.log("全部完成:", status);
        });
    });
});
// 发起 fetchUser 注册好回调后，外层函数立即 return 退出，把线程让出来
```

平心而论，Callback 确实解开了刚才的物理死结：外层函数注册完回调就立刻 `return` 退栈，一微秒都不占用工作线程；而需要跨阶段保留的变量 `userId`，则被里层的闭包捕获保存在了堆上。

但代价是**把痛苦全转嫁给了写代码的人**：
明明在人类脑子里是「第 1 步查用户 → 第 2 步查订单 → 第 3 步发通知」的一条直线，写出来却变成了不断向右缩进的「回调地狱（Callback Hell）」。一旦中间加上 `if / else` 分支、循环或者错误提前返回，逻辑就被切得支离破碎。

## 现代方案：`async / await` 与状态机

既然人类喜欢按从上往下的顺序写代码，而底层为了主动让出线程又必须把函数拆成一段一段的——那能不能**让程序员照常按顺序写代码，由编译器在编译期自动帮我们把它改写成一段一段的数据结构**？

这就是现代语言中 **`async / await`**（以及 Kotlin 中的 `suspend` 协程）诞生的原因。

我们来看看，当你在 Rust 里用 `async / await` 写下这段清爽的顺序代码时，背后到底发生了什么：

```rust
async fn process_order(username: String) -> String {
    let user_id = fetch_user(&username).await; // 挂起点 1：若未就绪，主动让出线程
    let orders = fetch_orders(user_id).await;  // 挂起点 2：若未就绪，主动让出线程
    format!("用户 #{} 的订单: {}", user_id, orders)
}
```

这段代码读起来和开头的同步阻塞代码几乎一模一样，只是在函数前加了 `async`，在两步网络等待后加了 `.await`。

但在编译期，Rust 编译器看到 `async fn` 和里面的两个 `.await` 挂起点时，并不会把它编译成一个一条道跑到黑的普通函数，而是自动帮你生成了一个我们在第 6 章学过的**枚举状态机（`enum` State Machine）**。

### 1. 用枚举字段保存局部变量

编译器会仔细检查你的函数体，看哪些局部变量需要跨过 `.await` 挂起点继续存活（比如第 1 步之前的 `username`，以及跨过第 1 个 `.await` 传给第 2 步的 `user_id`），然后直接把它们变成**枚举变体里的字段**：

## 异步运行时：线程池与 Event Loop

现在，「车（状态机结构体）」已经被编译器造出来了。但状态机自己只是一块静态的数据，它不会自己调用自己的 `step()` 方法。

当阶段 1 发起网络请求并返回 `None` 让出工作线程之后，**是谁在后台帮它盯着网卡数据到没到？等 25 毫秒后网卡数据到了，又是谁重新调了一次 `task.step()` 把它推进到阶段 2 的？**

这就引出了所有异步系统背后都必不可少的那台「永动机」——**异步运行时（Asynchronous Runtime，在 Rust 生态中最主流的实现就是 `tokio`）**。

如果你把 `tokio` 这台永动机的引擎盖掀开，里面其实就装着两个不停配合运转的齿轮：

1. **少而精的工作线程池（Worker Thread Pool）**：
   比如在 8 核机器上，`tokio` 启动时只创建 8 个操作系统线程。这 8 个工作线程内部跑着一个循环：不停地从**就绪任务队列**里拎出已经准备好往下走的状态机，调用一次它的推进方法；
2. **底层的 I/O 事件循环（Event Loop / Reactor）**：
   专门对接操作系统内核的高效多路复用接口（Linux 的 `epoll`、macOS 的 `kqueue`、Windows 的 `IOCP`）。

我们跟着一个任务在「永动机」里走一圈，画面就彻底活起来了：
- **让出线程**：工作线程 1 拎起你的状态机调了一次 `step()`，发起了查用户请求，状态机返回「还没好（`None`）」。工作线程 1 随手把这个状态机挂到旁边的 **Event Loop 等待架**上（此时该任务占用的 CPU 为 `0`，占用的内存只有状态机那几十个字节），然后工作线程 1 立刻去拎队列里的下一个任务，1 微秒都不耽误；
- **唤醒重入**：25 毫秒后，网卡收到了数据库返回的 `user_id`。操作系统内核通知 **Event Loop**：「302 号连接的数据到了！」Event Loop 立刻把这个状态机从等待架上取下来，重新塞回**就绪任务队列**；
- **继续推进**：工作线程池里任意一个空闲的线程（比如工作线程 3）从队列里拎起这个状态机，再调一次它的 `step()`——状态机顺着 `match` 直接跳进阶段 1，拿着 `user_id` 继续往下跑！

编译器把 `async fn` 拆成枚举。工作线程调用 `step`；没准备好就挂到 Event Loop，数据到达后再塞回就绪队列。

## 跨语言异步方案对照

看懂了「状态机保存现场 + 背后永动机驱动」这套底层骨架后，我们再来横向看看主流编程语言在这个问题上各自做出了怎样的工程取舍。

### 1. JavaScript：单线程 Event Loop 与 `Promise`

JavaScript 是最早普及异步编程的语言之一。为了走出前文看到的 Callback 回调地狱，JS 先后引入了 `Promise` 对象和 `async / await` 语法糖。

在底层实现上，JS 的选择非常鲜明：
- **内置的纯单线程永动机**：JS 虚拟机（如 V8 引擎）直接内置了一台**单线程 Event Loop**。所有 JS 代码永远在唯一一个主线程上交替运行——好处是程序员根本不需要考虑多线程数据竞争和加锁，坏处是无法直接利用多核 CPU 的并行算力；
- **立即执行与堆上分配**：在 JS 中，只要你调用了 `fetchUser("alice")`（哪怕后面还没写 `await`），这个函数**当场就会开始执行第一步**，同时在堆内存上分配一个由垃圾回收器（GC）托管的 `Promise` 对象，用来挂载后续的状态与回调链。

### 2. Go 与 Java：有栈协程

来到后端多核时代，Go 语言（以及 Java 21+ 的虚拟线程 Virtual Threads）走了另一条截然不同的技术路线——它们甚至不要求程序员在函数上写 `async` 和 `await` 关键字。

不写 `.await`、不把函数拆成状态机，怎么做到中途让出线程还不丢局部变量？
Go 的办法是**「有栈协程（Stackful Coroutine）」**：
- 每当你用 `go foo()` 启动一个协程时，Go 运行时就在**堆内存**里为这个协程单独分配一块只有 **2KB 的微型调用栈**；
- 当协程在半路遇到网络 I/O 等待时，它根本不需要 `return` 退栈，而是直接把这个 2KB 的微型栈连同里面的局部变量原封不动地封存在堆上，然后把操作系统工作线程切换去跑别的 `goroutine`（若函数调用太深、2KB 不够用了，运行时会在堆上自动申请一块更大的内存把栈拷贝过去）。

这种方案写起来最接近传统线程，但它的物理代价也很明确：**语言必须在生成的每一个二进制程序里，强制捆绑一套庞大的内置运行时调度器与垃圾回收器（GC）**，用来管理成千上万个堆上微型栈的分配、扩容与回收。

### 3. Kotlin：JVM 上的状态机

Kotlin 没有采用 Go 那种给每个任务分配独立小栈的做法，而是走了和 Rust 一样的**「无栈协程（Stackless Coroutine） / 编译器状态机」**路线：
- 当你写下一个带 `suspend` 关键字的挂起函数时，Kotlin 编译器在编译期会自动把它改写成一个带有 `label` 状态码的状态机类（`Continuation`），跨挂起点的局部变量直接变成这个类实例的成员变量；
- 语言标准库本身只保留最薄的挂起原语，而把背后那台「线程池 + Event Loop」永动机交给官方库 `kotlinx.coroutines` 去提供。
- 不过，由于运行在 JVM 之上，Kotlin 生成的每一个状态机实例依然是在**堆上动态 `new` 出来的对象**，其生命周期由 JVM 的垃圾回收器负责管理。

### 4. Rust：内联状态机与可插拔运行时

对照前面三门语言，Rust 在设计 `async / await` 时做出了三项符合系统级语言定位的取舍：

1. **零堆分配的静态内联状态机**：
   不同于 JS 的 `Promise`、Go 的 2KB 堆栈或 Kotlin 在 JVM 堆上 `new` 出的状态机对象，Rust 编译器把 `async fn` 展开成的 `enum` 状态机是一个**编译期大小完全确定的普通值**（比如正好占 64 字节）。它可以像普通结构体一样直接放在栈上，或者内联嵌套在上层状态机内部，**不需要在每次调用时动态分配堆内存，也完全不需要 GC**。
2. **纯惰性求值（Lazy）**：
   不同于 JS 调用 `async` 函数即刻开始执行，在 Rust 中调用 `process_order("alice")` **不会执行函数体里的任何一行代码**——它仅仅是在内存里构造并返回了一个处于初始阶段 0 的 `enum` 状态机实例。只有当你把它交给运行时去 `.await` 驱动时，它才会真正开始干活。
3. **语言零内置运行时（编译器造车，社区库造发动机）**：
   遵循我们在[第 7 章章末视野](/abstraction/kernel-and-library/)讲过的「内核机制与库策略分离」，Rust 语言本身**不内置任何异步运行时**。
   如果你在写高并发 Web 服务器，可以引入 **`tokio`** 作为多线程工作窃取永动机；如果你在写没有操作系统的汽车芯片或智能手表固件（`#![no_std]`），你只需要一个几百字节的极简轮询循环就能驱动同一套 `async / await` 状态机——绝不强迫不需要的人付出任何运行时体积与内存代价。

## 小结

顺着这一节的脉络，我们已经把异步并发最核心的骨架立了起来：
1. **为什么要异步**：海量 I/O 等待下，不能让任务占着昂贵的操作系统线程干等，必须在等待时主动 `return` 让出线程；
2. **为什么是状态机**：函数一旦中途 `return` 退栈，栈上的局部变量就会销毁；通过 `async / await`，编译器自动把跨挂起点的局部变量打包进 **`enum` 状态机结构体**替栈帧保存现场，彻底告别了手写 Callback 回调地狱；
3. **谁在驱动它**：背后那台由「固定工作线程池 + I/O Event Loop」组成的**异步运行时（如 `tokio`）**，负责在后台一拍一拍地推动状态机。

现在，请仔细想一个问题：
既然「状态机」是 Rust 编译器生成的，而驱动它的「永动机（`tokio`）」是外部社区库写的——**它们两个之间必须有一套全国通用的标准握手协议，否则 `tokio` 怎么知道该调状态机身上的哪个方法？当状态机在等待网卡数据时，Event Loop 又怎么知道该唤醒哪一个状态机？**

下一节（`14.2`），我们就来拆解这份连接编译器状态机与异步运行时的核心契约——**`Future` Trait、`poll` 方法与门铃唤醒器 `Waker`**。
