在上一章（第 12 章）里，我们通过 `Rc<T>`、`Cell<T>` 和 `RefCell<T>` 解决了**单个线程内部**的多方共享与内部修改问题。在那间单线程的温室里，CPU 永远按顺序一条接一条地执行指令，绝不会出现「两个人同一纳秒同时往同一个内存地址写数据」的情况。

但现代计算机的 CPU 都有多个物理核心。当我们希望同时利用多个 CPU 核心并行计算、或者在后台处理耗时任务时，程序就必须跨出单线程温室，启动多个**操作系统线程（OS Threads）**。

很多习惯了 Java、Python 或 Go 的开发者第一次写 Rust 多线程代码时，往往会产生一种强烈的挫败感：**「在别的语言里，我随便 new 一个线程、把外面的对象传进去就能跑；怎么到了 Rust 里，刚写两行 `thread::spawn` 就被编译器拦得寸步难行？」**

本章的任务，就是带你从零建立多线程的物理内存图景，理解为什么传统语言里「随手就能跑起来」的多线程代码会在暗中埋下致命的并发地雷，而 Rust 的所有权与借用模型又是如何在编译期替你把这些地雷一颗颗排干净的。

本章分五节循序渐进地展开：

1. **创建线程与数据传递（`thread::spawn`、`join`、`move` 与 `thread::scope`）**：先对比 Java 等语言的并发隐患与 Rust 的编译期拦截，建立「每个线程独占调用栈、共享同一个堆」的物理模型；从最简单的第一行无参线程写起，掌握用 `move` 跨线程转移所有权，以及用 `thread::scope` 零成本借用父线程局部变量。
2. **跨线程共享所有权（为什么 `Rc<T>` 会崩溃，而 `Arc<T>` 是安全的？）**：当多个后台常驻线程必须共同持有一份只读配置时，用慢镜头拆解为什么 `Rc<T>` 的非原子计数在多线程同时加减时会算错账并导致提前释放，进而引出基于 CPU 硬件原子指令的 **`Arc<T>`**。
3. **线程间通信（通过通道 `Channel` 跨线程移交所有权）**：掌握并发协作的第一条正道——使用 `std::sync::mpsc` 通道在线程间传递消息，看清 `tx.send(val)` 如何通过 Move 语义从根源上切断发送方与接收方的数据竞争。
4. **共享状态并发（互斥锁 `Mutex<T>`、读写锁 `RwLock<T>` 与 `Arc<Mutex<T>>`）**：掌握并发协作的第二条正道——当多个线程确实需要原地修改同一份数据时，通过跨语言对照看清 Rust 如何把被保护的数据直接锁进 `Mutex<T>` 盒子里，利用 `MutexGuard` 的 `DerefMut` 与 `Drop` 自动加解锁，并掌握 `Arc<Mutex<T>>`、`RwLock<T>` 与持锁粒度审查。
5. **`Send` 与 `Sync`**：在前四节积累了充足的实战体感后，从「为什么要发明这套标签」与「为什么分成 `Send` 和 `Sync` 两个单词」出发，通过 2×2 四象限全景表收束第 12～13 章的全部类型边界。

## 读完本章，检验自己的五个问题

- 为什么在 Java / Go 中把局部对象传给子线程非常容易写，但容易引发数据竞争，而在 Rust 中 `thread::spawn` 默认连借用父线程栈上的一个局部引用都不允许？在什么条件下可以直接用 `std::thread::scope` 借用局部变量？
- 为什么第 12 章的 `Rc<T>` 不能跨线程使用？它的多线程孪生兄弟 `Arc<T>` 在底层改了什么，为什么 Rust 不干脆把所有 `Rc<T>` 默认都做成原子的？
- 当子线程通过通道调用 `tx.send(data)` 把数据发给主线程后，如果子线程紧接着再去打印 `data`，编译器会报什么错？这解决了传统语言通道通信的什么隐患？
- 对比 C++ / Java 中「先建一把锁 `lock`，再去改旁边的变量 `data`」，Rust 的 `Mutex<T>` 在类型构造器设计上有什么本质不同？`Arc<Mutex<T>>` 与第 12 章的 `Rc<RefCell<T>>` 是如何一一对应的？
- 请用物理动作解释：什么是 `Send`，什么是 `Sync`？为什么第 12 章的 `RefCell<T>` 满足 `Send`，却绝不满足 `Sync`？
