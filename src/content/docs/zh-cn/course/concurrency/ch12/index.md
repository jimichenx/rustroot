在第 1 章 `1.6` 节复盘所有权推演链时，我们曾留下过全指南的第三个未解缺口：**如果一份数据在业务逻辑上确实需要被多个结构共同持有，且在编译期算不出谁先退场、谁最后退场，该怎么办？**

同时，在第 4 章与第 11 章建立借用规则时，我们反复强调了编译期的「读写排他规则」：只要数据处于共享只读状态（`&T`），任何人都不允许修改它。可如果多方共享同一份数据后确实需要原地修改，或者某个外部 Trait 方法签名写死了只读接收者 `fn send(&self)`，我们在实现时却必须往内部缓冲区里追加记录，又该如何处理？

遇到这两道限制时，初学者常会觉得编译期的静态规则把路走窄了。而本章要展示的，正是 Rust 的机制与库策略分工：**当编译期无法静态算出唯一所有者或读写排他顺序时，我们不需要退回 `unsafe` 裸指针，而是可以利用第 10 章学过的 `Deref` 与 `Drop` 机制，通过标准库的类型构造器，将「所有权计数」和「借用检查」按需、局部地搬到运行时。**

本章分三节推进这套单线程下的动态机制：

1. **`Rc<T>` 与 `Weak<T>`（把唯一所有者放宽为单线程引用计数）**：从有向无环图（DAG）多上游共享同一节点的困境出发，看清 Rust 如何在不引入全局垃圾回收的前提下，用 `Rc<T>` 在局部构建出一套「Python 式的按需引用计数回收器」，并用不持有所有权的弱引用 `Weak<T>` 化解循环引用内存泄漏。
2. **`Cell<T>` 与 `RefCell<T>`（内部可变性——把借用检查搬到运行时）**：区分继承可变性与内部可变性，拆解「整进整出、零运行时计数」的 `Cell<T>` 与「运行时维护借用计数器、交出 `Ref<T>` / `RefMut<T>` 守卫、违规当场触发 `panic!`」的 `RefCell<T>`。
3. **组合模式与工程边界（`Rc<RefCell<T>>` vs 索引图 Arena）**：将两者合流为单线程多所有者可变组合 `Rc<RefCell<T>>`，剖析跨语句持有借用守卫引发线上崩溃的隐患，并演示如何用工业级的 **`Vec<Node> + usize` 下标索引（Arena 模式）** 重塑图结构所有权。

## 读完本章，检验自己的三个问题

- 为什么说 `Rc<T>` 像是用 Rust 自己的 `Deref` 和 `Drop` 机制在局部构建的「微型按需引用计数回收器」？调用 `Rc::clone(&a)` 时在栈和堆上分别发生了什么，为什么当循环引用出现时必须请出 `Weak<T>` 与 `.upgrade()`？
- 同样是在不可变引用 `&self` 下修改内部数据，`Cell<T>` 和 `RefCell<T>` 的解决思路有什么区别？为什么 `RefCell::borrow()` 返回的是智能指针 `Ref<T>` 而不是普通引用 `&T`？
- 在构建复杂图节点或双向关联结构时，为什么到处使用 `Rc<RefCell<Node>>` 是一种工程反模式？如何用 `Vec<Node> + usize` 下标（Arena 模式）把运行时的计数与崩溃风险重新拉回编译期？
