---
title: 共享、并发与异步
description: 当编译期单一所有权与单线程同步栈帧不够用时，通过 Rc / RefCell（单线程运行时计数与内部可变性）、Arc / Mutex / Channel / Send / Sync（多线程并发）以及 async / await 与 Pin（异步状态机），跨越所有权、线程与同步边界。
---

走完前四篇，我们已经搭建起 Rust 核心的零运行时开销静态防线：**同一时刻唯一所有者**（第 1～2 章）、**类型构造器与代数数据类型**（第 3～6 章）、**泛型单态化与 Trait 多态**（第 7～9 章），以及**单一所有权下的 `Box<T>`、`Deref`、`Drop` 与编译期生命周期 `'a`**（第 10～11 章）。

在树形数据结构与单向数据流中，这套在编译期结清的规则既快又安全。但在工业级系统里，我们迟早会遇到三类**仅靠编译期单一所有权和同步栈帧无法表达**的工程场景：

1. **单线程内的多方共享与局部修改**：比如在一张有向无环图（DAG）或 UI 组件树里，多个上游节点需要共同持有一个下游节点，直到最后一个持有者退场才能释放；或者某个接口签名锁定了只读引用 `&self`，但内部仍需更新本地缓存状态。
2. **跨越多核操作系统的多线程并发**：当计算与状态需要分发到多个操作系统线程并行执行时，如何在编译期杜绝数据竞争（Data Race），安全地在线程间移交所有权或共享修改？
3. **成千上万个高并发 I/O 任务的协作式调度**：当面对海量网络连接时，如何突破高成本的操作系统线程栈帧，用 `async / await` 将异步函数编译为紧凑的状态机，并用 `Pin<P>` 解决跨挂起点的自引用移动难题？

这一篇分三章，顺着**「单线程共享 → 多线程并发 → 异步状态机」**的三级台阶依次推进：

- **第 12 章（单线程共享与内部可变性）**：填平第 1 章留下的「多所有者共享」缺口，看清 Rust 如何在现有的 `Deref` 与 `Drop` 机制之上，构建出局部的按需引用计数智能指针 **`Rc<T>` / `Weak<T>`**，以及将借用检查从编译期搬到运行时的内部可变性容器 **`Cell<T>` / `RefCell<T>`**，并掌握用数组下标图（Arena 模式）替代滥用 `Rc<RefCell<T>>` 的工程重构手法。
- **第 13 章（多线程并发与 `Send` / `Sync`）**：与第 12 章构成 1:1 的同构镜像升级——将非原子的 `Rc<T>` 升级为硬件原子计数 **`Arc<T>`**，将单线程的 `RefCell<T>` 升级为互斥锁 **`Mutex<T>` / `RwLock<T>`**（或用 `Channel` 移交所有权），并揭晓编译器如何仅凭 **`Send` 与 `Sync`** 两个标记 Trait 在编译期拦截一切跨线程数据竞争。
- **第 14 章（异步并发 `async / await`、`Future` 状态机与 `Pin<P>`）**：从阻塞式线程走向协作式 `Future::poll` 状态机，掌握 `async / await` 的使用逻辑与跨 `.await` 挂起点的借用边界，并拆解编译器生成的自引用状态机为什么必须靠 **`Pin<P>`** 锁死物理内存地址。
