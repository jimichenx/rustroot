如果你有 Java、C# 或 Python 等面向对象（OOP）语言的背景，看到这一篇的主题是「类型」，多半会产生一个疑问：类型不就是 `int`、`float`、`boolean` 那些基础数据类型吗？一张表格就能列完，为什么需要用整篇去拆解？

这个疑问来自其他语言与 Rust 在数据模型上的第一道分歧。因此本章不急着罗列整数、浮点数的语法表（基础标量可随时查阅附录「[标量、元组与单元类型](/appendix/basics/scalars-and-tuples/)」），而是先用三节搭起认知 Rust 类型的整体骨架——阅读时只需抓准大体架构，示例中提前路过的 `Vec<u8>` 等复合写法不必追求当场全懂，本篇后续各章会逐一拆开。

## 从「一切皆对象」到「一切皆类型」

在许多主流语言里，基础值与复杂数据被分成了两套体系，或者统一交给了运行时的「对象」：

- 在 **Java** 中，基本类型（Primitive Type）通常只指 `int`、`double`、`boolean` 等几个基础数值；一旦涉及复杂结构与业务逻辑，主角就换成了**类（`class`）与对象（Object）**——在面向对象视角下，一个 `class` 就是「一块存放字段的内存 + 一组绑在上面的方法（Method）」。
- 在 **Python** 中，运行时的「一切皆对象」走得更彻底：连一个整数 `1`，在堆上都是顶着二十多字节头部的 `PyObject` 对象。

Rust 中没有 `class` 关键字，也没有「基本类型 vs 对象」的二元划分。

如果说面向对象语言在运行时追求「一切皆对象」，Rust 在编译期贯彻的就是**「一切皆类型（Everything is a Type）」**：

- 占 4 字节的整数 `i32` 是类型；
- 持有堆缓冲区的字符串 `String`、自定义的结构体 `User` 是类型；
- 在其他语言里只算访问修饰或语法特性的只读引用 `&String`、可变引用 `&mut i32`、数组切片 `&[u8]`，乃至后续会见到的每一个函数与闭包，都是各自独立、地位平等的**类型**。

而且在 Rust 中，类型承载的内容既不像 C 语言那样只有内存布局，也不止面向对象里的「内存字段 + 方法」。

## 类型的构成：编译期类型表与「类型实体」

既然内存布局只是类型的一半，另一半存放在哪里、记录了什么？

在源码里，`: i32`、`: &i32`、`: &mut i32`、`: String` 看起来只是写在冒号后面的几个符号；但在编译器（`rustc`）运行的内存里，编译器维护着一张**编译期类型表**——程序里用到的每一个具体类型，在编译器内部都对应表里一个装满元数据的独立对象。类似 Java 在运行时 JVM 里为每个类维护一个 `Class` 对象，Rust 是在编译期维护这些类型对象。本章为直观起见，我们暂且把编译期类型表里的每一个这样独立的具体类型对象称为一个**「类型实体」**（对应工程标准术语里的**具体类型 Concrete Type**）。

每一个类型实体内部都由两个栏位共同构成：

| 实体栏位 | 回答什么问题 | 登记的具体信息 |
| --- | --- | --- |
| **1. 物理表示（Representation）** | 这段数据在内存里**怎么排**？ | 1. **大小与对齐**：占多少字节（如 `i32` 占 4 字节，`String` 占 24 字节），编译期大小是否已知（`Sized`）；<br/>2. **位模式解释**：这些字节代表整数、内存地址，还是包含指针的控制头。 |
| **2. 行为与安全约束（Constraints）** | 对这段数据**能做什么、谁负责**？ | 1. **可调用的方法与行为**：挂载了哪些函数与 Trait；<br/>2. **所有权与释放责任**：赋值走 `Copy` 还是移动？离开作用域时是否调用 `Drop` 释放堆内存？<br/>3. **读写权限与数据不变量**：允许只读共享（`&T`）还是独占修改（`&mut T`）？内容须满足什么格式（如 `String` 的 UTF-8 约束）？<br/>4. **有效区间（生命周期）**：内部包含的引用在哪一段代码区间内有效？ |

把这张**编译期类型表**与上一篇追踪变量有效性的**编译期状态表**（见[声明与绑定](/memory/bindings/)）放在一起，就能看清类型实体在编译器内部是如何工作的：

<CompilerTypeTableDiagram />

对照图中的四个类型实体，可以核对三处关键机制：

1. **引用类型实体必然绑定具体的有效区间（scope）**：编译期类型表里不存在脱离有效区间的裸 `&i32`。<span class="rr-keypoint">源码里外层的 `r1` 与内层块的 `r2` 都写成 `&i32`，有效区间一长一短，在编译期类型表里是两个独立的类型实体。</span>当有效区间相同（或把外层长区间安全缩小赋给内层短区间）时，编译器允许按位复制；一旦反过来把内层短区间的 `r2` 赋给需要长区间的 `r1`，编译器核对两个类型实体的区间约束后就会直接拦截（呼应[悬垂引用](/memory/lifetimes/)）。
2. **`&i32` 与 `&mut i32` 是约束相反的两个类型实体**：两者的物理表示栏都写着 8 字节地址；但 `&i32` 登记了 `Copy: 是`，`&mut i32` 登记了 `Copy: 否`。编译 `let m2 = m1;` 时，编译器先查**编译期类型表**中 `m1` 对应的类型实体读出 `Copy: 否`，随即去改**编译期状态表**把变量 `m1` 标为「已移出」。
3. **`String` 与 `Vec<u8>` 同样是两个独立的类型实体**：物理表示都是 24 字节控制头，但 `String` 的类型实体在约束栏额外登记了合法 UTF-8 的不变量要求，不符合该约束的字节转换会被拒绝。

## 信息守恒与零成本抽象

再往底层追问一步：要让程序安全运行——知道数据有多大、能调用什么方法、何时释放内存——所需的信息总量不会凭空消失，只会改变存放的位置。

对比 Python / Java、C 与 Rust 存放这些信息的位置，就能看清 Rust **零成本抽象（Zero-Cost Abstractions）**的物理来源。

### 1. Python 与 Java：把信息放在运行时对象头上

在 CPython 中，一个整数 `1` 在堆上占 28 字节，其中前 24 字节是引用计数与类型指针等**对象头（Object Header）**。

在 Java 中，栈上的引用变量大小固定；而「对象属于哪个类、锁状态是什么、有哪些方法可调」的信息，保存在运行时堆对象的对象头里（64 位 JVM 上每个对象通常包含 12～16 字节对象头）。程序运行时，内存要为对象头留出空间，CPU 也要在运行期读取这些元数据。

### 2. C 语言：去掉对象头，但类型系统不检查安全约束

C 语言去掉了运行时对象头，内存布局紧凑。但它的类型主要描述「占多少字节、如何计算偏移」；指针归谁释放、是否已经悬垂、能否同时修改，类型系统不做记录，全靠程序员人工维护。

### 3. Rust：把信息装进编译期类型表，检查后整表擦除

在 Rust 中，堆上的 `"hello"` 只有 5 个字符字节，栈上的 `i32` 只有 4 个整数字节——运行时内存里没有对象头，也没有记录「能否修改、归谁释放、有效多久」的附加标记位。

为了安全与抽象所需的信息，全部装进了编译器内存里的**编译期类型表**。编译器在编译阶段查表完成借用检查、权限核对与方法地址绑定；检查通过、生成机器码时，整张编译期类型表随编译结束而擦除，交给 CPU 的只剩下裸字节与直接跳转的机器指令。

<TypeErasureDiagram />

不同语言在这套内存光谱上的横向对比可查阅附录「[从「一切皆对象」到「一切皆类型」](/appendix/comparisons/objects-to-types/)」；Rust 如何将 Java `class` 承担的多项职责拆回独立机制，可参阅附录「[没有 `class` 的对象感](/appendix/comparisons/oop/)」。

<Aside type="note" title="什么时候信息会留到运行时？">
编译后擦除类型信息是 Rust 的默认路径。只有遇到编译期确实无法确定的信息时——例如长度在运行期才决定的切片 `&[T]`，或需要在运行期动态分派方法的 `dyn Trait`——Rust 才会把缺失的那一项信息（长度 `len` 或虚表指针 `vtable`）显式放进指针中。即便如此，目标数据本体依然没有对象头。
</Aside>

## 小结与下一个问题

本节确立了三个基础判断：

1. **一切皆类型**：Rust 没有 `class` 与基本类型的二元划分，`i32`、`String`、`&String`、`&mut i32` 都是各自独立的类型；
2. **每个具体类型对应编译期类型表里的一个类型实体**：实体内部由「物理表示」与「行为与安全约束（含引用的实际有效区间）」两栏构成，哪怕表面同写 `&i32`，只要绑定的有效区间不同就是两个独立的类型实体；编译器通过查类型表来驱动变量状态表完成静态检查；
3. **信息前移并在编译后擦除**：Rust 不依赖运行时堆对象头保存类型元数据，核对通过生成机器码时，编译期类型表被整表擦除。

顺着第二条继续往下推，会遇到一个直接的问题：当我们在源码里写下 `struct User` 定义一个新结构体时，只往编译期类型表里放进了 `User` 这一个类型实体——从未手写定义过的 `&User` 和 `&mut User` 这些新类型实体，是在什么时候、由谁造出来放进编译期类型表的？下一节拆解生产类型实体的机制。
