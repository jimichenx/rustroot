看到第二篇的标题是「类型」，如果你有 Java、C# 或 Python 等面向对象（OOP）语言的背景，心里很可能会冒出一个疑问：**「类型（Type）不就是 `int`、`float`、`boolean` 那些基础数据类型吗？一张表格十分钟就能看完，为什么要用整整一篇的篇幅去讲类型？」**

这份疑惑，恰恰来自其他语言与 Rust 在底层世界观上的第一个分水岭。

## 从「一切皆对象」到「一切皆类型」

在许多主流语言里，开发者脑子里的概念是割裂的，或者全都托付给了运行时的「对象」：
- 在 **Java** 中，提到数据类型（Primitive Type），通常只指 `int`、`double`、`boolean` 这几个简单的数值；一旦涉及复杂的数据结构和业务逻辑，主角就变成了**类（`class`）与对象（Object）**——在 OOP 的视角里，一个 `class` 就是「一块存放字段的内存 + 一组绑在上面的方法（Method）」。
- 在 **Python** 中，更是把「一切皆对象」推到了极致：连一个最简单的整数 `1`，在运行时都是堆上顶着二十多字节头部的 `PyObject` 对象。

但在 Rust 里，**根本没有 `class` 这个关键字，也没有「基本类型 vs 对象」的二元割裂。**

如果说面向对象语言在运行时追求「一切皆对象」，那么 Rust 在编译期贯彻的就是**「一切皆类型（Everything is a Type）」**：
- 一个 4 字节的整数 `i32` 是类型；
- 带着堆缓冲区的字符串 `String`、你自己定义的结构体 `User` 是类型；
- 连在其他语言里只算「访问方式或语法特性」的**只读引用 `&String`**、**可变引用 `&mut i32`**、**数组切片 `&[u8]`**，甚至后续章节会见到的**每一个函数和闭包**，全都是各自独立、地位平等的**类型**。

更重要的是，在 Rust 里，一个类型身上承载的东西，既不像 C 语言那样只有裸内存布局，也不只是 OOP 里的「内存字段 + 方法」。

## 类型只是「内存布局」吗？

很多学过 C 语言或底层开发的读者，会带入另一种直觉：**「类型无非就是告诉编译器这段内存占几个字节、按什么格式解读。」**

真是这样吗？我们直接写一段代码，用标准库的 `std::mem::size_of` 打印几个类型在栈上占用的字节数（64 位平台）：

<Code code={sizes} lang="rust" />

运行程序，输出如下：

&i32:      8 bytes

String:    24 bytes

盯住这组结果里的两对类型：
1. **`&i32` 与 `&mut i32`**：在内存里一模一样，都只占 8 个字节（一个指向栈上 `i32` 的内存地址）；
2. **`String` 与 `Vec<u8>`（字节数组）**：在栈上也一模一样，都占 24 个字节（`ptr`、`len`、`cap` 三个机器字），堆上装的也都是连续的字节。

## 类型的构成：物理表示 + 行为与安全约束

上面两个例子把真相彻底亮了出来：**只知道内存里长什么样，在 Rust 里连一行赋值能不能编译通过都判断不了。**

在编译器的眼里，一个类型绝不仅仅是你写在源码里的那几个字母（比如 `i32` 或 `String`），而是编译器在**编译期**专门维护的一个完整信息集合体——我们把它叫作**编译期类型实体（compile-time type entity）**。每一个编译期类型实体，都由**两个部分**共同构成：

| 组成部分 | 回答什么问题 | 包含的具体信息 |
| --- | --- | --- |
| **1. 物理表示（Representation）** | 这段数据在内存里**怎么排**？ | 1. **大小与对齐**：占几个字节（如 `i32` 占 4 字节，`String` 占 24 字节），编译期大小是否已知；<br/>2. **位模式解释**：这些字节代表整数、内存地址，还是包含指针的控制头。 |
| **2. 行为与安全约束（Constraints）** | 对这段数据**能做什么、谁负责**？ | 1. **可调用的方法与行为**：绑定了哪些函数与 Trait（对应 OOP 里的方法）；<br/>2. **所有权与释放责任**：赋值时是走 `Copy` 还是走移动？离开作用域时要不要调用 `Drop` 释放堆内存？<br/>3. **读写权限与不变量**：允许只读共享（`&T`）还是独占修改（`&mut T`）？数据必须满足什么格式（如 `String` 的 UTF-8 约束）？<br/>4. **有效区间（生命周期）**：内部包含的引用在哪一段代码区间内有效？ |

回看刚才那两对布局相同的类型，区别全在**第二部分（行为与安全约束）**：
- `&i32` 和 `&mut i32` 的**物理表示**都是 8 字节地址；但在**编译期类型实体**的约束表里，`&i32` 登记了「只读、可 `Copy`」，而 `&mut i32` 登记了「可写、禁止 `Copy`（赋值即移动）」。
- `String` 和 `Vec<u8>` 的**物理表示**都是 24 字节控制头；但 `String` 的类型实体额外要求「内容必须为合法 UTF-8」。

## 信息守恒与零成本抽象

讲到这里，我们可以再往底层追问一步：**要让一个程序安全运行（知道数据有多大、能调什么方法、什么时候释放内存），总的信息量是守恒的。信息不会凭空消失，只会发生转移。**

不同语言把这些信息存放在不同的地方。对比一下 Python/Java、C 与 Rust 的选择，就能看透 Rust **零成本抽象（Zero-Cost Abstractions）**的物理根基。

### 1. Python 与 Java：把信息背在运行时对象头上

在 CPython 中，连一个整数 `1` 都在堆上占 28 字节，其中前 24 字节全是引用计数与类型指针等**对象头（Object Header）**。

在 Java 中，栈上的引用变量整齐划一；而「这个对象是什么类型、锁状态是什么、有哪些方法可以调」的信息，全都住在**运行时堆对象的对象头**里（64 位 JVM 上每个对象额外多出 12 到 16 字节）。程序跑起来时，内存要为对象头付出空间代价，CPU 也要在运行时读取这些元数据。

### 2. C 语言：去掉对象头，但编译器也不管安全

C 语言去掉了运行时的对象头，内存紧凑。但它的类型几乎只管「占几个字节、怎么算偏移」；至于指针归谁释放、有没有悬空、能不能同时修改，类型系统一概不知，全靠写代码的人自己在脑子里记。

### 3. Rust：把信息搬进编译期，检查后彻底擦除

在 Rust 中，堆上的 `"hello"` 就是干干净净的 5 个字符字节，栈上的 `i32` 就是干干净净的 4 个整数字节——**运行时内存里没有任何对象头，也没有任何标记「能不能修改、归谁释放、活多久」的附加位。**

那些为了安全和抽象所必需的信息去哪了？全部转移到了编译器在**编译期**维护的**编译期类型实体**里（在接下来的章节中，只要没有跨语言对比的歧义，我们都将其简称为**类型实体**）。

编译器在编译阶段利用这些富信息完成借用检查、权限核对与方法地址绑定；一旦检查通过、生成机器码的那一刻，**整套类型实体被彻底擦除**，留给 CPU 的只剩下最纯粹的裸字节和直接的机器指令。

（如果你好奇 Python、Java、Go、C/C++ 与 Rust 在这套物理布局上的完整横向解剖，可选读[附录：从「一切皆对象」到「一切皆类型」](/appendix/comparisons/objects-to-types/)；关于 Rust 如何将 Java `class` 的六项职责拆回独立零件，也可参阅[附录：没有 `class` 的对象感](/appendix/comparisons/oop/)。）

<Aside type="note" title="什么时候信息不得不留到运行时？">
「编译后彻底擦除类型信息」是 Rust 的默认常态。只有当你在代码里遇到**编译期实在算不出来**的信息时（比如第 4 章要讲的长度在运行时才确定的切片 `&[T]`，或第 8 章要在运行时动态决定调用哪个方法的 `dyn Trait`），Rust 才会把那一点点缺失的信息（长度 `len` 或虚表指针 `vtable`）显式地塞进指针里。即便如此，数据本体依然没有对象头。
</Aside>

## 小结与下一个问题

这一节立住了整个第二篇的基础判断：

1. **在 Rust 中一切皆 Type**：没有 `class` 与基本类型的割裂，`i32`、`String`、`&String`、`&mut i32` 都是独立的**编译期类型实体**（以下简称**类型实体**）；
2. **类型实体 = 物理表示 + 行为与安全约束**：表示决定内存怎么排，约束决定能调什么方法、走 `Copy` 还是移动、能不能改、由谁释放；
3. **信息从运行时搬到了编译期**：Rust 不靠运行时的堆对象头记录类型元数据，而是把表示与约束装进类型实体，核对完毕后在生成机器码时擦除——这就是零成本抽象的物理来源。

但顺着第 1 条往下想，一个让人好奇的问题马上就冒出来了：

既然 `String`、`&String`、`&mut String` 是**三个完全不同的类型实体**，那当我们自己在代码里写下 `struct User` 定义一个新结构体时，我们明明只定义了 `User` 这一个类型——**请问 `&User` 和 `&mut User` 这两个类型实体，是在什么时候、由谁定义出来的？**
