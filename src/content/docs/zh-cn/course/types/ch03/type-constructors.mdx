回答「`&User` 这个类型实体是由谁放进编译期类型表的」之前，需要先把一个前提确认清楚：**在 Rust 中，`T`、`&T`、`&mut T` 不是「一个类型加两种借用修饰符」，而是三个独立的类型，在编译期类型表中对应各自独立的类型实体。**

## `User`、`&User`、`&mut User` 是三个独立的类型

刚学完借用、或有 C / C++ 背景的开发者，看到下面代码里的 `User`、`&User`、`&mut User` 时，往往会以为这里自始至终只有一个类型 `User`，前面的 `&` 和 `&mut` 只是贴在 `User` 上的访问修饰符（类似 C 语言里的 `const`）。

先看一段定义并使用结构体 `User` 的代码（`struct User { id: i32 }` 定义了一个只含单个整数字段 `id` 的类型，通过 `.` 访问字段；完整语法可随时查阅附录「[`struct`、`enum` 与 `match` 语法](/appendix/basics/custom-types/)」）：

在编译器的**编译期类型表**里，`User`、`r` 对应的 `&User` 以及 `m` 对应的 `&mut User` 是三个平级、互不隶属的类型实体，差异就像 `i32` 与 `String` 一样明确：

| 类型实体 | 栈上物理表示 | 是否实现 `Copy` | 允许的操作、有效区间与职责 |
| --- | --- | --- | --- |
| **`User`** | 4 字节（直接存放 `id: i32`） | 否（默认未实现，赋值即移动） | 持有所有权，无借用区间，离开作用域时负责释放 |
| **`&User`（绑定 `r` 的区间）** | 8 字节（存放 `User` 的栈地址） | **是**（可按位复制） | 只读借用视图，受限于 `r` 的有效区间，不承担释放责任 |
| **`&mut User`（绑定 `m` 的区间）** | 8 字节（存放 `User` 的栈地址） | **否**（赋值即移动） | 独占可变视图，允许修改字段，受限于 `m` 的有效区间，不承担释放责任 |

如果取消代码中 `// let r2: &mut User = &u;` 这一行的注释，将 `&User` 赋给类型为 `&mut User` 的变量，编译器报出的不是修饰符警告，而是直接的**类型不匹配（`error[E0308]: mismatched types`）**——编译器查表发现两侧对应的是两个不同的类型实体。

认清这一点后，上一节末尾的问题就摆在了台面上：回看 `on-demand-type.rs` 前三行，源码只写过 `struct User`，初始只在编译期类型表里放进了 `User` 这一个类型实体。`&User` 和 `&mut User` 这两个新类型实体，是由谁生成的，又在什么时候入表？

## 编译期按需生成：类型构造器

标准库和编译器不可能预先把所有自定义结构体（包括你刚命名的 `User`）以及各种借用区间的引用类型实体提前填好。编译器在类型表之外，内置了一套按需生产新类型实体的模板机制——**类型构造器（Type Constructor）**。

以 `&` 和 `&mut` 为例：

- `&` 和 `&mut` 本身不在编译期类型表里，还不是可以直接用来声明变量的类型实体，而是两个内置的**类型构造器**；
- 如果整个程序只用了 `User`、从未写过 `&User`，编译期类型表里就始终只有 `User` 这一个类型实体，不会生成 `&User`；
- 当编译器扫描源码、第一次遇到 `r: &User`（借用表达式 `&u`）时，才会调用 `&` 构造器，将 `r` 的**具体有效区间**与目标类型 **`User`** 一并作为编译期参数填入，按 `&` 自己的规则重写物理表示与安全约束，在编译期类型表里**按需生成并存入**一个全新的类型实体。遇到 `m: &mut User` 时同理，由 `&mut` 构造器生成第三个类型实体。

## 生成公式与三类编译期参数

在工程标准术语里，像 `User`、`Vec<i32>` 或绑定了有效区间的 `&User` 这样填满参数、入表成为独立类型实体的产物，统称为**具体类型（Concrete Type）**。Rust 生成复合类型的规则可以写成一个公式：

**类型构造器 + 编译期参数 → 具体类型（编译期类型表中的独立类型实体）**

尚未填满编译期参数的类型构造器还停留在模板阶段，编译期类型表里没有对应的类型实体，不能直接作为变量的类型标注。用标准库的动态数组构造器 `Vec` 验证这一点：

在 Rust 中，类型构造器可以接收三类编译期参数：

### 1. 类型参数（`T`）

最常见的参数是另一个类型。例如将 `i32` 或 `String` 填入 `Vec<T>`，分别合成 `Vec<i32>` 与 `Vec<String>`；将 `User` 填入引用构造器 `&T`，合成 `&User`。

### 2. 编译期常量参数（`N`）

构造器的参数位不仅能接收类型，还能接收编译期已知的常量数值。典型代表是定长数组构造器 `[T; N]`（`[1, 2, 3]` 创建数组，`a[0]` 读取首元素）：

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/array-const-param.rs</code></small>
<Code code={arrayConst} lang="rust" />

`[i32; 3]` 与 `[i32; 4]` 填入的长度常量不同，生成的就是**两个不同的类型**（栈上分别占 12 字节与 16 字节）。取消 `// let c: [i32; 3] = b;` 的注释，编译器同样报类型不匹配（`error[E0308]: expected an array with a size of 3, found one with a size of 4`）。

### 3. 生命周期参数（无名有效区间与参数名 `'a`）

回想[悬垂引用](/memory/lifetimes/)中见过的现象：外层变量 `r_outer` 与内层代码块里的 `r_inner`，在源码里表面都写作 `: &String`，为什么把内层借用赋给外层变量会被编译器拦截？

对照前两类参数，就能看清引用构造器 `&` 接收的实际参数：类型槽位 `T` 填入的是具体类型 `String`，常量槽位 `N` 填入的是具体数值 `3`；而 `&` 构造器的区间槽位，**实际填入的是一份由编译器测算出的不具名区间数据（描述这次借用在源码哪一段范围内有效），单引号开头的 `'a`（如 `&'a String`）只是给这份区间数据起的参数名。**

与 `String` 或数字 `3` 不同，源码里没有描述「第 4 行到第 9 行」的区间字面量。写下 `r_outer: &String` 与 `r_inner: &String` 时，编译器在内部测算出两份一长一短的无名区间数据，分别填入 `&` 构造器，在编译期类型表里生成了**两个独立的类型实体（两个不同的具体类型）**：

初学时常把「省略 `'a`」误判成编译器藏起了一个默认名字，甚至想在局部变量上补写出 `let r: &'a String = &s;`。从参数命名的角度看，何时写 `'a`、何时不写遵循同一条规则：**只有需要在多处位置指代同一份区间数据时，才需要给它定义名字**。

- **不使用区间名字时无需定义**：局部变量 `r_outer` 的有效区间只在自身这一个引用上生效，不需要跨位置与其他引用核对关联。编译器直接在内部持有这份无名区间数据即可，无需起名——若未提前声明名字就直接写 `let r: &'a String = &s;`，编译器会报未声明的生命周期名错误（`error[E0261]: use of undeclared lifetime name 'a`）。
- **定义了名字却不使用会触发报错或警告**：参数名 `<'a>` 只在函数或结构体定义处声明，用来关联多处引用的有效区间。如果声明了 `<'a>` 却未使用，编译器会直接报错（如结构体上的 `E0392`）或发出未使用警告；即便标在单个函数参数上却没有任何返回值或其他参数复用这个名字，静态检查工具（如 Clippy）也会提示该命名多余。何时需要在函数或结构体上声明 `<'a>`，留到[生命周期的出发点](/pointers/lifetime-origin/)再展开。

## 核心类型构造器一览

后续章节会陆续遇到不同的复合类型写法。按构造语法与机制划分，它们可归为四类，遵循同一套填参生成规则（下表仅作全局路标，各项用法在后续章节逐一展开）：

| 构造器类别 | 常见写法 | 接收的编译期参数 | 生成的具体类型示例 | 主要职责 |
| --- | --- | --- | --- | --- |
| **1. 引用构造器** | `&T`、`&mut T` | 有效区间（无名区间或 `'a`）+ 类型 `T` | `&i32`、`&mut String` | 构造不承担释放责任的共享只读视图或独占可变视图 |
| **2. 数组与切片构造器** | `[T; N]`、`[T]` | 类型 `T` + 常量长度 `N`（或抹去长度） | `[i32; 4]`、`[u8]` | 构造连续排列的同类型元素序列 |
| **3. 元组构造器** | `(T1, T2, ...)` | 零个或多个类型 | `(i32, bool)`、`()` | 将多个类型按固定顺序打包（零个元素即为单元类型 `()`） |
| **4. 泛型结构体与枚举构造器** | `Vec<T>`、`Option<T>`、`Result<T, E>`、`Box<T>` | `<...>` 内的类型、常量或生命周期参数 | `Vec<u8>`、`Option<User>`、`Box<i32>` | 构造容器、分支模型、堆智能指针及自定义复合类型 |

前三类使用各自的专用语法符号（`&`、`[;]`、`()`），第四类则统一通过尖括号 `<...>` 传入编译期参数——无论是动态数组 `Vec<T>`、分支枚举 `Option<T>`，还是堆智能指针 `Box<T>`，在类型系统里都属于泛型 `struct` 或 `enum` 构造器（语言内置构造器与标准库构造器的分界将在下一节拆开）。

## 新类型的约束由谁决定？

将一个类型 `T` 填入类型构造器、在编译期类型表里生成新的类型实体时，有一条关键规则：

**新类型实体里的物理表示与安全约束（占多少字节、能否 `Copy`、能否修改），不是从内部参数 `T` 原样继承的，而是由最外层的类型构造器重新填写的。**

用这条规则核对前文见过的两组反差：

1. **原本未实现 `Copy` 的类型，填入 `&` 构造器后变为可 `Copy`**：`String` 和 `User` 本身未实现 `Copy`（赋值即移动）；但填入只读引用构造器 `&` 后，生成的 `&String` 和 `&User` 不承担释放责任，约束由 `&` 构造器重定为实现 `Copy`（按位复制 8 字节地址，两个变量同时有效）。
2. **原本实现 `Copy` 的类型，填入 `&mut` 构造器后不再实现 `Copy`**：`i32` 是栈上 4 字节整数，实现了 `Copy`；但填入可变引用构造器 `&mut` 后，生成的 `&mut i32` 约束由 `&mut` 构造器重定为未实现 `Copy`，赋值时触发移动（原变量失效，再用报 `E0382`）。

因此，判断一个复合类型在栈上占几个字节、赋值时能否复制、离开作用域要不要释放堆内存，先看最外层是哪个类型构造器，而不是只看最里层的 `T`。

<Aside type="tip" title="标准库导读：带着具体类型视角查阅 reference 文档">
把 `&` 当成修饰符时，很少有人会去翻「引用」的标准库文档。带着「`T`、`&T`、`&mut T` 是三个独立类型」的视角打开标准库的 [`reference` 原生类型页](https://doc.rust-lang.org/std/primitive.reference.html)，翻到 `Trait Implementations` 一栏，本节的两条规则在源码签名里一目了然：

- **外层重写 `Copy`**：标准库直接定义了 `impl<T: ?Sized> Copy for &T`（`?Sized` 表示不定长目标也适用）——它并不要求内部参数 `T` 实现 `Copy`，任何只读引用都由外层 `&` 直接赋予按位复制能力；而在 `&mut T` 名下则没有 `Copy` 与 `Clone` 的实现。
- **独立挂载行为**：诸如相等比较（`PartialEq`）或调试打印（`Debug`）等能力，在文档里都能看到 `for &T` 与 `for &mut T` 两份各自独立的实现——因为它们在编译器里本来就是两个不同的类型。
</Aside>

## 小结与下一个问题

本节确立了三个判断：

1. **三个独立的类型**：`T`、`&T`、`&mut T` 不是同一类型加修饰符，而是在编译期类型表中对应三个独立类型实体的不同类型；
2. **按需入表公式**：「类型构造器 + 编译期参数（类型 / 常量 / 有效区间）→ 具体类型（类型实体）」，编译器遇到对应写法时按需往编译期类型表生成新实体，未填满参数的构造器不在类型表里，不能直接作为变量类型（报 `E0107`）；
3. **外层重写约束**：新类型实体中的物理表示与安全约束由最外层构造器重新填写。

「类型构造器 → 具体类型」是贯穿本篇的主线视角。后续遇到的 16 字节胖指针（`&[T]` 与 `&dyn Trait`）、方法接收者三件套（`self` / `&self` / `&mut self`）以及 `for` 循环的三种遍历方式，都可以顺着这一公式直接推出。
