学完 `Option<T>` 与 `Result<T, E>` 的底层机制后，我们把视角切换到真实的日常开发与代码审查（Code Review）。

几乎每一位从 Java、Python、Go 或 JavaScript 转向 Rust 的开发者，在刚写了几百行带 `Option` 和 `Result` 的业务代码后，都会遇到两个非语法层面的困惑：
1. **表达力之困**：「怎么走一步就要拆一次 `Option` 或 `Result`，写代码像剥洋葱一样繁琐？是不是 Rust 为了安全把编码体验搞得太复杂了？」
2. **边界之困**：「既然 `v.get(i)` 返回 `Option` 这么安全，为什么 Rust 还保留了一越界就当场崩溃（`panic!`）的 `v[i]`？到底什么时候该返回 `Result` / `Option`，什么时候该直接 `panic!`？」

作为第 6 章（也是整个第二篇「类型与数据」）的收官课，本节一次性把这两个工程难题彻底算清。

## 直面初学者的烦躁：安全 vs 表达力的取舍与破局

先回答第一个问题：**为什么初学者刚写 Rust 时，常常被满屏的 `Option` 和 `Result` 搞得心浮气躁？**

不妨回到我们在[第 1 章第 1 节：困难三角](/memory/hard-triangle/)建立的分析框架——**性能、安全与表达力三者的相互拉扯**。

在 6.3 和 6.4 节中我们已经证明，依靠栈上内联枚举与空位优化（Niche），`Option` 和 `Result` 在**「安全 ↔ 性能」**这条边上没有付出运行时开销；那么，把空值与错误检查全部前移到编译期，代价落在了哪里？**就落在了「安全 ↔ 表达力（写代码那一刻的即刻摩擦感）」这条边上。**

在其他语言里，你写一行 `user.profile.city` 或 `parseInt(raw) + 1` 之所以觉得顺畅，是因为语言允许你在写代码的那一刻**「先假装每一层都有值、每一步都成功」**，把「万一为空、万一报错怎么办」的烂摊子推迟到线上运行时。而 Rust 拒绝让你假装：只要一个操作可能缺失或失败，它的返回类型就是 `Option<T>` 或 `Result<T, E>`，编译器逼着你在写下代码的那一秒就必须当场表态。

但为什么度过适应期之后，有经验的 Rust 工程师反而觉得代码比以前更清爽？因为初学者觉得「到处都在拆包」，往往是因为掉进了两个习惯性误区：

### 误区一：患上「防御性包装综合征」，把内部函数参数也全写成了 `Option`

在 Java 或 Go 中，由于任何对象引用或指针天生都可能为 `null` / `nil`，大家习惯了「万事皆可空」。带着这个习惯刚写 Rust 时，很多人会在定义结构体和内部函数时，条件反射地把所有字段和参数统统写成 `Option<String>`、`Option<User>`。结果导致每一个内部函数一上来都在反复解包同一个 `Option`。

**破局心法：把 `Option` / `Result` 挡在系统入口边界，让内部主干享受 100% 有效的红利**。
请记住：在 Rust 里，普通类型 `T` 已经向你承诺了「百分之百有效」。因此：
- **只在真正的系统边界或查询入口使用 `Option` / `Result`**（例如解析外部 HTTP 请求参数、读取配置文件、按 ID 查数据库）；
- 在边界入口处，用上一节学的 **`?` 运算符**或 6.2 节的 **`let Some(user) = ... else { return ...; }`** 一次性完成拦截与拆包，拿到手的就是实打实的 `User`；
- **后续所有的内部核心业务函数，参数直接写 `user: &User`、`amount: u64`**。在这些核心函数里，你既不需要拆 `Option`，也不需要像在 Java 里那样防御性地写满 `if (user == null) throw ...`——整个核心业务层反而比传统语言干净得多。

### 误区二：不知道组合方法，遇到微小的默认值或借用转换也手写四行 `match`

除了上一节学过的 `?` 短路传播，标准库还为 `Option<T>` 和 `Result<T, E>` 提供了一套极其顺手的转换方法。掌握下面这三板斧，能直接省掉你代码里 80% 的手写 `match`。

### 1. 提供回退默认值：`.unwrap_or()` 与 `.unwrap_or_else()`

当你希望「如果是 `Some(v)` / `Ok(v)` 就拿出 `v`，如果是 `None` / `Err(_)` 就退回一个现成的默认值」时，不需要写 `match`，直接调用 **`.unwrap_or(默认值)`**（如第 18 行的 `.unwrap_or("anonymous")`）。
如果默认值的计算成本较高（比如需要调用函数或构造 `String`），则改用传闭包的 **`.unwrap_or_else(|| compute_default())`**，这样只有在真正遇到 `None` 或 `Err` 时才会去计算默认值。

### 2. 只读借用内部值：`.as_ref()`（从 `&Option<T>` 变成 `Option<&T>`）

看第 21 行：当 `Option<String>` 作为结构体字段 `u.name` 存放时，如果你只拿到了结构体的引用，或者你只想调用 `Option` 的辅助方法看一眼里面的字符串、**不想把 `u.name` 里的 `String` 移走（Move）**，直接调 **`u.name.as_ref()`**（对 `Result` 同理）。
它会借用原 `Option`，返回一个全新的轻量级枚举 **`Option<&String>`**——里面装的只是指向原字符串的 8 字节只读引用 `&String`，原字段 `u.name` 完好无损。

### 3. 从可变引用中合法抽走所有权：`.take()`（原地留下 `None`）

再看第 25 行，这解决了一个非常经典的借用检查难题：
假设你写了一个修改用户的方法 `fn clear_name(&mut self) -> Option<String>`，手里只有可变借用 **`&mut User`**，但你想把 `u.name` 里面的 `String` **移走拿出来**交给别处。
我们在第 5 章 5.3 节学过，编译器严禁通过引用（哪怕是 `&mut`）直接把字段的值移走（报 `E0507`），因为一旦移走，`User` 结构体的 `name` 字段就变成未初始化的内存空洞了。

怎么在不破坏 `User` 完整性的前提下把里面的 `String` 拿走？
答案是在拿走 `Some(String)` 的同一瞬间，往原字段里塞回一个合法的替补值——而 `Option` 恰好就有一个现成且不占堆资源的合法值 **`None`**。
标准库的 **`u.name.take()`** 干的就是这件事：它需要 `&mut Option<T>` 权限，把原本的 `Some("Ferris")` 整个换出来返回给你（赋值给 `taken`），同时把原地 `u.name` 改写成 `None`。所有权顺利到手，而结构体 `u` 的每个字段依然处于合法状态。

| 手里持有的变量 | 你想要达到的目标 | 地道工程写法 |
| --- | --- | --- |
| `Option<T>` / `Result<T, E>` | 为空或失败时回退到默认值 | `opt.unwrap_or(default)` |
| `&Option<String>`（只读借用） | 只读借用里面的数据，不移走原值 | `opt.as_ref()`（产出 `Option<&String>`） |
| `&mut Option<String>`（可变借用） | 把里面的 `String` 所有权抽走，原位置空 | `opt.take()`（产出 `Option<String>`，原地留 `None`） |

## 终极边界：什么时候返回 `Result` / `Option`，什么时候直接 `panic!`？

现在回答开头提出的第二个核心问题：**既然 `Option` 和 `Result` 能把失败写进类型签名，为什么数组下标访问 `v[i]` 在越界时没有返回 `Option<&T>`，而是直接触发 `panic!` 停下程序？**

试想一下：如果语言规定每一次写 `v[i]`、每一次做整数加法 `a + b`（可能溢出）都强制返回 `Option` 或 `Result`，会发生什么？
在一段普通的循环代码 `for i in 0..v.len() { sum += v[i]; }` 里，下标 `i` 明明是你刚刚根据 `v.len()` 算出来的，百分之百不可能越界；如果编译器依然逼你在每一行 `v[i]` 后面写 `.unwrap()` 或 `match`，那所有正确的业务代码都会被毫无意义的拆包噪声彻底淹没。

### 1. 可预期的环境与输入失败 → 返回 `Result<T, E>` 或 `Option<T>`

当失败是由**程序外部的客观世界**引起的——比如用户输入的字符串不是合法数字、要打开的配置文件不存在、网络请求超时、或者用外部传入的未知索引去查元素（如第 10 行调用 **`v.get(i)`** 返回 `Option<&i32>`）——哪怕你的代码写得再完美，这些情况在线上也一定会发生。
对于这类**可恢复的预期内失败**，必须返回 `Result` 或 `Option`，把决定权写进函数签名交给调用方（提示用户重输、走降级逻辑或向上 `?` 传播）。

### 2. 程序内部契约被打破（Bug） → 直接 `panic!` 当场止损

当失败意味着**程序员自己写错了代码逻辑（违反了前置契约或内部不变量 Invariant）**——比如用 **`v[i]`** 访问数组却发生了越界（取消第 11 行注释会在运行时直接 `panic: index out of bounds`）、或者除数为 `0`——这说明程序内部的状态已经出现了 Bug。
此时继续往下跑只会污染数据甚至造成安全事故，调用方也无法在运行时替你修好代码里的 Bug。因此最安全的做法就是**当场触发 `panic!`**，打印出错行号与调用栈，清理当前线程栈上的所有局部变量并立即停下。

| 维度 | 可恢复错误：`Result<T, E>` / `Option<T>` | 不可恢复错误（程序 Bug）：`panic!` |
| --- | --- | --- |
| **问题根源** | **外部输入或运行环境**（用户输错、文件缺失、网络断开、未查到记录） | **代码自身的逻辑缺陷**（下标计算越界、内部不变量契约被打破） |
| **调用方能否处理？** | **能，且必须处理**（重试、返回错误码、提供默认值） | **不能**（属于需要程序员修代码、发版修复的 Bug） |
| **代表 API 对照** | `v.get(i)`、`str::parse()`、`File::open()` | `v[i]`、`assert!()`、越界切片 `&s[0..99]` |

## 代码审查（Code Review）红线：如何审视 `.unwrap()` 与 `.expect()`？

连接上述两个世界的桥梁，正是我们在前面提过的 **`.unwrap()`** 与 **`.expect("说明")`**。
它们的作用只有一句话：**把一个原本可恢复的 `Option` 或 `Result`，强行转换成「如果是 `None` 或 `Err` 就当场 `panic!`」**。

在日常编写代码或审查（尤其是审查 AI 生成的 Rust 代码）时，请守住以下三条铁律：

1. **生产业务主干严禁对外部数据裸调 `.unwrap()`**：
   AI 编写代码时为了省事，极易在解析网络请求、读取文件或字典查找后直接接 `.unwrap()`。一旦线上收到一条畸形请求，整个服务线程就会当场 `panic` 崩溃。在 Code Review 中看到这类 `.unwrap()`，一律要求改为 `?` 传播、`let ... else` 提前返回或 `.unwrap_or` 默认值。
2. **当人类比编译器更确信「这里绝不可能失败」时，用 `.expect("不变量原因")` 替代 `.unwrap()`**：
   看 `panic-or-option.rs` 的第 13 行：
   ```rust
   let n: i32 = "42".parse().expect("a literal we wrote ourselves");
   ```
   `"42"` 是我们自己在源码里硬编码的字面量，它 100% 是合法整数；只是因为 `parse()` 的签名统一返回 `Result`，编译器不知道 `"42"` 不会失败。在这种**「一旦失败就说明代码本身写错了」**的场景下，调用 `.expect(...)` 是完全合理的——并且要把参数写成一句说明「为什么这里必定成功」的契约注释。
3. **测试代码与原型脚本可以放宽**：
   在单元测试（`#[test]`）或一次性验证脚本中，为了在出错时第一时间让测试挂掉，可以直接使用 `.unwrap()` 或 `?`。

## 小结

1. **用架构边界化解拆包繁琐**：在系统入口边界用 `?` 或 `let else` 拦截并拆开 `Option` / `Result`，在内部核心业务函数中直接传递 100% 有效的普通类型 `T`，即可同时兼顾编译期安全与主干代码的整洁。
2. **善用三板斧省去样板 `match`**：回退默认值用 `.unwrap_or()`，隔着引用只读借用用 `.as_ref()`，从可变引用中抽走所有权并原地留 `None` 用 `.take()`。
3. **划清 `Result` 与 `panic!` 的工程边界**：外部环境或输入引起的预期内失败一律用 `Result` / `Option` 写进签名；程序内部契约被打破（Bug）用 `panic!` 当场止损；生产业务代码中拒绝无脑 `.unwrap()`，仅在证明内部不变量成立时使用 `.expect()`。

### 动手核对与小练习

1. **Code Review 裁决**：审查下面两处使用 `.unwrap()` / `.expect()` 的代码，判断哪一处是合理的，哪一处存在线上崩溃隐患并应如何修改：
   - **代码 A**：在程序启动时编译一条固定的正则表达式字面量 `Regex::new(r"^\d{4}-\d{2}-\d{2}$").expect("hardcoded date regex must be valid")`。
   - **代码 B**：在 Web 后端接口中读取用户请求头 `let token = req.headers.get("Authorization").unwrap();`。
2. **综合重构练习**：下面这段函数试图从配置结构体 `&mut Config` 中取走一次性密钥 `one_time_key: Option<String>`，解析为数字后再加上偏移量返回，但写得非常繁琐且第 6 行因隔着可变引用移出字段无法编译。请结合 `.take()` 与 `?` 运算符，将整个函数体精简为 2～3 行平铺代码：
   ```rust
   use std::num::ParseIntError;

   struct Config {
       one_time_key: Option<String>,
   }

   fn consume_and_parse(cfg: &mut Config) -> Result<u64, ParseIntError> {
       // 直接 match cfg.one_time_key 会报 E0507！
       let raw = match cfg.one_time_key {
           Some(s) => s,
           None => String::from("0"),
       };
       let num = match raw.parse::<u64>() {
           Ok(n) => n,
           Err(e) => return Err(e),
       };
       Ok(num + 100)
   }
   ```

1. **Code Review 裁决**：
   - **代码 A 合理**：正则表达式字符串是源码里写死的常量，其合法性属于程序内部不变量（若写错应在启动时立刻暴露给开发者修复），使用 `.expect()` 恰当。
   - **代码 B 存在严重隐患**：客户端发来的 HTTP 请求完全可能不带 `Authorization` 请求头，这属于外部输入缺失，裸调 `.unwrap()` 会导致任何未登录请求直接炸毁处理线程。应改为 `let Some(token) = req.headers.get("Authorization") else { return Err(AuthError::MissingToken); };`。
2. **用 `.take()` + `.unwrap_or_default()` + `?` 精简重构**：
   ```rust
   fn consume_and_parse(cfg: &mut Config) -> Result<u64, ParseIntError> {
       let raw = cfg.one_time_key.take().unwrap_or(String::from("0"));
       let num = raw.parse::<u64>()?;
       Ok(num + 100)
   }
   ```
   - `cfg.one_time_key.take()` 将 `Some(String)` 抽走并在原地留下 `None`，化解了 `E0507`；
   - `.unwrap_or(...)` 一行替代了第一个手写 `match`；
   - `raw.parse::<u64>()?` 一行替代了第二个向上传播错误的手写 `match`。
