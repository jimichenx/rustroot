上一节的 `Option<T>` 处理了「查到 `Some(T)` 或查不到 `None`」的场景。而在解析用户输入 `"forty-two"`、打开配置文件或发起网络请求时，一旦操作失败，调用方不仅需要知道没拿到结果，还必须获知**失败的具体原因**（格式非法、文件缺失还是权限不足）。

## 为什么不用 `try / catch` 异常

在 Java、Python 或 C++ 中，这类失败通常通过抛出异常（Exception）处理：函数签名照常写返回 `int`，遇到错误时中断正常返回路径，沿调用栈向上跳转寻找 `try / catch`：

```java
int n = Integer.parseInt(input);
```

用审视 `null` 的同一套标准衡量，非受检异常（Unchecked Exception）存在两处同样的签名缺口：

1. **返回签名隐瞒了失败分支**：单看 `int parseInt(String s)`，调用方看不出该函数可能失败，也看不出可能抛出哪些异常；
2. **控制流隐式跳转**：任意一行普通调用都可能中途跳出当前函数，编译器无法强制调用方处理错误分支。

既然「成功产出 `T`」与「失败给出原因 `E`」是同一次调用的两种互斥结果，Rust 直接用和类型把两者并列写进函数返回签名。

## 用 `Result<T, E>` 声明成败

标准库定义了双参数泛型枚举 **`Result<T, E>`**（及变体 **`Ok`**、**`Err`**，同样已由 Prelude 默认导入）：

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

- 当函数成功返回计算结果、失败返回错误原因时，签名写为 `Result<i32, ParseIntError>`；
- 当函数只需执行动作而无业务返回值（对应[函数、元组与表达式](/types/functions-and-expressions/)中的单元类型 `()`）、但执行可能失败时，签名写为 **`Result<(), std::io::Error>`**——成功返回 `Ok(())`，失败返回 `Err(e)`。

<Aside type="caution" title="#[must_use] 防止静默丢弃错误">
对于返回 `Result<(), io::Error>` 的写入操作，调用方会不会干脆不接收返回值而忽略错误？标准库在 `Result` 定义上标注了 **`#[must_use]`** 属性：若单写一行 `text.parse::<i32>();` 不做任何处理，编译器会发出 `warning: unused Result that must be used` 警告提醒漏判。
</Aside>

## 用 `?` 运算符传播错误

在实际调用链中，中间函数遇到错误时往往无法自行恢复，需要将错误向上返回给调用方。若只用手写 `match` 传播两次解析错误，代码会写成：

### `?` 的编译期 `match` 展开

<span class="rr-keypoint">`?` 并非隐式异常机制，它在编译期直接展开为带提前 `return` 的 `match` 分支：</span>

```rust
let x = match a.parse::<i32>() {
    Ok(n) => n,
    Err(e) => return Err(From::from(e)),
};
```

遇到 `Ok(n)` 解包赋给 `x` 继续向下执行；遇到 `Err(e)` 则立即从当前函数 `return` 返回错误。

### 在 `Option` 上链式短路

在返回类型为 `Option<...>` 的函数中，`?` 同样可以直接作用于 `Option` 值——遇到 `Some(v)` 解包继续访问下一层，遇到 `None` 当场展开为 `return None;`：

## `?` 的两条返回签名约束

因为 `expr?` 会展开出针对当前所在函数的 `return Err(...)` 或 `return None;`，它直接受当前函数返回类型的约束：

### 函数返回类型必须兼容

在返回 `()` 或普通整数 `u16` 的函数（如默认的 `fn main()`）内使用 `?`，展开出的 `return Err(e)` 会与返回签名冲突并触发 `error[E0277]`（`the ? operator can only be used in a function that returns Result or Option`）。同理，也不能在返回 `Result` 的函数里直接对 `Option` 用 `?`，需先调 `.ok_or(err)?` 将 `Option` 转为 `Result`。

### 错误类型必须一致或可转换

若函数内先后调用了返回 `std::io::Error` 与 `ParseIntError` 的两步操作，而返回签名只写了 `Result<i32, ParseIntError>`：

```text
error[E0277]: `?` couldn't convert the error to `ParseIntError`
 --> types/result-and-panic/src/bin/mixed-errors.rs:5:47
  |
4 | fn read_number(input: &str) -> Result<i32, ParseIntError> {
  |                                -------------------------- expected `ParseIntError` because of this
5 |     let input = std::fs::read_to_string(input)?;
```

标准库未定义从 `io::Error` 到 `ParseIntError` 的自动转换（`From` 转换契约与跨模块错误归并将在[转换契约与一揽子实现](/abstraction/conversions-and-from/)中展开；当前阶段也可用 `.map_err(|e| e.to_string())?` 显式转为统一的错误类型）。
