空引用（`null`）发明者 Tony Hoare 曾将其称为「十亿美元的错误」——在 Java、C / C++ 或 Go 中，`NullPointerException`、`nil` 解引用与段错误长期占据线上崩溃榜首。Rust 取消了 `null` 关键字，仅靠前两节建立的和类型与穷尽匹配，就在编译期消除了空指针解引用，同时没有增加额外指针字节。

## 为什么 `null` 是类型缺陷

考虑按用户名查询资料的函数 `find_user(name)`。结果存在两种互斥可能性：查到有效 `User`，**或**查无此人。按和类型的定义，这本应表达为 `User | 无结果`。

但在 Java、C++ 或 Go（指针）中，语言将空地址 `null` 隐式混入了每一个引用或指针类型：

```java
User u = findUser("Ferris");
System.out.println(u.name);
```

用[类型的两面](/types/representation-and-constraints/)与前两节的模型审视这两行代码，问题出在两处：

1. **签名将和类型伪装成单一类型**：返回类型写着 `User`，运行时实际返回的却是 `User | null`；
2. **编译器无法强制穷尽检查**：因为任何 `User` 引用都可能为空，编译器看到 `u.name` 时无法区分「此处已经判空」与「漏了判空」，只能放行编译，等运行时遇到空值才崩溃。

<Aside type="note" title="为什么 Java 8 的 Optional<T> 无法根治空指针？">
Java 8 虽然在标准库补入了 `Optional<User>`，但底层并未移除 `null`：普通 `User` 引用依然随时可能为空，连 `Optional<User>` 变量本身都能被赋为 `null`；此外 JVM 中的 `Optional` 是独立的堆包装对象，每次返回还需承担额外的对象头分配与二次指针跳转。
</Aside>

## 用 `Option<T>` 显式编码缺失

Rust 通过两条互补规则切开了这种含混状态：

1. **普通类型 `T` 始终持有有效值**：语言内不存在 `null`。只要变量或参数写着 `u32`、`String`、`User` 或 `&User`，编译期就保证其中存有已初始化的有效数据，可直接访问字段而无需写防御性判空；
2. **可能缺失时显式套上 `Option<T>`**：当业务结果确实可能为空时，使用标准库定义的普通泛型枚举 **`Option<T>`**（及其变体 **`Some`**、**`None`**，均已由 Prelude 默认导入作用域）：

```rust
enum Option<T> {
    None,
    Some(T),
}
```

## 空位优化：为什么 `Option<&T>` 仍占 8 字节

按[从常量枚举到代数数据类型](/types/enums-and-adt/)拆解的「判别式标签 + 共享载荷区」布局，8 字节的 `&i32` 套上 `Option` 后似乎应该外加 1 字节标签并对齐填充到 16 字节。运行下面这段程序实测 `u32`、`&i32` 与 `String` 套上 `Option` 前后的字节大小：

<small class="code-source">源文件：<code>examples/types/enum-option-match/src/bin/option-ref-size.rs</code></small>
<Code code={optionRefSize} lang="rust" />

<small class="code-source">运行输出（64 位平台）</small>
```text
u32: 4B -> Option<u32>: 8B
&i32: 8B -> Option<&i32>: 8B
String: 24B -> Option<String>: 24B
```

`Option<u32>` 从 `4B` 变成了 `8B`（4 字节整数 + 1 字节标签 + 3 字节对齐填充），但 **`Option<&i32>` 依然是 `8B`，`Option<String>` 也依然是 `24B`**，没有增加 1 个字节。

差异源于目标类型内部是否存在永远不会出现的**非法位模式（空位，Niche）**：

1. **`u32` 没有空位**：4 字节共 \(2^{32}\) 种位组合，从 `0` 到 `4,294,967,295` 每一种都是合法整数，编译器只能在外部另加标签字节区分 `Some` 与 `None`；
2. **`&i32` 与 `String` 拥有全 `0` 空位**：在[引用](/memory/references/)中确立过，合法引用 `&T` 必须指向有效数据，绝不可能是全 `0` 地址（`0x0000...`）。编译器直接利用这个闲置的全 `0` 位模式表示 `None`，非零地址表示 `Some(&i32)`；同理，`String`（及 `Vec<T>`）的 24 字节控制头首字段也是非空堆指针，编译器顺着字段找到该空位表示 `None`，使 `Option<String>` 保持 **24 字节**。

这项由编译器自动完成的布局压缩称为**空位优化（Niche Optimization）**。<span class="rr-keypoint">运行时内存中，`Option<&T>` 与 C 语言可能为 `NULL` 的指针同样占 8 字节、判空同样只是一条判零指令，但编译期通过独立类型隔离了空值，消除了未经检查解引用空指针的可能。</span>（注意若再套一层写成 `Option<Option<&i32>>`，内层 `None` 已占用了唯一的全 `0` 空位，外层 `Option` 便需额外加标签并对齐到 16 字节。）

<Aside type="tip" title="还有哪些类型支持空位优化？">
除引用、`String`、`Vec<T>` 与 `Box<T>` 外，`bool`、`char`、非零整数 `NonZeroU32` 等含有非法位模式的类型均可触发空位优化；完整实测对照与失效条件见附录「[niche 优化](/appendix/mechanisms/niche/)」。
</Aside>

`Option<T>` 表达了无需说明原因的「有值或缺失」。而当解析文本、读写文件或发起网络请求失败时，调用方还必须拿到具体的失败原因并向上层传递——下一节进入携带错误数据的 `Result<T, E>` 与 `?` 短路传播。
