上一章用结构体（`struct`）把多个**同时存在**的字段打包成一个所有权单元（积类型 Product Type）。但在真实业务中，数据建模还有另一半需求：**表达「一个类型存在几种互斥的合法可能性（或关系）」**。

在 C / C++ 或早期 Java 中，枚举常被当作普通的具名整数常量表；而在 Rust 中，**`enum`（枚举）**是代数数据类型（ADT）中的**和类型（Sum Type）**。仅靠这一项基础机制与标准库的两个泛型枚举，Rust 便在编译期统一解决了空指针（`Option<T>`）与错误处理（`Result<T, E>`）两类高频事故。

本章分五步推进：

- **从常量枚举到代数数据类型（ADT）**：对比用结构体加标志位拼凑、面向对象用「父类 + 子类」模拟和类型的局限，拆解 Rust `enum` 如何在编译期闭合全部合法可能性，并在固定长度的栈内存中通过判别式标签与共享载荷区存放不同分支的数据。
- **模式匹配与编译期穷尽性检查**：从 `let 模式 = 表达式;` 出发打通积类型与和类型的解构规则，厘清 `match`、`if let` 与 `let else` 的分工，并核对模式绑定中的移动与借用流向。
- **消灭空指针（`Option<T>` 与空位优化）**：说明为什么隐式 `null` 会破坏类型约束，理解 `Option<T>` 如何将「可能缺失」隔离为独立的类型，并验证为什么 `Option<&T>` 在运行时仍只占 8 字节。
- **错误即数据（`Result<T, E>` 与 `?` 短路传播）**：将成功结果与失败原因并列写进函数返回签名，拆解后缀 `?` 运算符在编译期展开为 `match` 提前返回的机制与签名限制。
- **工程表达力与 `panic!` 边界**：确立「系统边界拆包、内部传递有效值」的分层原则，掌握 `unwrap_or`、`as_ref` 与 `take` 的转换用法，划清返回 `Result` 与触发 `panic!`（及 `.unwrap()` / `.expect()`）的审查边界。

读完本章，你应当能独立回答以下问题：

1. 面向对象用「父类 + 子类」表达互斥分支时存在哪些边界缺陷？在内存中，一个带载荷 `enum` 的字节大小由什么决定？
2. 为什么元组和结构体可以直接写 `let (a, b) = pair;` 解构，而对枚举单写 `let Role::Member(p) = role;` 会编译失败？`match`、`if let` 和 `let else` 分别如何处理未命中的分支？
3. 为什么 `size_of::<Option<u32>>()` 比 `u32` 大，而 `size_of::<Option<&i32>>()` 和 `size_of::<Option<String>>()` 却与原类型相等？
4. `?` 运算符在编译期展开成了什么代码？审查业务代码时，何时应当拒绝 `.unwrap()`，何时可以使用 `.expect()`？
