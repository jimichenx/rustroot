在 C、C++ 或早期 Java 中，**`enum`（枚举）**通常只是一组具名整数常量（如星期一到星期日）。而在 Rust 中，`enum` 与[结构体（`struct`）](/types/structs/)并列构成**代数数据类型（Algebraic Data Types，简称 ADT）**——日常高频使用的空值表示 `Option<T>` 与错误表示 `Result<T, E>`，均是用普通 `enum` 定义出来的库类型。

理解这项设计，先从数据建模如何表达**「或关系」**说起。

## 数据建模的「与」和「或」

结构体把多个**同时存在**的字段打包在一起（如账号同时拥有用户名且拥有注册时间），表达逻辑上的**「与关系（AND）」**。

真实业务中还有另一类相反的数据形态——**「或关系（OR，多选一）」**：一个类型存在几种互斥的合法可能性，同一时刻只能处于其中一种，且**每种可能性携带的数据各不相同**。例如权限系统中的用户角色只有三种合法状态：

1. **未登录访客（`Guest`）**：无附加属性；
2. **普通会员（`Member`）**：持有会员积分 `vip_points: u64`；
3. **管理员（`Admin`）**：持有部门编号 `dept_id: u64` 与安全密钥 `security_key: u64`。

类型理论将这种表达「有限可能性多选一」的类型称为**和类型（Sum Type）**。如果不使用原生 `enum`，传统工程通常只有两条替代路线。

## 结构体拼凑与子类继承的局限

### 结构体加标志位

<small class="code-source">运行输出</small>
```text

```

用「与关系」拼凑「或关系」直接暴露了三处缺陷：

1. **被迫填入占位假数据**：创建普通会员（`role_tag: 1`）时，仍必须为管理员专属的 `dept_id` 和 `security_key` 填入无意义的初值；
2. **编译器拦不住跨分支误读**：代码已进入 `user.role_tag == 1` 分支，依然能直接读取管理员的 `user.security_key`；
3. **内存冗余**：哪怕当前是无附加数据的访客（`role_tag: 0`），每个实例仍要在栈上并排携带全部四个字段。

### 父类与子类继承

在 Java 或 C++ 等面向对象（OOP）语言中，标准做法是定义抽象基类 `Role`，再派生出 `Guest`、`Member`、`Admin` 三个子类（Subclass），各自持有专属字段：

```java
abstract class Role {}
class Guest extends Role {}
class Member extends Role { long vipPoints; }
class Admin extends Role { long deptId; long securityKey; }
```

OOP 的子类继承同样在尝试表达和类型，但在编译期约束与内存布局上留有三处短板：

1. **可能性集合默认敞开**：继承树默认允许在任意模块继续新增 `class Hacker extends Role`，编译器不知道 `Role` 共有几种子类，用 `instanceof` 分支处理漏掉 `Admin` 时无法报错（直到 Java 17 引入 `sealed class` 密封类才补上闭合限制）；
2. **拆碎成多个独立类型**：`Member` 和 `Admin` 是不同的类，一旦装入 `List<Role>` 就退化为基类 `Role`，读取字段又得依赖运行时类型检查与向下转型（Downcast）；
3. **被迫堆分配与间接寻址**：基类无法预知子类体积，栈上只能存引用指针，实例必须分散分配到堆上并各自附带对象头。

<Aside type="tip" title="跨语言对照">
从 C 的 `union`、C++ 的 `std::variant` 到 Java 的 `sealed class` 与 TypeScript 联合类型，各语言实现和类型的取舍对比可参阅附录「[不同语言如何实现「和类型」](/appendix/comparisons/sum-types/)」。
</Aside>

## 原生和类型 `enum`

Rust 在语言核心直接提供了原生的闭合和类型。我们将 `Role` 的三种合法可能性列在同一个 `enum` 花括号内，每种可能性称为一个**变体（Variant）**，可按需携带专属数据（称为**载荷 Payload**）：

```rust
enum Role {
    Guest,
    Member(u64),
    Admin { dept_id: u64, security_key: u64 },
}
```

三种变体形态与结构体的三种形态一一对应：无载荷的类单元变体 `Guest`、按位置携带数据的类元组变体 `Member(u64)`，以及带具名字段的类结构体变体 `Admin { ... }`。构造实例时统一写 `枚举名::变体名`（如 `Role::Member(500)`）。

## 积类型与和类型

把 `struct` 与 `enum` 合称为**代数数据类型（ADT）**，源于计算合法取值总数时的代数法则。设无载荷枚举 `Direction` 有东、南、西、北 `4` 种可能，`bool` 有 `2` 种可能：

- **`struct` 是积类型（Product Type，`×`）**：`struct MoveCmd { dir: Direction, fast: bool }` 同时持有两个字段，合法状态总数为 **`4 × 2 = 8` 种**。若将原本互斥的字段塞进同一个 `struct`，相乘多出来的组合就是 `BadRole` 那样的非法状态；
- **`enum` 是和类型（Sum Type，`+`）**：`enum Action { Turn(Direction), Sprint(bool), Idle }` 同一时刻只取其一，合法状态总数为各变体相加：**`4 + 2 + 1 = 7` 种**。

| 维度 | 积类型（`struct` / 元组） | 和类型（`enum`） |
| --- | --- | --- |
| **逻辑关系** | **与关系（AND）**：同时持有字段 `A` 且持有字段 `B` | **或关系（OR）**：处于变体 `A` 或处于变体 `B` |
| **合法取值总数** | 各字段可能性**相乘**（`\|A\| × \|B\|`） | 各变体可能性**相加**（`\|A\| + \|B\|`） |
| **建模职责** | 捆绑共同构成一个实体的多项属性 | 收拢互斥的业务角色、状态阶段或成败结果 |

## 标签与共享载荷区

`Guest`（0 字节载荷）、`Member(u64)`（8 字节载荷）与 `Admin`（16 字节载荷）长短不一，而且 `let mut r: Role` 在运行期随时可能从 `Guest` 改赋为 `Admin`。要在不借助堆分配的前提下让 `Role` 拥有编译期固定的栈大小，内存只能按**「判别式标签 + 最大变体共享载荷区」**（底层称带标签联合体 Tagged Union）组织：

对照输出与内存布局图，`Role` 固定的 **24 字节**栈槽位由两段拼成：

1. **判别式标签（Discriminant / Tag）**：记录当前处于第几种变体（`0`、`1`、`2`）。无载荷的 `Direction` 只需 `1B`；而在 `Role` 中，后方 `u64` 载荷要求按 8 字节边界对齐，1 字节标签加上 7 字节对齐填充（Padding）共占前 **`8B`**；
2. **共享载荷区（Shared Payload）**：剩余 **`16B`** 按最大变体 `Admin` 的两个 `u64` 留足，由各变体分时复用——`Guest` 闲置全部 16 字节，`Member` 只用前 8 字节，`Admin` 用满 16 字节。三个实例在栈上均固定占 `24B`，既比并排累加的 `BadRole`（`32B`）紧凑，又省去了堆分配与指针跳转。

<Aside type="caution" title="警惕巨型变体撑大整个枚举">
因为共享载荷区必须迁就**最大的变体**，若某枚举有 9 个变体仅占 8 字节，唯独 1 个罕见变体内含 1024 字节大结构体，所有枚举实例在栈上都会膨胀到千字节以上。审查遇到这类头重脚轻的定义时，可将超大变体的载荷用[单一所有权的堆智能指针 `Box<T>`](/pointers/box-smart-pointer/)移到堆上，使该变体缩回 8 字节指针。
</Aside>

正因为后 16 字节共享载荷区在不同标签下存放着截然不同的数据（甚至处于未初始化闲置状态），编译器绝不允许直接写 `r2.0` 或 `r3.security_key` 读取载荷。如何安全地核对标签并取出内部数据，由下一节的模式匹配解决。
