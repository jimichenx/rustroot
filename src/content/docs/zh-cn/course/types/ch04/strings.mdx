前两节理清了通用连续内存序列 `[T; N]`、`&[T]` 与 `Vec<T>` 的分工。当存放的内容从普通数据变成文本时，日常编码会交替用到两种核心字符串类型：只读借用的**字符串切片 `&str`** 与可增长、独自承担释放责任的**堆字符串 `String`**。

## `&str` 与 `String` 的基本用法

先通过五行的基础操作认识它们的起步写法：

```rust
let literal: &str = "hello";
let mut msg: String = String::from("hello");
msg.push_str(" world");
msg.push('!');
println!("{literal} -> {msg}");
```

对照上面的代码，日常起步把握三点：

- **只读文本用 `&str`**：代码中直接写出的双引号字面量 `"hello"`，类型就是 `&str`。只需读取文本、打印日志或向函数传递只读字符串参数时，直接使用 `&str`；
- **动态修改与独立持有用 `String`**：运行期需要拼接修改或将文本长期保存在结构体中时，用 `String::from("hello")` 从字面量构造（或用 `String::new()` 创建空串），声明为 `let mut` 后调用 `.push_str("...")` 追加字符串切片；
- **区分双引号 `&str` 与单引号 `char`**：Rust 不混用单双引号——双引号 `"..."` 是字符串切片 `&str`，单引号 `'!'` 则是固定占 **4 字节**的单个 Unicode 字符 `char`（见附录「[标量、元组与单元类型](/appendix/basics/scalars-and-tuples/)」），对应调用 `.push('!')` 追加单个字符。

单看创建与追加，写法与其他语言差别不大。但从 Java、Python 或 Go 转向 Rust 时，很快会遇到两处疑问：**为什么其他语言靠一个 `String` 就能包办字面量、子串和拼接，Rust 却要拆出 `&str` 与 `String`？** 以及在处理文本时，**为什么取第 0 个字符写 `s[0]` 会直接编译失败？**

## 为什么需要两种字符串

在 Java 或 Python 中，双引号字面量、截取出的子串与动态拼接结果对外都是同一个 `String` 类型——底层运行时借助堆对象、字符串常量池与垃圾回收器（GC），在幕后包揽了共享与内存回收。

在没有 GC 的 Rust 中，如果只保留唯一一种负责释放堆内存的 `String` 类型，会立即带来两处资源浪费：

1. **写一行固定提示语也要上堆**：`"hello"` 这 5 个字节在编译期已写入可执行文件，若变量类型只能是管理堆块的 `String`，程序每次运行到这里都得去堆上申请内存、复制字节，离开作用域再释放；
2. **只读截取一段子串也要复制**：若只想检查某行百字节日志的前 5 个字符，没有借用视图就意味着每次切子串都必须新开一块堆内存。

要在无 GC 前提下兼顾**「动态生成的文本有明确的堆释放责任人」**与**「读取字面量或局部子串零堆分配、零字节复制」**，就必须将拥有堆缓冲区的容器 `String` 与只借用一段字节的胖指针视图 `&str` 拆成两个独立的类型。

### 内置原生类型 `str` 与标准库结构体 `String`

把前两节的连续内存载体直接映射过来，字符串家族就是在 `[u8]`、`&[u8]`、`Vec<u8>` 之上叠加了一条类型级安全约束：**内部字节序列在任何时刻都必须是合法的 UTF-8 编码。**

| 对应字节载体 | 字符串类型 | 栈上物理表示（64 位） | 底层身份与职责定位 |
| --- | --- | --- | --- |
| **`[u8]`** | **`str`** | 编译期大小未知（**DST**，不可直接上栈） | **语言内置原生类型**：内存中任意一段连续的合法 UTF-8 字节 |
| **`&[u8]`** | **`&str`** | **16 字节胖指针** `(ptr, len)` | **字符串切片引用**（日常简称字符串切片）：不复制字节的只读视图 |
| **`Vec<u8>`** | **`String`** | **24 字节控制头** `(ptr, len, cap)` | **标准库结构体**：拥有并负责释放堆缓冲区，支持动态追加与扩容 |
| **`&Vec<u8>`** | **`&String`** | **8 字节瘦指针** `ptr` | 指向栈上 `String` 控制头的普通只读引用 |

回扣[构造器的组合](/types/type-combinations/)中「语言内置 vs 标准库」的划分，`str` 与 `String` 的实现层次并不对称：

- **`str` 是编译器内置的原生类型（Primitive Type）**：编译器负责解析双引号字面量 `"hello rust"`，在编译期校验 UTF-8 并写入可执行文件的**只读数据段（Read-Only Data Segment）**，同时确定 `&str` 的 16 字节胖指针布局。只读数据段在程序运行全程有效，字面量的完整类型为 **`&'static str`**（`'static` 表示全局有效区间，详见[编译器的幕后逻辑：范围包含关系（型变）与 `'static`](/pointers/lifetime-variance-and-static/)）。而你在 `str` 上调用的 `.len()`、`.trim()`、`.split()` 等方法，全是用普通 Rust 代码写在标准库 `impl str` 块里的；
- **`String` 是标准库定义的普通结构体**：翻开标准库源码，它的定义只有一行私有字段封装 `pub struct String { vec: Vec<u8> }`。<span class="rr-keypoint">`String` 的合法 UTF-8 约束并非编译器特权，而是靠私有字段隔离内部 `Vec<u8>`，再由公开构造与修改入口（如校验字节并返回 `Result` 的 `String::from_utf8`、只接收合法切片的 `push_str(&str)`）共同守住的库级不变量。</span>将原始字节切片 `&[u8]` 零复制受检转换为 `&str`，调用的同样是标准库函数 `std::str::from_utf8`。

<Aside type="note" title="遇到不保证合法 UTF-8 的外部数据时怎么办？">
正因为 `&str` 与 `String` 严格要求内部字节为合法 UTF-8，当程序跨出纯文本边界、与操作系统或 C 语言库交互时，标准库按同样的「借用切片 ↔ 拥有者容器」对偶结构提供了三组专用类型：

- **`&OsStr` ↔ `OsString`（`std::ffi`）**：承接环境变量与命令行参数等操作系统原生字符串（Linux 允许任意非零字节序列，Windows 采用 16 位宽字符，均未必是合法 UTF-8）；
- **`&Path` ↔ `PathBuf`（`std::path`）**：在 `OsStr` 之上封装跨平台路径分隔符、父目录与扩展名操作，专用于文件系统路径；
- **`&CStr` ↔ `CString`（`std::ffi`）**：以空字节 `\0` 结尾、内部不含 `\0` 的字节序列，专用于与 C 语言接口跨界传递字符串（处理纯二进制或未知编码网络流时，则直接使用 `&[u8]` ↔ `Vec<u8>`）。
</Aside>

### 内存编码取舍：UTF-8 与定宽字符序列的权衡

不同语言在字符串内存表示上做过不同的取舍：

- **定宽 4 字节序列（UTF-32）**：若将字符串直接存成 `[char]` 数组，每个字符固定占 4 字节，虽能按 `O(1)` 下标取字符，但纯英文空间会膨胀四倍——5 个字母的 `"hello"` 就要占 20 字节；
- **Java 的 `char[]`（UTF-16）与紧凑字符串**：Java 早期以 2 字节 `char` 序列存储字符串，纯英文比单字节编码多占一倍内存。Unicode 扩充后，超出基本多文种平面的字符（如 `'🦀'`）仍需拆成一对代理项（占 4 字节、2 个 `char`），调用 `charAt(i)` 遇到 Emoji 时拿到的只是半截代理项，并未换来真正的定长字符索引。Java 9 起引入**紧凑字符串（Compact Strings）**，纯拉丁文本改用单字节，但只要混入一个汉字或 Emoji，整串所有字符便会整体退化回双字节 UTF-16。

Rust 选择在内存中统一以变长的 **UTF-8 编码**存储字符串：英文 ASCII 占 **1 字节**，带重音拉丁字母等占 **2 字节**，常用汉字占 **3 字节**，Emoji 占 **4 字节**。

这一选择带来了两项工程收益：第一，代码、JSON 键值、HTTP 报文与日志包含大量 ASCII 字符，UTF-8 通常更节省内存与 CPU 缓存；第二，现代网络协议与主流文件格式普遍采用 UTF-8，Rust 从网卡或磁盘读入字节流后，只需做一次合法性校验即可零复制转为 `&str`，省去了跨 I/O 边界在内部 UTF-16 与外部 UTF-8 之间反复编解码的开销。

相应的代价与边界同样明确：常用汉字在 UTF-8 中占 **3 字节**（高于 UTF-16 的 2 字节），纯中文长文本的内存占用会略高；同时，变长编码也直接封死了整数下标 `s[i]`。回到刚才的 `"Rust语言"`：4 个字母占 4 字节，`'语'` 与 `'言'` 各占 3 字节，`.len()` 记录的是底层总字节数 `10`。若让 `s[4]` 按字节返回首字节 `232`，拿到的只是半截汉字残片；若让 `s[4]` 按字符返回 `'语'`，CPU 又必须从首字节起逐个解码计数，违背了下标运算应在常数时间 `O(1)` 完成的性能预期。

因此，Rust 禁掉 `s[i]`，要求在调用点显式指明操作的是哪一层文本粒度：

- **按原始字节（`u8`）**：调用 **`s.as_bytes()`** 取得 `&[u8]` 切片，或用 **`s.bytes()`** 逐字节遍历；
- **按 Unicode 标量值（`char`）**：调用 **`s.chars()`** 逐个解码出 4 字节 `char`（需同时获取每个字符对应的起始字节偏移量时调用 **`s.char_indices()`**）；
- **按人类视觉字符（字素簇 Grapheme Cluster）**：即便是 `s.chars().count()` 也不总等于屏幕上的视觉字数——带组合重音符的字母或组合 Emoji（如家庭图标）由多个 `char` 拼接而成，需按视觉字符统计或截断时应引入 `unicode-segmentation` 等分词库。

### 切片的字符边界

既然不能写 `s[0]`，不少代码（包括未加留意的 AI 生成代码）在需要截取文本摘要时，会顺手写成范围切片 `&input[0..10]`。按字节偏移构造胖指针属于 `O(1)` 操作，编译能够通过，但有一条运行时约束：**起止字节下标必须恰好落在 UTF-8 字符的分界点上。**

## `&str` 与 `String` 的工程选型

在日常设计函数签名、定义数据结构与编写字符串拼接逻辑时，可按以下边界裁决：

| 工程场景 | 选型判据 | 底层与成本依据 |
| --- | --- | --- |
| **只读函数参数** | **写 `fn process(s: &str)`**（不写 `&String`） | `&String` 排斥字面量与子切片，且是 8 字节瘦指针需二次跳转；`&str` 零分配接纳所有来源 |
| **需持有所有权的参数** | **写 `fn register(name: String)`** | 函数内需存入结构体或移交他处时按值接收，将是否需要复制分配交给调用方决定 |
| **函数返回值** | **新拼装文本返回 `String`；截取输入参数返回 `&str`** | 函数内新开的堆缓冲区须移交释放责任；从输入 `&str` 切出的片段直接返回胖指针即可 |
| **结构体字段** | **常规业务实体默认用 `String`** | 结构体独立持有堆文本，可自由移动与长期存续，不受外部借用有效区间限制 |
| **日常构造与循环拼接** | **字面量用 `String::from`；借用转拥有用 `.to_owned()`；多变量模板用 `format!`** | 循环内高频拼接大量片段时，先用 **`String::with_capacity(n)`** 预留容量再配 **`.push_str(...)`** 原地追加，避免循环内调用 `format!` 反复分配短命堆块 |

审查业务代码（包括 AI 生成的代码）时，对照上表可重点拦截两类冗余堆分配：

1. **参数收 `&str`，进函数首行立刻 `.to_owned()`**：例如签名写成 `fn register(name: &str)`，函数体第一行就执行 `name.to_owned()` 存入结构体。若调用方手里原本就有一个不再使用的 `String`，这种签名会迫使调用方先借用，函数内再重复申请堆内存复制一遍；直接改为 `fn register(name: String)`，调用方有现成 `String` 时即可零分配移动传入，只有手握 `&str` 时才在调用点显式写 `.to_owned()`。
2. **只读切分函数写死 `&String -> String`**：例如 `fn parse_header(line: &String) -> String` 内部只截取冒号前的字段名返回，可将参数放宽为 `line: &str`，并在调用方仍持有原文本时将返回类型改为 `Option<&str>`（配合 `line.split_once(':')` 或 `line.get(..idx)`），一次省去堆内存分配与字节复制。
