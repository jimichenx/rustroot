前两节理清了通用连续内存序列 `[T; N]`、`&[T]` 与 `Vec<T>` 的分工。当存放的内容从普通数据变成文本时，日常编码会交替用到两种核心字符串类型：只读借用的**字符串切片 `&str`** 与可增长、独自承担释放责任的**堆字符串 `String`**。

## `&str` 与 `String` 的基本用法

先通过五行基础操作认识它们的起步写法：

```rust
let literal: &str = "hello";
let mut msg: String = String::from("hello");
msg.push_str(" world");
msg.push('!');
println!("{literal} -> {msg}");
```

对照上面的代码，日常起步把握三点：

- **只读文本用 `&str`**：代码中直接写出的双引号字面量 `"hello"`，类型就是 `&str`。只需读取文本、打印日志或向函数传递只读字符串参数时，直接使用 `&str`；
- **动态修改与独立持有用 `String`**：运行期需要拼接修改或将文本长期保存在结构体中时，用 `String::from("hello")` 从字面量构造（或用 `String::new()` 创建空串），声明为 `let mut` 后调用 `.push_str("...")` 追加字符串切片；
- **区分双引号 `&str` 与单引号 `char`**：Rust 不混用单双引号——双引号 `"..."` 是字符串切片 `&str`，单引号 `'!'` 则是固定占 **4 字节**、表示单个 **Unicode 标量值（Unicode Scalar Value）** 的 `char` 类型（见附录「[标量、元组与单元类型](/appendix/basics/scalars-and-tuples/)」），对应调用 `.push('!')` 追加单个 `char`。

单看创建与追加，写法与其他语言差别不大。但从 Java、Python 或 Go 转向 Rust 时，很快会遇到两处疑问：**为什么其他语言靠一个 `String` 就能包办字面量、子串和拼接，Rust 却要拆出 `&str` 与 `String`？** 以及在处理文本时，**为什么取第 0 个元素写 `s[0]` 会直接编译失败？**

## 为什么需要两种字符串

在 Java 或 Python 中，双引号字面量、截取出的子串与动态拼接结果对外都是同一个 `String` 类型——底层借助堆对象、字符串常量池与垃圾回收器（GC）在幕后包揽了共享与回收。

在没有 GC 的 Rust 中，如果只保留唯一一种负责释放堆内存的 `String` 类型，会立即带来两处资源浪费：

1. **固定字面量也要上堆**：`"hello"` 这 5 个字节在编译期已写入可执行文件，若变量类型只能是管理堆块的 `String`，程序每次运行到这里都得去堆上申请内存、复制字节，离开作用域再释放；
2. **只读截取子串也要复制**：若只想检查某行百字节日志的前 5 个字节，没有借用视图就意味着每次切子串都必须新开一块堆内存。

要在无 GC 前提下兼顾**「动态生成的文本有明确的堆释放责任人」**与**「读取字面量或局部子串零堆分配、零字节复制」**，就必须将拥有堆缓冲区的容器 `String` 与只借用一段字节的切片视图 `&str` 拆成两个独立的类型。

### 内置原生类型 `str` 与标准库结构体 `String`

把前两节的连续内存载体直接映射过来，字符串家族就是在 `[u8]`、`&[u8]`、`Vec<u8>` 之上叠加了一条类型级安全约束：**内部字节序列在任何时刻都必须是合法的 UTF-8 编码。**（下表物理表示以 64 位平台为例，字段顺序仅作示意：）

| 对应字节载体 | 字符串类型 | 栈上物理表示（64 位） | 底层身份与职责定位 |
| --- | --- | --- | --- |
| **`[u8]`** | **`str`** | 编译期大小未知（**DST**，不可直接上栈） | **语言内置原生类型**：内存中任意一段连续的合法 UTF-8 字节 |
| **`&[u8]`** | **`&str`** | **16 字节胖指针**（含 `ptr`、`len`） | **字符串切片引用**（日常简称字符串切片）：不复制字节的只读视图 |
| **`Vec<u8>`** | **`String`** | **24 字节控制头**（含 `ptr`、`len`、`cap`） | **标准库结构体**：拥有并负责释放堆缓冲区，支持动态追加与扩容 |
| **`&Vec<u8>`** | **`&String`** | **8 字节瘦指针** `ptr` | 指向栈上 `String` 控制头的普通只读引用 |

回扣[构造器的组合](/types/type-combinations/)中「语言内置 vs 标准库」的划分，`str` 与 `String` 的实现层次并不对称：

- **`str` 是编译器内置的原生类型（Primitive Type）**：编译器负责解析双引号字面量 `"hello rust"`，在编译期校验 UTF-8 并写入可执行文件的**只读数据段（Read-Only Data Segment）**，同时确定 `&str` 的切片胖指针布局。只读数据段在程序运行全程有效，字面量的完整类型为 **`&'static str`**（`'static` 表示全局有效区间，详见[编译器的幕后逻辑：范围包含关系（型变）与 `'static`](/pointers/lifetime-variance-and-static/)）。而你在 `str` 上调用的 `.len()`、`.trim()`、`.split()` 等方法，均写在标准库的 `impl str` 块里；
- **`String` 是标准库定义的普通结构体**：它的定义只有一行私有字段封装 `pub struct String { vec: Vec<u8> }`。<span class="rr-keypoint">`String` 的合法 UTF-8 约束并非编译器特权，而是靠私有字段隔离内部 `Vec<u8>`，再由公开构造与修改入口（如受检转换 `String::from_utf8`、只接收合法切片的 `push_str(&str)`）共同守住的库级不变量。</span>将字节切片 `&[u8]` 零复制受检转换为 `&str`，调用的同样是标准库函数 `std::str::from_utf8`。

<Aside type="note" title="遇到不保证合法 UTF-8 的系统数据时怎么办？">
当跨出纯文本边界与操作系统或 C 接口交互、外部字节未必满足合法 UTF-8 时，标准库按同样的「借用切片 ↔ 拥有者」对偶提供了专用类型：文件路径用 `&Path` ↔ `PathBuf`，环境变量等系统原生串用 `&OsStr` ↔ `OsString`，以 `\0` 结尾的 C 接口字符串用 `&CStr` ↔ `CString`，纯二进制流则直接用 `&[u8]` ↔ `Vec<u8>`。
</Aside>

## 为什么禁止 `s[0]`，以及范围切片何时失败

下面用一段包含 4 个英文字母和 2 个汉字的文本 `let s = String::from("Rust语言");` 实测 `.len()` 与 `.chars().count()`，并尝试按下标读取：

<Code code={utf8Indexing} lang="rust" />

<small class="code-source">运行输出与编译器诊断摘要（取消 utf8-indexing.rs 第 7 行注释后）</small>
```text
byte length (.len()): 10
char count (.chars()): 6
slices: Rust | 语言
chars: [R] [u] [s] [t] [语] [言] 

error[E0277]: the type `str` cannot be indexed by `{integer}`
 --> types/slices/src/bin/utf8-indexing.rs:7:19
  |
7 |     let first = s[0];
  |                   ^ string indices are ranges of `usize`
```

先看清这两行输出背后的编码事实：Rust 字符串在内存中统一采用变长的 **UTF-8 编码**——英文 ASCII 占 **1 字节**，带音标拉丁字母等占 **2 字节**，常用汉字占 **3 字节**，Emoji 占 **4 字节**。

因此，在 `"Rust语言"` 中，4 个英文字母占 4 字节，`'语'` 与 `'言'` 各占 3 字节，**`s.len()` 数的是底层 UTF-8 字节总数（`10`）**，而不是字符个数。这也直接决定了编译器为什么禁止整数下标 `s[i]`：若让 `s[4]` 按字节返回首字节 `232`，拿到的只是半截汉字残片；若让 `s[4]` 返回 `'语'`，CPU 又必须从首字节起逐个解码计数（`O(N)`），违背下标访问 `O(1)` 的性能预期。

为此，Rust 要求在调用点显式指明操作的是哪一层文本粒度：

- **1. 字节（Byte，`u8`）**：`s.len()` 返回字节长度，`s.as_bytes()` 借出 `&[u8]` 切片，`s.bytes()` 逐字节遍历；
- **2. Unicode 标量值（`char`，固定占 4 字节）**：`s.chars()` 将 UTF-8 字节流逐个解码为 `char`（上例共解码出 `6` 个标量值），`s.char_indices()` 则同时给出每个 `char` 的起始字节偏移；
- **3. 字素簇（Grapheme Cluster，视觉上的单个字符）**：带组合音标的字母或组合 Emoji（如家庭图标）由多个 `char` 拼接而成，`s.chars().count()` 也未必等于屏幕上的视觉字数，需按视觉字符统计或截断时应使用 `unicode-segmentation` 等库。

与其他语言的内存编码相比，定宽 4 字节序列（UTF-32）会让纯英文内存膨胀四倍，Java 的双字节 UTF-16（及 Java 9 引入的拉丁单字节紧凑字符串）遇到 Emoji 仍需代理项拆分且跨网络/文件边界常需转码；Rust 统一采用 UTF-8，在常见 ASCII 混排文本上更省内存，从网卡或磁盘读入字节流后经一次校验即可零复制转为 `&str`（代价是纯中文占 3 字节且无 `O(1)` 标量值下标）。

### 范围切片必须落在标量值边界上

## `&str` 与 `String` 的工程选型

在日常设计函数签名、定义数据结构与编写字符串拼接逻辑时，可按以下边界裁决：

| 工程场景 | 选型判据 | 底层与成本依据 |
| --- | --- | --- |
| **只读函数参数** | **写 `fn process(s: &str)`**（不写 `&String`） | `&String` 排斥字面量与子切片且需二次跳转；`&str` 零分配接纳所有来源 |
| **需持有所有权的参数** | **写 `fn register(name: String)`** | 函数内需存入结构体或移交他处时按值接收，将是否需要复制分配交给调用方决定 |
| **函数返回值** | **新拼装文本返回 `String`；截取输入参数返回 `&str`** | 函数内新开的堆缓冲区须移交释放责任；从输入 `&str` 切出的片段直接返回胖指针即可 |
| **结构体字段** | **常规业务实体默认用 `String`** | 结构体独立持有堆文本，可自由移动与长期存续，不受外部借用有效区间限制 |
| **日常构造与循环拼接** | **字面量用 `String::from`；借用转拥有用 `.to_owned()`；多变量模板用 `format!`** | 循环内高频拼接大量片段时，先用 **`String::with_capacity(n)`** 预留容量再配 **`.push_str(...)`** 原地追加，避免循环内调用 `format!` 反复分配短命堆块 |

审查业务代码（包括 AI 生成的代码）时，对照上表可重点拦截两类冗余堆分配：

1. **参数收 `&str`，进函数首行立刻 `.to_owned()`**：若签名写成 `fn register(name: &str)`，进函数第一行就执行 `name.to_owned()` 存入结构体，当调用方手里原本就有不再使用的 `String` 时，会白白多做一次堆分配与复制；改为 `fn register(name: String)`，调用方有现成 `String` 时即可零分配移动传入，手握 `&str` 时才在调用点显式 `.to_owned()`。
2. **只读切分函数写死 `&String -> String`**：如 `fn parse_header(line: &String) -> String` 只截取冒号前的字段名返回，可将参数放宽为 `line: &str`，并在调用方仍持有原文本时返回 `Option<&str>`（配合 `line.split_once(':')` 或 `line.get(..idx)`），省去堆分配与字节复制。
