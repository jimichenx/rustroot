定长数组 `[T; N]` 独自承担释放责任，但长度 `N` 固定在编译期；切片引用 `&[T]` 支持任意运行期长度，但只是不持有数据的借用视图。当程序需要从文件或网络收集一批数量未知的数据、自己持有所有权并随时增删元素时，使用的是标准库动态数组构造器——**`Vec<T>`**（对应 Java 的 `ArrayList<T>`、Python 的 `list`）。

对照上面的代码，日常起步只需掌握三点：

- **已知初始元素时用 `vec!` 宏**：如 `vec![10, 20]`（或重复初始化 `vec![0; 4]`）。注意区分语法：不带 `vec!` 的 `[10, 20]` 是栈上定长数组 `[i32; 2]`；带上 `vec!` 才是管理堆缓冲区的 `Vec<i32>`；
- **从空列表起步时用 `Vec::new()`**：若后续紧接着调用了 `push` 推入元素，编译器会顺着元素自动推断出具体类型；像 `empty` 这样尚未推入元素时，则需显式写出类型标注 `: Vec<i32>` 填满类型参数 `T`；
- **追加与读取**：声明为 `let mut` 可变绑定后，调用 `.push(...)` 向末尾追加元素，通过下标 `scores[0]` 与 `.len()` 读取元素和当前长度。

单独看创建、追加与读取，`Vec<T>` 的写法与 Java 的 `ArrayList` 或 Python 的 `list` 几乎一致。但只要把「借用内部元素」与「往末尾追加」或「按下标取走元素」组合在一起，就会接连遇到两条在带垃圾回收器（GC）语言里从未见过的编译拦截。

往列表末尾追加第 2 号元素，怎么会威胁到第 0 号元素的只读引用？答案藏在 `Vec<T>` 的控制头与扩容机制中。

### 24 字节控制头与扩容

由于元素个数在运行时动态增长，`Vec<T>` 将元素连续存放在堆缓冲区中。在 64 位平台上，栈上的局部变量 `Vec<T>` 固定占 **24 字节**，记录三项控制信息（下表按职责说明，不锁定标准库内部字段顺序；空 `Vec` 未必实际分配堆内存）：

| 控制头信息 | 大小（64 位） | 物理职责 |
| --- | --- | --- |
| **`ptr`** | 8 字节 | 指向堆上连续元素缓冲区的起始地址 |
| **`len`** | 8 字节（`usize`） | **当前有效长度**：缓冲区内已初始化、正在使用的元素个数 |
| **`cap`** | 8 字节（`usize`） | **缓冲区总容量（Capacity）**：当前堆块在不重新分配的前提下最多容纳的元素个数 |

预留容量 `cap` 将 `push` 操作分成了两种运行路径：

- 当 **`len < cap`** 时：缓冲区仍有空位，`push` 直接将新元素写入第 `len` 号槽位并将 `len` 加 `1`，零堆分配；
- 当 **`len == cap`** 时：缓冲区已满，继续 `push` 会触发扩容——分配器可能原地扩大当前堆块，也可能在堆上另开一块更大的新缓冲区，将已有元素按位复制过去，并**当场释放旧堆块**。

### 存引用还是直接内联

回到刚才的 `E0502` 报错，对比 Java 的 `ArrayList<String>` 与 Rust 的 `Vec<String>`，就能看清两者的内存差异：

- **Java 的 `ArrayList<String>` 在数组里存放对象引用**：真正的 `"Alice"` 独立存放在堆的另一处。即便 `add("Carol")` 触发扩容换掉了底层数组，局部变量 `leader` 指向的 `"Alice"` 对象依然完好，GC 不会释放它；
- **Rust 的 `Vec<String>` 将元素直接连续内联在自己的堆缓冲区里**：堆缓冲区中紧挨着排布的是每个 `String` 的 24 字节控制头。`let leader = &names[0];` 取出的地址，直接指向 `names` 当前堆缓冲区的第 0 号槽位。一旦 `names.push(...)` 因容量不足另开新堆块并**释放旧堆缓冲区**，`leader` 保存的旧槽位地址立即变成悬垂引用。

<span class="rr-keypoint">借用检查器不赌某次 `push` 在运行时是否恰好触发搬迁：只要内部元素引用的有效区间跨越了 `push` 等可变修改，编译期一律以 `E0502` 拦截。</span>调整代码顺序——先完成所有 `push` 再借用元素，或在 `push` 之前结束对 `leader` 的使用——即可消除该风险。

## 为什么不能按下标移走元素

开篇示例中 `scores[0]` 能直接读出整数 `10`，是因为 `i32` 实现了 `Copy`。换成元素未实现 `Copy` 的 `Vec<String>`，在 Java 中写 `String first = names.get(0);` 只会复制一份引用；而在 Rust 中直接写 `let first = names[0];`，则会触发第二条编译拦截：

<Code code={vecSafetyRules} lang="rust" anchor="move_out_of_index" />

取消 `// let first = names[0];` 的注释后，编译器报出 `error[E0507]`：

<small class="code-source">编译器输出摘要（取消 vec-safety-rules.rs 中 let first = names[0]; 注释后）</small>
```text
error[E0507]: cannot move out of index of `Vec<String>`
  --> types/slices/src/bin/vec-safety-rules.rs:19:17
   |
19 |     let first = names[0];
   |                 ^^^^^^^^ move occurs because value has type `String`, which does not implement the `Copy` trait
   |
help: consider borrowing here: `&names[0]`
```

原因与[数组](/types/arrays/)中的 `E0508` 一致：`Vec<T>` 必须保证堆缓冲区 `0..len` 范围内的每一个槽位都处于有效初始化状态，以便 `names` 离开作用域时按 `len` 逐一释放。若允许 `names[0]` 单独移走第 0 格的 `String`，连续有效区间内部就会留下一格已失效的空位。

因此，访问或取出 `Vec<T>` 中的非 `Copy` 元素时，须按「只读借用」与「移出所有权并填平空位」区分方法：

1. **只读借用（不接手所有权）**：已知下标在界内时写 `&names[i]`（若 `i >= len` 会在运行时触发 `panic` 终止）；处理可能越界的外部输入下标时，优先调用 **`names.get(i)`**。
   注意运行输出中的 `Some("Bob")` 与 `None`：Rust 没有 `null`，像 `.get(i)` 这类可能查无结果的方法，统一返回标准库的 `Option` 包装类型——查到时返回 `Some(值)`，越界时安全返回 `None`（其底层枚举结构将在[消灭空指针：`Option<T>` 与空位优化](/types/option-and-null/)中拆解）。
2. **移出所有权（同步缩减 `len` 消除空位）**：
   - **`names.pop()`**：移出末尾元素并返回 `Option<T>`，`len` 减 `1`（空表返回 `None`，时间复杂度 `O(1)`）；
   - **`names.remove(i)`**：移出第 `i` 格元素 `T`，并将后方所有元素向前平移一格填补空位（`O(N)`）；
   - **`names.swap_remove(i)`**：不要求保持剩余顺序时，直接将末尾元素换入第 `i` 格填补空位（`O(1)`）。

### 用 `for` 遍历元素的三种所有权写法

从按下标访问单个元素扩展到用 `for` 循环逐个遍历集合时，初学者常因漏写 `&` 在循环结束后遇到 `E0382`（移动后使用）。遍历 `Vec<T>`（以及后续的 `HashMap<K, V>`）时，须在 `in` 后面显式写出借用或消费方式：

```rust
let mut scores = vec![10, 20, 30];
for s in &scores { println!("{s}"); }
for s in &mut scores { *s += 5; }
for s in scores { println!("{s}"); }
```

三种写法分别对应已学的三种类型关系：

- **`for s in &scores`（只读借用）**：每次取出元素引用 `s: &i32`，循环结束后 `scores` 原样保留，是日常遍历的首选写法；
- **`for s in &mut scores`（原地修改）**：每次取出可变引用 `s: &mut i32`，配合解引用 `*s += 5` 直接修改缓冲区槽位，循环结束后 `scores` 仍归原变量持有；
- **`for s in scores`（按值消费）**：不加 `&` 时，整个 `scores` 的所有权在进入循环时即被移走，元素逐个移出并在循环结束时释放底层堆缓冲区，后续不可再访问 `scores`。

## 连续内存载体选型

至此，Rust 组织通用连续内存的三个核心类型——`[T; N]`、`Vec<T>` 与 `&[T]`——已经全部就位。栈上的 `[T; N]` 与堆上的 `Vec<T>` 在借用时均可零分配转为通用切片 `&[T]` / `&mut [T]`，并直接复用上一节 `[T]` 文档中的全部方法。

在定义数据结构或审查函数签名（包括审查 AI 生成的代码）时，可按以下边界裁决：

| 对比维度 | 定长数组 `[T; N]` | 动态数组 `Vec<T>` | 切片引用 `&[T]` / `&mut [T]` |
| --- | --- | --- | --- |
| **元素存储位置** | 直接内联在当前结构或栈帧中 | 连续内联在堆缓冲区，`Vec` 持有控制头 | 不持有数据，借用栈、堆或静态区连续内存 |
| **栈上大小（64 位）** | `N × size_of::<T>()` | **24 字节** `(ptr, len, cap)` | **16 字节** `(ptr, len)` |
| **长度确定时机** | **编译期**固定在类型中 | **运行时**动态增删、按需扩容 | **运行时**切取决定，视图自身不可扩容 |
| **工程选型场景** | 元素个数在编译期固定且体积较小（如 RGB 颜色 `[u8; 3]`） | 运行时决定个数、需动态增删，或放在结构体字段中独立持有数据 | **只读或原地修改序列的函数参数**（写 `fn f(data: &[T])`，拦截狭隘的 `&Vec<T>`） |

例如，若在代码审查中看到统计函数签名写为 `fn average(nums: &Vec<f64>) -> f64` 且首行直接写 `let first = nums[0];`，即可当场指出两处隐患：`&Vec<f64>` 把栈数组与子切片挡在了门外，应拓宽为 `nums: &[f64]`；外部传入空切片时 `nums[0]` 会越界崩溃，应改用 `nums.first()` 或 `nums.get(0)` 先判空再计算。
