```text
first: 10, len: 4

```

对照上面的代码，日常使用数组先掌握三点：

- **两种创建写法**：已知各项数值时逐个列出（如 `[10, 20, 30, 40]`）；需要批量填入相同初值时使用重复初始化语法 **`[初始值; 长度]`**（如 `[0; 4]` 生成 4 个连续的 `0`，中间用分号 `;`）；
- **类型标注 `[T; N]`**：方括号内前半部分是元素类型 `T`，分号后是元素个数 `N`（如 `[i32; 4]`；局部变量通常可省略类型标注交由编译器推断）；
- **下标读写与越界保护**：通过从 `0` 开始的下标 `a[0]` 读取元素，用 `.len()` 获取元素个数；若绑定声明为 `let mut a`，可通过 `a[1] = 99;` 原地更新元素。如果运行时下标超出 `0..len` 范围，Rust 会立即触发 `panic` 终止程序，不会像 C 语言那样静默读取越界脏内存。

## 编译期长度与栈上布局

看懂基础读写后，再看与其他语言的一处关键差异：在 Java 或 C# 中，可以用运行期读入的变量决定数组长度（如 `int n = readInput(); new int[n];`）；而在 Rust 中，若把运行期变量写进 `[0; n]`，编译器会直接拒绝——**Rust 数组 `[T; N]` 的长度 `N` 必须在编译期确定**（运行期长度未知或需动态增删的场景，将由后两节的切片 `&[T]` 与动态数组 `Vec<T>` 接手）。

为什么 Rust 把数组做成编译期定长？答案就在刚才最后一行输出 `size of [i32; 4]: 16 bytes` 里。每个 `i32` 占 4 字节，4 个 `i32` 恰好是 `4 × 4 = 16` 字节，对照[类型的两面](/types/representation-and-constraints/)中的信息守恒视角：

- **Java 的 `new int[4]` 位于堆上**：为了统一接纳各种运行期长度，Java 不把长度写进类型 `int[]`，而是在堆对象里除 16 字节元素外额外带上 **12 字节对象头 + 4 字节 `length` 字段**（外加栈上的引用变量），运行时的 `a.length` 需要访问堆内存读取；
- **Rust 的 `[i32; 4]` 直接连续内联在当前位置（如栈帧）上**：只占 **16 字节**——没有堆分配，没有指针，长度 `4` 在运行时不占任何字节。

运行时内存没存长度，代码里的 `a.len()` 与下标越界检查从哪里拿到数字 `4`？长度 `N` 作为**编译期常量参数**填入构造器 `[T; N]`，已经记录在 `[i32; 4]` 的编译期类型信息里；调用 `a.len()` 时，编译器直接将常数 `4` 写入机器指令。

这也意味着，向构造器 `[-; -]` 填入 `(i32, 2)` 生成的 **`[i32; 2]`** 与填入 `(i32, 4)` 生成的 **`[i32; 4]`**，在编译器中是**两个互不兼容的独立类型**。

## 数组的复制、移动与下标限制

数组构造器 `[T; N]` 生成的具体类型能否按位复制，直接取决于内部元素类型 `T`：

- **若元素 `T` 实现了 `Copy`**（如 `i32`）：`[i32; 4]` 自动实现 `Copy`，执行 `let b = a;` 按位复制栈上 16 字节，`a` 与 `b` 各自有效；
- **若元素 `T` 未实现 `Copy`**（如承担堆释放责任的 `String`）：`[String; 2]` 不实现 `Copy`，执行 `let moved_names = names;` 时整个数组发生移动，原数组 `names` 失效（再用报 `E0382`）。

为什么允许移走整个数组，却禁止移走单个元素 `names[0]`？顺着[复制与移动](/memory/minimal-model/)确立的唯一释放责任推演：

1. 数组下标 `names[0]` 直接指代栈上第 0 号元素的槽位；
2. `String` 未实现 `Copy`，执行 `let first = names[0];` 会将第 0 格的 `String` 移交给 `first`，原地留下失效空位，而 `names[1]` 仍然有效；
3. 真实代码中下标通常是运行期才算出的变量 `names[i]`。等到 `names` 离开作用域自动清理时，只看静态类型 `[String; 2]` 的编译器无法在编译期确定运行时哪一格已被移空、哪一格仍需释放。

## 定长类型的局限

把长度 `N` 放进类型省去了运行时头部开销，但也限制了函数的通用性。由于 `[i32; 4]` 与 `[i32; 3]` 是两个独立的类型，参数写成 `&[i32; 4]` 的求和函数只能服务长度为 `4` 的数组：

<small class="code-source">编译器输出摘要（取消 array-fixed-len.rs 第 11 行注释后）</small>

```text
error[E0308]: mismatched types
  --> types/slices/src/bin/array-fixed-len.rs:11:31
```

`sum4` 既无法接收 `[i32; 3]` 或 `[i32; 100]`，也无法只截取 `a4` 中间的两个元素来求和。因此，`[T; N]` 适合表达编译期元素个数固定不变的数据，无法直接充当通用的序列参数。

## 小结与动手核对

1. **编译期定长、内联布局**：`[T; N]` 的长度 `N` 记录在编译期类型信息中，运行时内存连续排列 `N` 个 `T`（占 `N × size_of::<T>()` 字节），无额外头部开销；
2. **不同长度对应不同类型**：`[i32; 3]` 与 `[i32; 4]` 互不兼容，`&[T; N]` 参数无法跨长度复用；
3. **随元素决定 `Copy` 与移动**：`T: Copy` 则 `[T; N]: Copy`；非 `Copy` 数组禁止通过 `arr[i]` 移出单个元素（报 `E0508`），应通过 `&arr[i]` 借用。

### 动手核对

在 `array-copy-move.rs` 中，为什么 `a[0]`（来自 `[i32; 4]`）可以直接按值读出，而 `names[0]`（来自 `[String; 2]`）却触发 `E0508`？

核对结果：`i32` 实现了 `Copy`，读取 `a[0]` 只按位复制 4 字节整数，原槽位依然有效，不会破坏数组的完整性；`String` 未实现 `Copy`，按值读取 `names[0]` 会移走第 0 格的所有权，在数组内留下编译器无法静态追踪释放责任的失效空位。
