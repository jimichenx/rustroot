在各门编程语言里，**数组（Array）**解决的都是同一个基础需求：用一段固定长度、连续排布的内存存放同一种类型的元素，创建后长度不再增减。

围绕**「长度能否在运行时才决定」**，Rust 的数组与许多主流语言做出了不同的取舍：

- **Java、C# 等语言支持运行时决定长度**（如 `int n = readInput(); new int[n];`）。为了统一接纳各种运行期长度，这些语言不把长度写进类型 `int[]`，而是将数组分配在**堆内存**上，在堆对象头部额外记录 `length`；
- **Rust 数组 `[T; N]` 的长度 `N` 必须在编译期确定**，不允许把运行期变量当作长度参数。因为编译期已知确切字节大小，数组无需去堆上动态申请，直接连续内联在当前位置（如栈帧）上，没有对象头与运行时长度字段开销。

至于「长度在运行时确定或需要动态增删」的场景，待理清 `[T; N]` 的边界后，将在随后两节的切片 `[T]` 与动态数组 `Vec<T>` 中逐一解决。

## 数组语法与栈上布局

Rust 创建数组有两种常见写法：

1. **逐个列出元素**：如 `[10, 20, 30, 40]`；
2. **重复初始化语法 `[初始值; 长度]`**：如 `[0; 4]`，表示连续排开 4 个值为 `0` 的元素（中间使用分号 `;`，与类型标注 `[i32; 4]` 一致）。

### 长度 `N` 存放在哪里

每个 `i32` 占 4 字节，4 个 `i32` 恰好是 `4 × 4 = 16` 字节。对照[类型的两面](/types/representation-and-constraints/)中的信息守恒视角：

- 在 **Java** 中，`new int[4]` 位于堆上，除 16 字节整数外还带有 **12 字节对象头 + 4 字节 `length` 字段**（外加栈上引用变量），运行时的 `a.length` 需要从堆内存读取；
- 在 **Rust** 中，`[i32; 4]` 在栈帧上只占 **16 字节**——没有堆分配，没有指针，长度 `4` 在运行时不占任何字节。

运行时内存没存长度，代码里的 `a.len()` 与下标越界检查从哪里拿到数字 `4`？答案在类型构造器 **`[T; N]`** 中：长度 `N` 作为**编译期常量参数**填入构造器，已经记录在 `[i32; 4]` 的编译期类型信息里。调用 `a.len()` 时，编译器直接将常数 `4` 写入机器指令，无需读取内存。

<ArrayStackLayout />

这也意味着，向构造器 `[-; -]` 填入 `(i32, 2)` 生成的 **`[i32; 2]`** 与填入 `(i32, 4)` 生成的 **`[i32; 4]`**，在编译器中是**两个互不兼容的独立类型**。

## 数组的复制、移动与下标限制

在[类型构造器](/types/type-constructors/)中提到，外层构造器决定新类型的约束。数组构造器 `[T; N]` 的规则随元素类型 `T` 而定：

- **若元素 `T` 实现了 `Copy`**（如 `i32`）：`[i32; 4]` 自动实现 `Copy`，执行 `let b = a;` 按位复制栈上 16 字节，`a` 与 `b` 各自有效；
- **若元素 `T` 未实现 `Copy`**（如承担堆释放责任的 `String`）：`[String; 2]` 不实现 `Copy`，执行 `let moved_names = names;` 时整个数组发生移动，原数组 `names` 失效（再用报 `E0382`）。

为什么允许移走整个数组，却禁止移走单个元素 `names[0]`？顺着[复制与移动](/memory/minimal-model/)确立的唯一释放责任推演：

1. 数组下标 `names[0]` 是指代第 0 号槽位的位置表达式；
2. `String` 未实现 `Copy`，执行 `let first = names[0];` 会将第 0 格的 `String` 移交给 `first`，原地留下失效空位，而 `names[1]` 仍然有效；
3. 真实代码中下标通常是运行期才算出的变量 `names[i]`。等到 `names` 离开作用域自动清理时，只看静态类型 `[String; 2]` 的编译器无法在编译期确定运行时哪一格已被移空、哪一格仍需释放。

## 定长类型的局限

把长度 `N` 放进类型省去了运行时头部开销，但也限制了函数的通用性。由于 `[i32; 4]` 与 `[i32; 3]` 是两个独立的类型，参数写成 `&[i32; 4]` 的求和函数只能服务长度为 `4` 的数组：

取消 `// println!("sum3: {}", sum4(&a3));` 的注释会触发类型不匹配：

<small class="code-source">编译器输出摘要（取消 array-fixed-len.rs 中注释行后）</small>
```text
error[E0308]: mismatched types
  --> src/bin/array-fixed-len.rs:11:30
   |
11 |     println!("sum3: {}", sum4(&a3));
   |                          ---- ^^^ expected an array with a fixed size of 4 elements, found one with 3 elements
```

`sum4` 既无法接收 `[i32; 3]` 或 `[i32; 100]`，也无法只计算 `a4` 的前两个元素。因此，`[T; N]` 适合表达编译期元素个数固定不变的局部数据，无法直接充当通用的序列参数。

## 小结与动手核对

1. **编译期定长、内联布局**：`[T; N]` 的长度 `N` 记录在编译期类型信息中，运行时内存连续排列 `N` 个 `T`（占 `N × size_of::<T>()` 字节），无额外头部开销；
2. **不同长度对应不同类型**：`[i32; 3]` 与 `[i32; 4]` 互不兼容，`&[T; N]` 参数无法跨长度复用；
3. **随元素决定 `Copy` 与移动**：`T: Copy` 则 `[T; N]: Copy`；非 `Copy` 数组禁止通过 `arr[i]` 移出单个元素（报 `E0508`），应通过 `&arr[i]` 借用。

### 动手核对

在 `array-copy-move.rs` 中，为什么 `a[0]`（来自 `[i32; 4]`）可以直接按值读出，而 `names[0]`（来自 `[String; 2]`）却触发 `E0508`？

核对结果：`i32` 实现了 `Copy`，读取 `a[0]` 只按位复制 4 字节整数，原槽位依然有效，不会破坏数组的完整性；`String` 未实现 `Copy`，按值读取 `names[0]` 会移走第 0 格的所有权，在数组内留下编译器无法静态追踪释放责任的失效空位。

回到上面的 `sum4` 函数：既然无法跨长度复用的症结在于类型里固定的 `; 4`，站在语言设计的角度，如果直接把 `; N` 从类型中抹去，编译器会放行吗？原本记录在类型里的长度信息又该放到哪里？带着这个问题进入下一节。
