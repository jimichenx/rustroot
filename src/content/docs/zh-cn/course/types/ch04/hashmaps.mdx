前两节的 `Vec<T>` 与 `String` 按顺序存放元素，通过整数下标或字节区间访问。在业务代码中，另一类高频需求是根据**键（Key，如用户名、配置项名、订单号）**直接查找对应的**值（Value）**。

如果用 `Vec<(String, i32)>` 存放键值对，每次按名字查询都得从头遍历比对。为此，标准库提供了基于哈希表的键值容器构造器——**`HashMap<K, V>`**（对应 Java 的 `HashMap<K, V>`、Python 的 `dict`、Go 的 `map[K]V`）。

## 双参数类型构造器与堆上哈希表

哈希表需要同时约束「键」与「值」两类数据，因此 `HashMap<K, V>` 是一个接收**两个编译期类型参数**的标准库类型构造器：

- 未填入参数 `K` 和 `V` 的裸 `HashMap` 只是构造器，不能直接用作变量类型（报 `E0107`）；
- 填入具体的键类型 `String` 与值类型 `i32`（或由编译器根据后续 `insert` 调用自动推断）后，合成出具体类型 `HashMap<String, i32>`。同一张表内所有键同属类型 `K`，所有值同属类型 `V`。

与 `Vec<T>` 和 `String` 相比，使用 `HashMap<K, V>` 有两点前置事项：

1. **显式引入模块路径**：`HashMap` 未放入默认自动导入列表（`std::prelude`），使用前需在文件顶部写 `use std::collections::HashMap;`；
2. **堆上哈希槽位与重哈希扩容**：`HashMap<K, V>` 在栈上只保存控制信息，实际的键值对存放在堆上分配的哈希槽位（Buckets）中。当元素增多触发扩容重哈希（Rehashing）时，所有键值对同样会搬迁到新分配的堆缓冲区，并释放旧堆内存。

初始化 `HashMap<K, V>` 常用两种写法：先用 `let mut scores = HashMap::new();` 建空表再插入，或由键值对数组直接构造 `HashMap::from([(String::from("Blue"), 10), (String::from("Yellow"), 50)])`。若业务只需对元素去重与判存、不需要挂载关联值，同一模块下还提供了单参数集合构造器 **`HashSet<T>`**（`use std::collections::HashSet;`，底层直接复用 `HashMap` 实现，所有权与借用规则一致）。

取消 `// println!("team: {team}");` 的注释后，编译器报出与[声明与绑定](/memory/bindings/)一致的移动后借用错误：

<small class="code-source">编译器输出摘要（取消 hashmap-ownership.rs 中注释行后）</small>
```text
error[E0382]: borrow of moved value: `team`
  --> types/slices/src/bin/hashmap-ownership.rs:11:22
   |
 7 |     let team = String::from("Blue");
   |         ---- move occurs because `team` has type `String`, which does not implement the `Copy` trait
...
10 |     scores.insert(team, initial_score);
   |                   ---- value moved here
11 |     println!("team: {team}");
   |                      ^^^^ value borrowed here after move
```

这里没有专属于 `HashMap` 的特殊规则，完全由参数类型的 `Copy` 约束决定：

- **`team: String` 未实现 `Copy`**：传入 `insert` 时发生移动，堆字符串的释放责任移交给 `scores`，原变量 `team` 失效；
- **`initial_score: i32` 实现了 `Copy`**：传入时按位复制 4 字节整数入表，原变量依然有效；
- **同名键覆盖并返回旧值**：再次插入 `"Blue"` 与新分数 `25` 时，哈希表覆盖原值并将被替换的旧值包在 `Option<V>` 中返回（首次插入返回 `None`，覆盖旧值返回 `Some(10)`）。

运行输出：

<small class="code-source">运行输出</small>
```text
Blue: Some(10), Green: None
```

`let blue_score = scores.get("Blue");` 体现了两项接口设计细节：

1. **返回类型是 `Option<&V>`**：查询不移走表内数据，因此返回内部槽位的只读引用 `&i32`；同时目标键可能不存在（如 `"Green"`），外层套上 `Option` 显式区分 `Some(&10)` 与 `None`。
2. **支持直接用 `&str` 查询 `HashMap<String, V>`**：尽管键类型 `K` 是 `String`，调用 `get` 时可直接传入字面量 `"Blue"`（`&str`），无需为单次查询额外调用 `String::from` 分配堆内存。`get` 签名接纳任何能借用出键等价视图的类型（底层的 `Borrow` 语义等价契约将在[借用视图与只读 API 设计](/abstraction/asref-and-borrow/)中拆解）。

如果取消代码中 `// scores.insert(String::from("Red"), 30);` 的注释，编译器会报出 `error[E0502]`：

<small class="code-source">编译器输出摘要（取消 hashmap-lookup.rs 中注释行后）</small>
```text
error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
  --> types/slices/src/bin/hashmap-lookup.rs:12:5
   |
11 |     let blue_score = scores.get("Blue");
   |                      ------ immutable borrow occurs here
12 |     scores.insert(String::from("Red"), 30);
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
13 |     println!("Blue: {:?}, Green: {:?}", blue_score, scores.get("Green"));
   |                                         ---------- immutable borrow later used here
```

原因与[动态数组：`Vec<T>` 与堆上连续内存](/types/vectors/)中持有 `&scores[0]` 期间禁止 `push` 一致：`blue_score` 内部握着指向哈希表当前堆槽位的 `&i32`，一旦 `insert(&mut self, ...)` 触发扩容重哈希并释放旧堆块，后续读取 `blue_score` 就会悬垂。

## 借用规则逼出的 `Entry` 模式：一次查找，原地更新

业务中常见的一类操作是「不存在则插入默认值，存在则保持或原地累加」（如初始化默认配置、统计词频）。如果按其他语言的习惯写成「先 `get` / `contains_key` 检查，再调用 `insert`」，在 Rust 中既会对同一个键重复计算两次哈希、查找两次槽位，还可能因跨写入持有引用触发 `E0502`。

为此，标准库提供了将「查找槽位」与「按需写入」合二为一的 **`entry`（槽位入口）模式**：

<small class="code-source">源文件：<code>examples/types/slices/src/bin/hashmap-entry.rs</code></small>
<Code code={hashmapEntry} lang="rust" />

运行输出：

<small class="code-source">运行输出</small>
```text
after or_insert: Blue = Some(10), Yellow = Some(50)
rust count: Some(3), types count: Some(1)
```

词频统计循环里的两行代码一气呵成完成了三步操作：

```rust
let count = counts.entry(word).or_insert(0);
*count += 1;
```

1. **`counts.entry(word)`**：对 `word` 计算一次哈希并定位目标槽位，返回表示该槽位占用或空置状态的 `Entry` 视图；
2. **`.or_insert(0)`**：若槽位为空则填入默认值 `0`，若已有值则保留原值；<span class="rr-keypoint">无论槽位原先是否为空，`.or_insert` 最终都交出指向该槽位内部值的可变引用 `&mut V`；</span>
3. **`*count += 1;`**：用[引用与可变引用](/types/reference-constructors/)中的解引用运算符 `*` 原地将槽位内的计数加 `1`，全程只做了一次哈希查找。

<Aside type="tip" title="代码审查判据：用 entry 替代 contains_key + insert">
审查业务代码或 AI 生成的代码时，遇到 `if !map.contains_key(&k) { map.insert(k, default_val); }` 这类两步写法，可直接重构为单行 **`map.entry(k).or_insert(default_val);`**，消除重复的哈希计算与槽位查找成本。
</Aside>

## 小结与动手核对

1. **双参数标准库构造器**：`HashMap<K, V>` 需显式 `use std::collections::HashMap;`，键值对存放在堆上哈希槽位中；
2. **所有权与重哈希防线**：`insert(k, v)` 按值接手 `K` 与 `V`；`get(&k)` 返回 `Option<&V>`，持有该引用期间禁止调用 `insert`（防重哈希悬垂，报 `E0502`）；
3. **原地更新用 `Entry`**：`map.entry(key).or_insert(default)` 一次查找定位槽位并返回 `&mut V`，配合 `*val` 原地更新。

### 动手核对

阅读下面这段统计登录次数的函数：

```rust
use std::collections::HashMap;

fn record_login(logins: &mut HashMap<String, u32>, user: String) {
    let count = logins.entry(user).or_insert(0);
    *count += 1;
    // println!("recorded user: {user}");
}
```

1. 变量 `count` 的具体类型是什么？为什么必须写 `*count += 1` 而不能写 `count += 1`？
2. 若取消 `// println!("recorded user: {user}");` 的注释，能否通过编译？为什么？

核对结果：① `count` 的具体类型是 **`&mut u32`**，保存的是哈希表槽位内整数的地址，需通过 `*count` 解引用定位目标槽位后才能加 `1`；② **不能通过编译（报 `error[E0382]`）**，`logins.entry(user)` 按值接收键 `String`（槽位为空时需直接将该 `String` 存入表中），`user` 在该行已发生移动，后续不可再读取。
