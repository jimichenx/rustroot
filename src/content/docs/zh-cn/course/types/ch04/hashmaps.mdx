`Vec<T>` 与 `String` 按位置顺序存放数据；当业务需要根据**键（Key，如队伍名、配置项、用户名）**直接查找对应的**值（Value）**时，使用的是标准库提供的双参数类型构造器——**`HashMap<K, V>`**（对应 Java 的 `HashMap<K, V>`、Python 的 `dict`、Go 的 `map[K]V`）。

## `HashMap` 的基本用法

与 `Vec<T>` 和 `String` 相比，`HashMap` 未放入默认自动导入列表，使用前需在文件顶部写一行 `use std::collections::HashMap;`。最基础的建表、写入与查询只需几行代码：

```rust
use std::collections::HashMap;

let mut scores = HashMap::new();
scores.insert(String::from("Blue"), 10);
scores.insert(String::from("Blue"), 25);
println!("Blue: {:?}, Green: {:?}", scores.get("Blue"), scores.get("Green"));
```

这段代码依次完成了三项基础操作：

- **创建表**：`HashMap::new()` 创建空哈希表。编译器会根据随后 `insert` 传入的实参，自动推断出具体类型 `HashMap<String, i32>`（若已知初始数据，也可由键值对数组直接构造 `HashMap::from([(String::from("Blue"), 10), (String::from("Yellow"), 50)])`）；
- **写入与覆盖**：`scores.insert(k, v)` 写入键值对；若再次写入同名键 `"Blue"`，新值 `25` 会覆盖旧值 `10`；
- **按键查询**：`scores.get("Blue")` 返回 `Option<&i32>`——键存在时返回指向表内值的 `Some(&25)`，键不存在（如 `"Green"`）时返回 `None`。

单看这几行基础读写，用法与 Java 的 `HashMap` 或 Python 的 `dict` 十分相似。但在 Java 中，放进表的变量可以继续读取、拿着查询结果也能随时往表里插入新键，全由垃圾回收器（GC）与独立堆对象在幕后兜底；而在没有 GC、且把键值直接内联存放在桶内存里的 Rust 中，继续顺着这套直觉往下写，会依次在三个环节遇到边界。

## 为什么 `insert` 会移走键

在 Java 中，把字符串变量 `team` 放进 `scores.put(team, 10)` 之后继续打印 `team` 习以为常。在 Rust 中照着写 `scores.insert(team, initial_score)`，紧接着再读取 `team`，编译器会立刻报出 `error[E0382]`：

<small class="code-source">运行输出与编译器诊断摘要（取消 hashmap-ownership.rs 第 11 行注释后）</small>
```text
initial_score is still valid: 10
replaced old value: Some(10), current map: {"Blue": 25}

error[E0382]: borrow of moved value: `team`
  --> types/slices/src/bin/hashmap-ownership.rs:11:22
   |
 7 |     let team = String::from("Blue");
   |         ---- move occurs because `team` has type `String`, which does not implement the `Copy` trait
...
10 |     scores.insert(team, initial_score);
   |                   ---- value moved here
11 |     println!("team: {team}");
   |                      ^^^^ value borrowed here after move
```

`i32` 复制、`String` 移动的基础规则在[声明与绑定](/memory/bindings/)中已经建立；这里真正值得明确的是接口设计意图：**为什么 `insert(k, v)` 默认按值收走键和值的所有权，而不只存一份引用？**

原因在于有效区间的匹配：哈希表往往作为配置表或状态表长期存续，而构造键名的字符串变量可能只是某次函数调用或循环体内的短命局部变量。若哈希表默认只保存外部变量的借用地址，一旦外部局部变量离开作用域释放，表内的键就会变成悬垂引用。因此，常规业务通常定义为 `HashMap<String, V>`，在调用 `insert` 时将堆字符串的释放责任直接移交给哈希表统一保管（同名键覆盖时，`insert` 还会通过 `Option<V>` 交回被替换出的旧值 `Some(10)`）。

## 为什么持有查询结果时不能 `insert`

再看查询环节。注意开篇与下方代码中的一个实用细节：尽管键类型 `K` 是 `String`，调用 `scores.get("Blue")` 时可以直接传入字面量 `"Blue"`（`&str`），无需为单次查询额外调用 `String::from` 分配堆内存（底层的 `Borrow` 等价查询契约将在[借用视图与只读 API 设计](/abstraction/asref-and-borrow/)中拆解）。

接下来按 Java 的日常习惯写：先查出 `"Blue"` 的分数握在手里，顺手往表里写入另一支互不相干的队伍 `"Red"`，最后打印刚才查出的结果：

<Code code={hashmapLookup} lang="rust" />

取消第 12 行 `// scores.insert(String::from("Red"), 30);` 的注释后，编译器以 `error[E0502]` 拒绝编译：

<small class="code-source">编译器输出摘要（取消 hashmap-lookup.rs 第 12 行注释后）</small>
```text
error[E0502]: cannot borrow `scores` as mutable because it is also borrowed as immutable
  --> types/slices/src/bin/hashmap-lookup.rs:12:5
   |
11 |     let blue_score = scores.get("Blue");
   |                      ------ immutable borrow occurs here
12 |     scores.insert(String::from("Red"), 30);
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
13 |     println!("Blue: {:?}, Green: {:?}", blue_score, scores.get("Green"));
   |                                         ---------- immutable borrow later used here
```

这里同样需要分清编译期的直接规则与它所保护的底层内存原因：

1. **编译期的直接规则（不取决于当次是否扩容）**：`scores.get("Blue")` 对整张表发起了共享借用 `&scores`（返回的 `Option<&i32>` 绑定在该借用区间上），而 `scores.insert(...)` 的签名要求可变借用 `&mut scores`。只要第 13 行仍要读取 `blue_score`，共享借用就尚未结束；此时调用需要排他访问的 `insert`，无论当前哈希表剩余容量是否充裕、当次插入在运行时会不会扩容，都会因借用区间重叠直接触发 `E0502`；
2. **`insert` 为什么必须要求 `&mut self`（内存布局差异）**：Java 的 `HashMap<String, Integer>` 在桶数组里只存独立堆对象的引用，即便 `put` 触发扩容换掉桶数组，旧 `Integer` 对象仍在原处；而 Rust 的 `HashMap<String, i32>` 将键 `K` 和值 `V` **直接内联存放在堆上的哈希桶缓冲区（Buckets）里**。`blue_score` 保存的地址直接指向当前桶缓冲区内部槽位——一旦某次 `insert` 因负载过高触发**扩容重哈希（Rehashing）**并释放旧桶内存，表内槽位地址就会悬垂。

先用完 `blue_score` 结束共享借用，再调用 `insert`，冲突便自然解除。

## 用 `Entry` 模式原地更新

实际业务中最常写的哈希表逻辑，往往不是单纯的插入或查询，而是**「查不到就填入初始值，查到了就在原值基础上更新」**——例如统计词频、累加用户请求次数，或向 `HashMap<String, Vec<String>>` 的分组列表里追加元素。

当键是可复制的 `&str` 时，这段代码虽然能跑通，但存在两处明显的工程短板：

1. **调用方反复发起多次查表**：处理一个新词时，`contains_key` 查第 1 次，`insert(word, 0)` 查第 2 次，`naive_counts[word]` 读取查第 3 次，最后 `insert(word, next)` 写回又查第 4 次；
2. **键换成 `String` 时触发所有权冲突**：若词是拥有所有权的 `word: String`，第 1 步 `insert(word, 0)` 就会把 `word` 移入表中，导致后续读取直接报 `E0382`。不少代码（包括未加留意的 AI 生成代码）为了绕过报错，只能妥协写成 `insert(word.clone(), 0)`，在键已存在时也平白多做堆分配与复制。

为消除「调用方先查再插」的割裂，标准库提供了 **`entry`（槽位入口）模式**，把查找与按需填充合成为一次入口操作：

<Code code={hashmapEntry} lang="rust" anchor="entry_count" />

循环体内的两行代码依次完成三步工作：

1. **`counts.entry(word)`**：定位 `word` 在哈希表中的目标槽位入口，返回表示该槽位当前已占用或空置的 `Entry` 视图（注意 `Entry` 的工程收益是**省去调用方先查再插的重复查找**，并非承诺底层在触发扩容重哈希时内部永远只算一次哈希）；
2. **`.or_insert(0)`**：若槽位为空则填入初值 `0`（容量不足时内部自动完成扩容），若已有值则保持原样；<span class="rr-keypoint">无论槽位原先是否为空，`.or_insert` 最终都返回指向该槽位内部值的可变引用 `&mut usize`；</span>
3. **`*count += 1;`**：用解引用运算符 `*` 顺着可变引用原地递增计数值，无需调用方二次查表写回。

<Aside type="tip" title="用 entry 替代判存后插入">
审查业务代码或 AI 生成的 Rust 代码时，若看到 `if !map.contains_key(&key) { map.insert(key.clone(), Vec::new()); }` 紧接着又调 `map.get_mut(&key)` 往里追加元素，可直接将其改写为 **`map.entry(key).or_insert(Vec::new()).push(item);`**，一次省去重复查表与防御性 `.clone()`。
</Aside>

最后用一段登录计数函数检验你对 `Entry` 所有权与返回类型的把握：

```rust
use std::collections::HashMap;

fn record_login(logins: &mut HashMap<String, u32>, user: String) {
    let count = logins.entry(user).or_insert(0);
    *count += 1;
    // println!("recorded user: {user}");
}
```

这里 `count` 的类型是槽位内部值的可变引用 **`&mut u32`**，因此递增时须写 `*count += 1`；而 `logins.entry(user)` 为了在槽位为空时直接将键移入表中，按值接收了 `user: String`（避免键已存在时提前克隆，又无需在空置时二次复制）——调用当行 `user` 的所有权已发生移动，若取消末行 `println!` 的注释，编译器会以 `E0382` 拦截。

<Aside type="note" title="标准库其余常用集合与本章容器的关系">
除 `Vec<T>` 与 `HashMap<K, V>` 外，`std::collections` 中另外三个高频集合同样建立在本章的堆内存与所有权规则之上：

- **`HashSet<T>`（去重集合）**：只需判断元素是否存在时使用，内部是 `HashMap<T, ()>` 的封装（值位填入占 `0` 字节的单元类型 `()`，见附录「[标量、元组与单元类型](/appendix/basics/scalars-and-tuples/)」）；
- **`BTreeMap<K, V>` 与 `BTreeSet<T>`（有序映射与集合）**：需要按键的大小顺序遍历或执行范围查询时，换用基于多路 B 树的 `BTreeMap<K, V>`；
- **`VecDeque<T>`（双端队列）**：`Vec<T>` 在头部增删需整体平移后方元素（`O(N)`），高频在首尾两端增删元素时使用基于环形缓冲区的 `VecDeque<T>`。
</Aside>
