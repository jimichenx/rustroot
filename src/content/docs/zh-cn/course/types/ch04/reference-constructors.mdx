在[引用](/memory/references/)与[悬垂引用](/memory/lifetimes/)中，我们从内存模型推演过为什么要借用、以及怎样在编译期防止悬垂引用，但还没有在真实代码中正式认识引用的读写语法。日常编码经常需要不转移所有权地读取数据，或者通过引用原地修改已有变量——例如向字符串末尾追加文本，或将计数器加 `1`。为此，Rust 提供了**共享引用 `&T`** 与**可变引用 `&mut T`**。

## 认识引用：基础读写与语法位置

先通过一段基础代码对比两种引用的日常写法：

```rust
let mut title = String::from("Rust");
let reader: &String = &title;
println!("read: {reader}");

let editor: &mut String = &mut title;
editor.push_str(" Root");
println!("updated: {title}");
```

在 Rust 中，**引用（Reference）**是一个保存目标内存地址的值，创建引用的动作叫**借用（Borrowing）**。对照上面的代码，起步先把握三条基础事实：

- **共享引用 `&T`（用 `&x` 创建）**：如 `let reader: &String = &title;`，只允许读取目标值而不移走所有权，原变量本身不必声明为可变；
- **可变引用 `&mut T`（用 `&mut x` 创建）**：如 `let editor: &mut String = &mut title;`，允许通过引用原地修改目标数据；回扣[可变与重新赋值](/memory/reassignment/)，要借出可变引用，原变量自身必须先声明为 `let mut`；
- **相同的运行时表示，都不承担释放责任**：以 64 位平台上指向编译期定长类型的引用为例（本章后续内存尺寸均以此为例，1 个机器字占 8 字节），`&T` 与 `&mut T` 的引用值本身都占 **8 字节**，保存目标位置的地址，离开作用域时都不释放目标数据。

再看声明引用时的一行典型代码 `let r: &mut i32 = &mut x;`，初学时常在这里混淆左右两侧的职责与语法分组：

- **左边是类型，右边是借用表达式**：冒号 `:` 后面的 `&mut i32` 是类型（Rust 没有 `mut i32` 这种可变类型修饰符，此处应拆读为由可变引用构造器 `&mut` 填入 `i32` 生成的 **`(&mut) i32`**，而非 `& (mut i32)`）；等号 `=` 右侧的 `&mut x` 是借用表达式，负责取出变量 `x` 的地址、构造一个 `&mut i32` 类型的值。
- **三个互不隶属的独立类型**：正如[类型构造器](/types/type-constructors/)所证明的，**`T`、`&T`、`&mut T` 是三个独立的类型**——把只读引用 `&i32` 传给要求 `&mut i32` 的变量或函数参数时，编译器会直接报类型不匹配错误（`error[E0308]: mismatched types`）。

看清基础写法后，顺着上面的代码往下走，本节重点解答三个问题：`let mut r` 和 `r: &mut T` 里的两个 `mut` 分别管什么？为什么读写借用放在一起有时通过、有时报 `E0502`？既然 `&i32` 与 `&mut i32` 的运行时表示完全一样，为什么一个能 `Copy`，另一个不能？

## 解引用 `*` 与两个位置的 `mut`

刚才对 `editor: &mut String` 调用 `.push_str(...)` 时，没有手写星号就修改了字符串——这是因为点号运算符 `.` 在调用方法或访问字段时会自动解引用（完整规则见[方法接收者三件套与自动解引用](/types/methods/)）。如果要直接读写 `m: &mut i32` 指向的整数本身，没有点号参与，就需要显式写出**解引用运算符 `*`（Dereference Operator）**。

对比变量名 `m` 与解引用 `*m` 指代的位置：直接写 **`m`**，代表引用变量自己存放 8 字节地址的槽位；加上星号写成 **`*m`**，则是顺着地址找到目标变量 `n` 的槽位。在原地读取与覆盖写入时，`*m = *m + 1;` 读写的正是 `n` 槽位里的值（区别在于引用不持有所有权，若目标是非 `Copy` 类型，不能通过 `*m` 把值移走）：

<Code code={derefRw} lang="rust" />

运行程序，依次输出 `read via *r: 7` 与 `updated n:   8`：`r` 的类型是 `&i32`，位置 `*r` 只允许读取；`m` 的类型是 `&mut i32`，`*m = *m + 1;` 直接将 `n` 的值改为 `8`。

变量 `r` 声明为不可变绑定 `let r`（未写 `let mut r`），执行 `*r += 1;` 依然正常编译并输出 `2` 与 `10`。两个 `mut` 管辖的位置互不交叉：

| `mut` 出现的位置 | 写法示例 | 管辖的权限 |
| --- | --- | --- |
| **1. `let` 后面（绑定属性）** | `let mut r: &i32 = &x;` | 管**变量 `r` 自身的槽位**能否换入新地址（后续能否写 `r = &y;` 改指其他变量） |
| **2. `:` 后面（类型构造器）** | `let r: &mut i32 = &mut x;` | 管**顺着 `r` 里的地址定位过去后**，能否修改 `*r` 处的值（能否写 `*r += 1;`） |

在 `two-mut.rs` 中，`r` 的类型是 `&mut i32`，通过 `*r += 1;` 修改 `x` 的值合法；但 `r` 自身是不可变绑定，取消 `// r = &mut y;` 的注释试图改指变量 `y`，就会触发 `error[E0384]: cannot assign twice to immutable variable r`。

一旦取消其中 `// println!("{r}");` 的注释，编译器立即报出 `error[E0502]`：

<small class="code-source">编译器输出摘要（取消 borrow-conflict.rs 中注释行后）</small>
```text
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
  --> types/representation-and-rules/src/bin/borrow-conflict.rs:15:26
   |
14 |     let r: &String = &s;
   |                      -- immutable borrow occurs here
15 |     let m: &mut String = &mut s;
   |                          ^^^^^^ mutable borrow occurs here
16 |     m.push_str(", world");
17 |     println!("{r}");
   |                - immutable borrow later used here
```

对照报错标注的三处位置与下方配图，可以把「借用冲突」与「悬垂引用」明确区分开：

1. **报错的直接原因是有效区间重叠，而非扩容悬垂**：回扣[悬垂引用](/memory/lifetimes/)，引用的有效区间算到它**最后一次被使用**的位置为止。第一段代码中，`r` 在 `println!("{r}");` 处使用完毕，共享访问随即结束，与后续 `m` 的可变访问互不重叠；第二段代码把 `println!("{r}");` 挪到下方后，`r` 的有效区间一直延续到末尾打印处，与中间 `m` 的可变访问发生了重叠。注意这里的 `r: &String` 指向的是变量 `s` 本身，并未直接指向内部堆缓冲区——即使 `push_str` 容量充足、没有触发扩容，只要后面还要用 `r`，这里仍会报 `E0502`（至于指向容器内部元素的引用为何可能因扩容而悬垂，留到[动态数组 `Vec<T>`](/types/vectors/)中验证）。
2. **编译器核对的是位置上的访问重叠，而非统计引用变量个数**：如果把借用规则记成「只存在唯一一个 `&mut T`」，常会误以为 Rust 只是在数引用变量——实际上，哪怕代码里只有 `m` 一个引用变量，只要在 `m` 的有效区间内直接写 `println!("{s}");` 读取原变量 `s`，同样会冲突。<span class="rr-keypoint">准确的规则是：对同一位置，任意时刻可以并存多条共享只读访问（`&T`），但排他的可变访问（`&mut T`）不能与任何其他访问在有效区间上重叠。</span>共享访问要求有效期内目标值保持稳定，可变访问要求有效期内自己拥有唯一的读写路径；编译器只按有效区间核对这两份契约，一旦重叠即拒绝编译。

## 为什么 `&mut T` 不实现 `Copy`

回到[类型的两面](/types/representation-and-constraints/)留下的问题：以 64 位平台上指向 `i32` 的引用为例，`&i32` 和 `&mut i32` 的运行时表示完全一样（都是 8 字节地址），为什么一个能 `Copy`，另一个不能？

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/same-size-diff-rules.rs</code></small>
<Code code={diffRules} lang="rust" />

取消 `// println!("{m1}");` 的注释后，编译器报出移动后借用错误：

<small class="code-source">编译器输出摘要（取消 same-size-diff-rules.rs 中注释行后）</small>
```text
error[E0382]: borrow of moved value: `m1`
  --> types/representation-and-rules/src/bin/same-size-diff-rules.rs:11:16
   |
 9 |     let m1: &mut i32 = &mut y;
   |         -- move occurs because `m1` has type `&mut i32`, which does not implement the `Copy` trait
10 |     let m2 = m1;
   |              -- value moved here
11 |     println!("{m1}");
   |                ^^ value borrowed here after move
```

落到代码中的 `let m2 = m1;`，先看清这里移动的到底是什么：**目标变量 `y` 原地不动，发生移动的是 `m1` 持有的引用值本身**。执行 `let m2 = m1;` 后，`m2` 接手了对 `y` 的排他可变访问，`m1` 在编译期状态表中标记为已失效，继续使用 `m1` 就会触发 `E0382`。

再反推一步：对只读引用执行 `let r2 = r1;` 按位复制地址后，多出一条只读访问路径符合共享规则；但如果 `&mut i32` 也实现 `Copy`，执行 `let m2 = m1;` 就会按位复制出第二份同时有效的 `&mut i32`——无需再次借用 `y`，仅凭一次变量赋值，同一位置上就会同时并存 `m1` 和 `m2` 两条活跃的可变访问路径，排他可变访问当场失效。

这也把[类型的两面](/types/representation-and-constraints/)与[类型构造器](/types/type-constructors/)建立的类型模型真正用在了具体规则上：`let mut y: i32` 里的 `mut` 只记录在变量绑定的状态表中，不改变类型本身（`y` 的类型仍是实现了 `Copy` 的 `i32`）；而 `&i32` 与 `&mut i32` 是由两个构造器生成的**独立类型**——它们在运行时擦除类型信息后都是同样的 8 字节地址，但标准库在编译期为所有 `&T` 实现了 `Copy`，对 `&mut T` 则不实现 `Copy`，从类型层面阻止排他访问被复制出第二份。

## 两种引用对照

| 对比维度 | 共享引用 `&T` | 可变引用 `&mut T` |
| --- | --- | --- |
| **构造器与类型身份** | 由 `&` 生成的**独立类型**（传给 `&mut T` 报 `E0308`） | 由 `&mut` 生成的**独立类型**（与 `T`、`&T` 互不隶属） |
| **运行时表示（64 位定长目标）** | 占 8 字节，保存目标地址 | 占 8 字节，保存目标地址 |
| **是否承担释放责任** | 否 | 否 |
| **解引用 `*r` 的权限** | 只读访问 | 读取与写入修改（`*m = new_val`） |
| **有效区间访问规则** | **共享**：同一位置可重叠多条只读访问 | **排他**：同一位置不能与其他访问重叠（冲突报 `E0502`） |
| **是否实现 `Copy`** | **是**（`let r2 = r1;` 复制地址，两者均有效） | **否**（`let m2 = m1;` 移动引用值，原引用失效报 `E0382`） |

留意对照表里运行时表示的前提条件——**「指向编译期定长类型时」**。`i32`、`String` 在编译期大小已知，引用只需 8 字节保存起始地址；如果要借用一段编译期长度未知的连续数据，单靠一个起始地址还够用吗？下一节先从长度已知的定长数组 `[T; N]` 开始。
