在[引用](/memory/references/)一节中，共享引用 `&T` 解决了「读取数据而不接手释放责任」的问题，但留下一道缺口：任何拿到 `&T` 的代码都不能修改目标数据。要通过引用修改数据，Rust 引入了可变引用 **`&mut T`**。

本节顺着上一章的「类型构造器 → 具体类型」公式，拆解 `&` 与 `&mut` 这两个内置构造器（局部引用填入的是编译器测算出的无名有效区间与目标类型 `T`，无需跨位置关联时不定义区间参数名）：为什么它们生成的具体类型在运行时都保存 8 字节内存地址，编译期约束却截然相反？

## 构造器的拆法：`(&mut) T`，而非 `&(mut T)`

初次见到 `&mut i32` 时，常会按字面顺序将它拆读成 **`& (mut i32)`**——误以为 `mut i32` 是一种「可变的 `i32` 类型」，外层再用 `&` 取引用。顺着这个误解写下 `let x: mut i32 = 7;`，编译器会直接报语法错误。

在 Rust 的类型系统中不存在 `mut T` 这种类型修饰符。正确的分组方式是 **`(&) T`** 与 **`(&mut) T`**：

- **`&`** 是共享引用构造器，填入 `i32` 合成出具体类型 `&i32`；
- **`&mut`** 是另一个独立的可变引用构造器，填入 `i32` 合成出具体类型 `&mut i32`。

在 `let m: &mut i32 = &mut n;` 这一行里，`&mut` 先后出现在两个不同的语法位置，对应两层概念：

- **写在冒号 `:` 后面、作用于类型 `T` 时**（`: &i32`、`: &mut i32`）：它是**类型构造器**，在编译期合成出名为「引用（Reference）」的具体类型；
- **写在等号 `=` 右侧、作用于变量 `n` 时**（`= &n`、`= &mut n`）：它是**借用运算符（Borrow Operator）**，执行的动作叫**借用（Borrowing）**——取出变量 `n` 的栈地址，构造一个对应引用类型的值。

动作叫「借用（`&n` / `&mut n`）」，产出的类型叫「引用（`&T` / `&mut T`）」。

## 解引用 `*`：从位置表达式理解 `*m` 与 `n`

`&i32` 和 `&mut i32` 在栈上保存的都是目标变量的 8 字节地址。拿到引用之后，如何顺着地址读写目标变量的值？

这需要先建立对**位置表达式（Place Expression）**的认识：有些表达式不用于计算临时结果，而是用来指代**内存中的一个具体槽位**。变量名 `n` 就是最直接的位置表达式，放在 `=` 左边表示向该槽位写入，放在右边表示从该槽位读取。

对引用变量 `m: &mut i32` 而言，直接写 **`m`** 指代的是引用变量自己在栈上的 8 字节槽位（里面装着地址）；要想指代目标整数所在的槽位，需要加上**解引用运算符 `*`（Dereference Operator）**——**`*m`** 表示顺着 `m` 保存的地址定位目标内存槽位。

因此，`*m` 与原变量名 `n` 指代的是内存里的同一个位置（完整规则可参阅附录「[位置表达式与值表达式](/appendix/mechanisms/place-and-value/)」），可以直接放在 `=` 左边修改目标值：

- `m` 的类型是 `&mut i32`，位置 `*m` 允许读写，`*m = *m + 1;` 直接将栈上 `n` 的值改为 `8`（回扣[可变与重新赋值](/memory/reassignment/)，要创建 `&mut n`，原变量自身须声明为 `let mut n`）。

<Aside type="note" title="为什么 r.id 和 r.len() 不用手动写 (*r)？">
上一章强调过 `User` 与 `&User`、`String` 与 `&String` 是互不混同的独立类型。既然 `r` 只是 8 字节地址、`*r` 才代表目标位置，为什么平时写 `r.id` 或 `r.len()` 时不需要写成 `(*r).id` 和 `(*r).len()`？

底层规则没有变，完整写法确实是 `(*r).id` 与 `(*r).len()`。为了避免日常访问字段和调用方法时满屏手写括号与星号，Rust 为**点号运算符 `.`** 提供了**自动解引用（Auto-deref）**：写下 `r.id` 时，编译器会自动补上 `*` 还原为 `(*r).id` 再核对类型；而直接向位置赋值（`*m = 8;`）没有点号参与，必须显式写出 `*`。点号调用方法时的完整解析过程将在[方法接收者三件套与自动解引用](/types/methods/)中展开。
</Aside>

变量 `r` 声明时写的是不可变绑定 `let r`，没有写 `let mut r`，但紧接着执行 `*r += 1;` 依然正常编译并输出 `2` 与 `10`。对照[可变与重新赋值](/memory/reassignment/)中的绑定可变性与本节的类型构造器，两个 `mut` 管辖的槽位互不交叉：

| `mut` 出现的位置 | 写法示例 | 管辖的权限 |
| --- | --- | --- |
| **1. `let` 后面（绑定属性）** | `let mut r: &i32 = &x;` | 管**变量 `r` 自身的 8 字节栈槽位**能否换入新地址（后续能否写 `r = &y;` 改指其他变量） |
| **2. `:` 后面（类型构造器）** | `let r: &mut i32 = &mut x;` | 管**顺着 `r` 里的地址定位过去后**，能否修改目标槽位的值（能否写 `*r += 1;`） |

在 `two-mut.rs` 中，`r` 的类型是 `&mut i32`，通过 `*r += 1;` 修改 `x` 的槽位合法；但 `r` 自身是不可变绑定 `let r`，一旦取消 `// r = &mut y;` 的注释试图改指变量 `y`，就会触发 `error[E0384]: cannot assign twice to immutable variable r`。

## 读写排他规则：为什么 `&T` 与 `&mut T` 不能并存

既然 `&T` 只读、`&mut T` 可写，如果针对同一个变量在同一有效区间内既有只读引用 `r: &String`，又有可变引用 `m: &mut String`，会发生什么？

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/borrow-conflict.rs</code></small>
<Code code={conflict} lang="rust" />

默认源码中，`r` 创建后未再使用，其有效区间在创建行即结束，随后创建 `m: &mut String` 调用 `m.push_str(", world")` 正常通过。一旦取消 `// println!("{r}");` 的注释，让 `r` 的有效区间跨越 `m` 的修改操作，编译器立即报出 `error[E0502]`：

<small class="code-source">编译器输出摘要（取消 borrow-conflict.rs 中注释行后）</small>
```text
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
```

顺着栈与堆的两跳结构推演，如果编译器放行读写区间重叠，运行时会暴露悬垂风险：

1. `s` 初始为 `"hello"`，假设堆缓冲区当前容量恰好为 5 字节（`cap = 5`）；`r: &String` 保存栈上 `s` 的地址，当读取方经由 `*r` 访问文本时（例如在函数调用如自追加 `s.push_str(&s)` 或并发读取过程中），已经顺着当时的 `s.ptr` 取出了那块 5 字节旧堆缓冲区的地址；
2. 同一区间内，`m.push_str(", world")` 写入 12 字节。一旦原位置后方空间不足，分配器就会在堆上另开一块新内存复制内容，**当场释放原 5 字节旧堆缓冲区**，并将 `s.ptr` 改指新地址；
3. 此时原先经由 `*r` 取出的旧堆地址已经指向被释放的内存，继续读取即造成**悬垂读取**。

<BorrowConflict />

为在编译期根除因扩容重分配或并发修改引发的内存失效与数据竞争，Rust 为 `&` 与 `&mut` 定下了**读写排他规则（Aliasing XOR Mutability）**：<span class="rr-keypoint">在同一个有效区间内，针对同一份数据，要么存在任意多个只读引用 `&T`（共享不可变），要么只存在唯一一个可变引用 `&mut T`（可变不共享）。</span>

## 为什么 `&mut T` 不实现 `Copy`

回到[类型的两面](/types/representation-and-constraints/)留下的现象：同样是栈上 8 字节地址，为什么 `&i32` 实现了 `Copy`，而 `&mut i32` 赋值时却触发移动？

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/same-size-diff-rules.rs</code></small>
<Code code={diffRules} lang="rust" />

假如 `&mut` 构造器也为生成的类型赋予 `Copy` 能力，执行 `let m2 = m1;` 按位复制 8 字节地址后，`m1` 与 `m2` 将同时保持有效——仅凭一行赋值，手里就会同时握着两个指向 `y` 的有效可变引用，「同一区间只准存在唯一一个 `&mut T`」的独占约束当场失效。

因此，两个引用构造器按各自的安全职责重写了 `Copy` 约束：

- **`&` 构造器（共享只读）**：多处同时只读互不干扰，为所有 `&T` 赋予 `Copy`；
- **`&mut` 构造器（独占可变）**：禁止出现第二个同时有效的副本，不为 `&mut T` 实现 `Copy`——执行 `let m2 = m1;` 时走移动语义，原引用 `m1` 立即失效（再用报 `E0382`）。

<Aside type="note" title="与 C/C++ 指针的差异：相同表示，不同编译期约束">
Rust 的 `&T` / `&mut T` 在运行时与 C/C++ 的指针 `const T*` / `T*` 一样是 8 字节地址，但编译期约束截然不同：C/C++ 裸指针允许为空（`nullptr`）、允许做 `p + 1` 地址偏移算术、允许目标释放后继续解引用，也允许多个可变指针同时修改同一内存；Rust 引用则保证非空对齐、禁止地址算术，并在编译期强制核对有效区间与读写排他。至于不带编译期安全约束的地址，在 Rust 中单独划分为**裸指针（`*const T` 与 `*mut T`）**。
</Aside>

## 两种引用对照与动手核对

| 对比维度 | 共享引用 `&T` | 可变引用 `&mut T` |
| --- | --- | --- |
| **栈上物理表示** | 8 字节地址（指向编译期定长类型时） | 8 字节地址（指向编译期定长类型时） |
| **是否承担释放责任** | 否 | 否 |
| **解引用 `*r` 的权限** | 只读访问 | 读取与写入修改（`*m = new_val`） |
| **编译期并存规则** | **共享**：同一区间可并存多个 `&T` | **独占**：同一区间仅限唯一一个 `&mut T`（冲突报 `E0502`） |
| **是否实现 `Copy`** | **是**（赋值复制 8 字节，两侧均有效） | **否**（赋值即移动，原引用失效报 `E0382`） |

### 动手核对

在 `borrow-conflict.rs` 中，如果把注释行 `println!("{r}");` **挪到 `let m: &mut String = &mut s;` 的正上方**（先创建并打印 `r`，再创建 `m` 修改字符串），程序能否通过编译？为什么？

核对结果：可以通过编译。借用检查器按引用**最后一次被使用的位置**计算有效区间：当 `println!("{r}");` 位于 `let m = &mut s;` 之前时，只读引用 `r` 在打印完毕后即告结束，与后续 `m` 的可变借用区间互不重叠，符合读写排他规则。

留意对照表第一行的前提条件——**「指向编译期定长类型时」**。`i32`、`String`、`User` 在编译期大小已知，指向它们的引用只需保存 8 字节起始地址；如果要借用一段编译期长度未知的连续数据，8 字节地址还够用吗？要看清长度信息的去向，下一节先从定长数组 `[T; N]` 开始。
