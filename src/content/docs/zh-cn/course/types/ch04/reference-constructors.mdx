在[引用](/memory/references/)一节中，共享引用 **`&T`** 解决了「读取数据而不接手释放责任」的问题，但拿到 `&T` 的代码只能读取、不能修改目标数据。日常编码经常需要通过引用原地更新原变量——例如向字符串末尾追加后缀，或将计数器加 `1`。为此，Rust 提供了**可变引用 `&mut T`**。

## `&T` 与 `&mut T` 的基本用法

先通过几行基础代码对比两种引用的日常写法：

```rust
let mut title = String::from("Rust");
let reader: &String = &title;
println!("read: {reader}");

let editor: &mut String = &mut title;
editor.push_str(" Root");
println!("updated: {title}");
```

对照上面的代码，日常起步先把握三点：

- **只读借用用 `&x`（类型写作 `&T`）**：如 `let reader: &String = &title;`，允许读取目标值而不移走所有权，原变量本身不必声明为可变；
- **可变借用用 `&mut x`（类型写作 `&mut T`）**：如 `let editor: &mut String = &mut title;`，允许通过引用原地修改目标数据；回扣[可变与重新赋值](/memory/reassignment/)，要借出 `&mut title`，原变量自身必须先声明为 `let mut title`；
- **都不接手释放责任**：以 64 位平台为例（1 个机器字占 8 字节，本章后续内存尺寸均以 64 位平台为例），指向编译期定长类型的 `&T` 与 `&mut T` 在栈上都只保存 8 字节内存地址，离开作用域时都不释放目标数据。

看懂基础读写后，顺着上面的代码继续往下看，会遇到三个关键问题：`&mut T` 里的 `mut` 为什么跟在 `&` 后面、和 `let mut` 有什么区别？为什么同时使用 `reader` 与 `editor` 会报错？同样是 8 字节地址，为什么 `&T` 能复制而 `&mut T` 赋值会移动？

## 构造器的拆法：`(&mut) T`，而非 `&(mut T)`

初次见到 `&mut i32` 时，常会按字面顺序将它拆读成 **`& (mut i32)`**——误以为 `mut i32` 是一种「可变的 `i32` 类型」，外层再用 `&` 取引用。顺着这个误解写下 `let x: mut i32 = 7;`，编译器会直接报语法错误。

在 Rust 的类型系统中不存在 `mut T` 这种类型修饰符。回扣[类型构造器](/types/type-constructors/)中的生成公式，正确的分组方式是 **`(&) T`** 与 **`(&mut) T`**（局部引用同时隐式填入编译器测算出的无名有效区间）：

- **`&`** 是共享引用构造器，填入 `i32` 合成出具体类型 `&i32`；
- **`&mut`** 是另一个独立的可变引用构造器，填入 `i32` 合成出具体类型 `&mut i32`。

由两个不同的构造器分别生成，决定了 **`T`、`&T`、`&mut T` 是三个平级、互不隶属的独立类型**，而非在同一个类型上增减权限修饰符。把只读引用 `&i32` 传给要求 `&mut i32` 的变量或函数参数时，编译器报出的是直接的**类型不匹配错误（`error[E0308]: mismatched types`）**（反过来在明确接收 `&T` 的位置传入 `&mut T` 之所以能通过，是因为编译器支持从独占可变引用向只读引用的单向转换，并非二者属于同一类型）。

在 `let m: &mut i32 = &mut n;` 这一行里，`&mut` 先后出现在两个不同的语法位置，对应两层概念：

- **写在冒号 `:` 后面、作用于类型 `T` 时**（`: &i32`、`: &mut i32`）：它是**类型构造器**，在编译期合成出名为「引用（Reference）」的具体类型；
- **写在等号 `=` 右侧、作用于变量 `n` 时**（`= &n`、`= &mut n`）：它是**借用运算符（Borrow Operator）**，执行的动作叫**借用（Borrowing）**——取出变量 `n` 的栈地址，构造一个对应引用类型的值。

## 解引用 `*` 与两个位置的 `mut`

刚才对 `editor: &mut String` 调用 `.push_str(...)` 时，点号运算符自动顺着地址找到了目标字符串；如果要直接读写 `m: &mut i32` 指向的整数本身，则需要用到**解引用运算符 `*`（Dereference Operator）**。

先从「内存槽位」看懂普通变量名：平时写 `n = n + 1;` 时，变量名 **`n`** 直接代表栈上存放整数的那个槽位——放在 `=` 右边是从该槽位读出旧值，放在 `=` 左边是把算好的新值写回该槽位。

引入引用变量 `m` 后，栈上有了两个槽位：直接写变量名 **`m`**，代表的是 `m` 自己存放 8 字节地址的槽位；加上星号写成 **`*m`**，则是顺着地址找过去，直接代表目标变量 `n` 的那个槽位。在原地读取与覆盖写入时，可以把 `*m` 当作原变量 `n` 本身来使用——写下 `*m = *m + 1;`，读写的正是 `n` 的槽位（区别仅在于引用不持有所有权，若目标是非 `Copy` 类型，不能通过 `*m` 把值移走）：

<Aside type="note" title="为什么 editor.push_str(...) 和 r.len() 不用手动写 (*r)？">
既然 `r` 保存的是地址、`*r` 才代表目标槽位，为什么访问字段或调用方法时不需要写成 `(*r).id` 和 `(*editor).push_str(...)`？为了免去日常满屏手写括号与星号，Rust 为**点号运算符 `.`** 提供了**自动解引用（Auto-deref）**：写下 `r.id` 时，编译器会自动补上 `*` 还原为 `(*r).id`；而直接向槽位赋值（`*m = 8;`）没有点号参与，必须显式写出 `*`。点号调用方法的完整解析规则将在[方法接收者三件套与自动解引用](/types/methods/)中展开。
</Aside>

## 读写排他规则：为什么借用区间不能重叠

既然 `&T` 只读、`&mut T` 可写，如果针对同一个变量 `s`，在共享引用 `r: &String` 仍要继续使用的期间创建可变引用 `m: &mut String`，会发生什么？

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/borrow-conflict.rs</code></small>
<Code code={conflict} lang="rust" />

默认源码中，`r` 在第 4 行创建后未再使用，其有效区间（按最后一次使用位置计算）当行即结束，随后第 5 行创建 `m: &mut String` 修改字符串正常通过。一旦取消第 7 行 `// println!("{r}");` 的注释，编译器立即报出 `error[E0502]`：

<small class="code-source">编译器输出摘要（取消 borrow-conflict.rs 第 7 行注释后）</small>
```text
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> types/representation-and-rules/src/bin/borrow-conflict.rs:5:26
  |
4 |     let r: &String = &s;
  |                      -- immutable borrow occurs here
5 |     let m: &mut String = &mut s;
  |                          ^^^^^^ mutable borrow occurs here
6 |     m.push_str(", world");
7 |     println!("{r}");
  |                - immutable borrow later used here
```

对照报错标注的三处位置，看清这次拦截的直接原因与底层动机：

1. **`E0502` 的直接原因（有效区间重叠）**：在这段代码中，`r: &String` 指向栈上的变量 `s` 本身，并未直接保存旧堆缓冲区地址。报错的原因是第 7 行仍要读取 `r`，使 `s` 的共享借用区间从第 4 行一直延续到第 7 行；而第 5 行 `let m = &mut s;` 试图在这段区间内取得 `s` 的**排他可变访问**——两段借用区间发生重叠，借用检查器当场拒绝编译；
2. **规则保护的底层风险**：为什么语言必须禁止共享借用与可变借用重叠？一旦某处代码已经借出了指向容器内部数据的只读地址（如切出字符串片段、借用数组元素，或在多线程下并发读取），此时若允许另一处可变引用修改内容甚至触发堆扩容释放旧内存，原有的只读地址就会立即失效或引发数据竞争（内部元素引用因扩容悬垂的真实案例，将在[动态数组 `Vec<T>`](/types/vectors/)中验证）。

<BorrowConflict />

为此，Rust 为 `&` 与 `&mut` 定下了编译期的**读写排他规则（Aliasing XOR Mutability）**：<span class="rr-keypoint">在同一个有效区间内，针对同一份数据，要么存在任意多个只读引用 `&T`（共享不可变），要么只存在唯一一个可变引用 `&mut T`（可变不共享）。</span>

## 为什么 `&mut T` 不实现 `Copy`

回到[类型的两面](/types/representation-and-constraints/)留下的现象：同样保存 8 字节地址，为什么 `&i32` 实现了 `Copy`，而 `&mut i32` 赋值时却触发移动？

<small class="code-source">源文件：<code>examples/types/representation-and-rules/src/bin/same-size-diff-rules.rs</code></small>
<Code code={diffRules} lang="rust" />

取消第 11 行 `// println!("{m1}");` 的注释，编译器会报出移动后使用错误：

<small class="code-source">编译器输出摘要（取消 same-size-diff-rules.rs 第 11 行注释后）</small>
```text
error[E0382]: borrow of moved value: `m1`
  --> types/representation-and-rules/src/bin/same-size-diff-rules.rs:11:16
   |
 9 |     let m1: &mut i32 = &mut y;
   |         -- move occurs because `m1` has type `&mut i32`, which does not implement the `Copy` trait
10 |     let m2 = m1;
   |              -- value moved here
11 |     println!("{m1}");
   |                ^^ value borrowed here after move
```

假如 `&mut` 构造器也为生成的类型赋予 `Copy`，执行 `let m2 = m1;` 按位复制地址后，`m1` 与 `m2` 将同时保持有效——仅凭一行赋值，手里就会同时握着两个指向 `y` 的有效可变引用，「同一区间只准存在唯一一个 `&mut T`」的独占约束当场失效。

这里再次体现了「独立类型」与「绑定属性」的分工：`let mut y: i32` 里的 `mut` 只记录在变量绑定的状态表中，不改变类型本身（`y` 的类型仍是实现了 `Copy` 的 `i32`）；而 `&i32` 与 `&mut i32` 是**两个独立的类型**，标准库按具体类型挂载 Trait——为所有 `&T` 实现 `Copy`，对 `&mut T` 则不实现 `Copy`，令 `let m2 = m1;` 走移动语义使原引用失效。

<Aside type="note" title="与 C/C++ 指针的差异：相同表示，不同编译期约束">
Rust 的 `&T` / `&mut T` 在运行时与 C/C++ 的指针 `const T*` / `T*` 一样保存内存地址，但编译期约束截然不同：C/C++ 指针允许为空（`nullptr`）、允许做 `p + 1` 地址算术、允许目标释放后继续解引用，也允许多个可变指针同时修改同一内存；Rust 引用则保证非空对齐、禁止地址算术，并在编译期强制核对有效区间与读写排他。不带编译期安全约束的地址在 Rust 中单独划分为**裸指针（`*const T` 与 `*mut T`）**。
</Aside>

## 两种引用对照与动手核对

| 对比维度 | 共享引用 `&T` | 可变引用 `&mut T` |
| --- | --- | --- |
| **构造器与类型身份** | 由 `&` 生成的**独立类型**（传给 `&mut T` 报 `E0308`） | 由 `&mut` 生成的**独立类型**（与 `T`、`&T` 互不隶属） |
| **栈上物理表示（64 位）** | 8 字节地址（指向编译期定长类型时） | 8 字节地址（指向编译期定长类型时） |
| **是否承担释放责任** | 否 | 否 |
| **解引用 `*r` 的权限** | 只读访问 | 读取与写入修改（`*m = new_val`） |
| **编译期并存规则** | **共享**：同一区间可并存多个 `&T` | **独占**：同一区间仅限唯一一个 `&mut T`（冲突报 `E0502`） |
| **是否实现 `Copy`** | **是**（赋值复制地址，两侧均有效） | **否**（赋值即移动，原引用失效报 `E0382`） |

### 动手核对

对照上方的配图左栏，在 `borrow-conflict.rs` 中将 `println!("{r}");` **挪到 `let m: &mut String = &mut s;` 的正上方**（先创建并打印 `r`，再创建 `m` 修改字符串），程序能否通过编译？为什么？

核对结果：可以通过编译。借用检查器按引用**最后一次被使用的位置**计算有效区间：当 `println!("{r}");` 位于 `let m = &mut s;` 之前时，共享引用 `r` 在打印完毕后即告结束，与后续 `m` 的可变借用区间互不重叠，符合读写排他规则。

留意对照表物理表示一栏的前提条件——**「指向编译期定长类型时」**。`i32`、`String` 在编译期大小已知，引用只需保存起始地址；如果要借用一段编译期长度未知的连续数据，单靠一个地址还够用吗？下一节先从定长数组 `[T; N]` 开始。
