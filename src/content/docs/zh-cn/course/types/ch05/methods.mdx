上一节用 `struct` 将多个字段组合成了自定义类型，但 `struct` 花括号内只声明数据布局，不写任何方法。

在 Java 或 Python 中，实例方法挂在堆对象上，通常依赖隐藏的对象头与虚表（`vtable`）在运行时寻址，并且自带隐式的 `this` / `self` 指针。而在 Rust 中，上一节刚实测过结构体采用扁平内联布局、没有任何隐藏对象头——既然内存里只有纯数据，方法究竟挂在哪里？编译器又如何知道某个方法只读取字段、修改字段还是直接取走内部资源？

答案在于：Rust 将**数据定义（`struct`）与行为实现（`impl`）分开书写**，把方法还原为挂载在类型名命名空间下的普通函数，并要求首个参数显式写出访问权限。

## `impl` 块与关联函数

要为结构体 `TextBuffer` 挂载函数，使用 **`impl`（实现，implementation）**关键字开启实现块。

在 Java 中，`class` 把字段和全部方法锁死在同一个花括号与同一个文件里，业务一多就会长成数千行的巨型类。Rust 将数据与行为拆开后，类型与 `impl` 块变成了 **`1:N`（含 `0`）**关系：纯数据结构体可以不写 `impl`；复杂类型则可以按职责拆成多个独立的 `impl TextBuffer` 块，甚至分散在当前包的不同模块文件中，编译时统一合并到同一类型名下。

这种多块组织不仅避免了单文件膨胀，也为后续按不同泛型条件或契约分块挂载行为留出了空间。传统 `class` 的职责捆绑与 Rust 的拆分细节，见附录「[没有 `class` 的对象感](/appendix/comparisons/oop/)」。

在 `impl` 块内部，定义的所有函数统称**关联函数（Associated Functions）**——字面意思就是「与当前类型关联的函数」。按首个参数是否为 `self`，它们在日常称呼与调用方式上分为两类：

它挂在类型名这个命名空间下，不依赖任何已有实例，调用时必须写**类型名加双冒号 `::`**，例如 `TextBuffer::new("[INFO] ")`（前文见过的 `String::from("hi")` 与 `Vec::new()` 均属此类）。与允许对实例调静态方法的 Java 不同，Rust 严格区分类型路径 `::` 与实例调用 `.`。

此外，Rust 没有 `new` 构造函数关键字，工程上约定用名为 `new`（或 `with_capacity`、`from_...`）的关联函数构造新实例。

<Aside type="note" title="大写 Self 与小写 self，以及成本命名惯例">
在 `impl TextBuffer` 内部，首字母大写的 **`Self`** 是当前目标类型 `TextBuffer` 的内置别名（写 `-> Self` 与 `Self { ... }` 等同于写 `TextBuffer`）；全小写的 **`self`** 则是方法首个参数的名字，指代调用该方法的实例。此外，社区约定将所有权成本写进方法名前缀（只读视图用 `as_`、复制新数据用 `to_`、消费所有权转换用 `into_`，读取字段不加 `get_` 前缀），完整对照见附录「[Rust 命名约定与工程惯例速查](/appendix/basics/conventions/)」。
</Aside>

### 方法：接收者 `&self`、`&mut self` 与 `self`

首个参数为 `self`、`&self` 或 `&mut self` 的关联函数特称为**方法（Methods）**，对实例用点号 `.` 调用（如 `buf.len()`）。

在物理本质上，<span class="rr-keypoint">固有方法并不是「长在对象内存里的特殊构件」，它只是把目标类型实例作为第 1 个参数的普通关联函数。</span>编译器在编译期直接把 `buf.append("ok")` 静态解析为函数调用 `TextBuffer::append(&mut buf, "ok")`——直接跳转到固定机器码地址，既不需要对象头，也没有运行时查表开销。

在 Java 中，隐式的 `this` 始终具备读写权限，仅看一行方法签名无法判断调用它是否会改动状态。Rust 则把首个参数（称为**接收者 Receiver**）变成编译期的权限声明，直接对应[类型构造器](/types/type-constructors/)与[引用与可变引用](/types/reference-constructors/)确立的三个独立类型：

| 接收者简写 | 等价完整签名 | 所有权与借用规则 | 调用后原实例状态 | 典型工程用途 |
| --- | --- | --- | --- | --- |
| **`&self`** | `self: &Self` | 共享只读借用 | 继续有效 | 读取字段、计算派生结果（如 `len()`、`is_empty()`） |
| **`&mut self`** | `self: &mut Self` | 独占可变借用 | 继续有效（要求绑定声明 `let mut`） | 原地更新字段、增删元素（如 `append()`、`push()`） |
| **`self`** | `self: Self` | 按值接手所有权（非 `Copy` 则移动） | **已失效（被消费）** | 零分配移交内部资源（如 `into_string()`）或一次性终结操作 |

### 消费型 `self` 的两项工程能力

前两种借用接收者（`&self` 与 `&mut self`）对应常规的只读与原地修改；而第三种按值接手的 **`self`**，在传统带隐式 `this` 的语言中根本无法表达——在 Java 里，对象方法无法在签名上声明「调用完我之后，原变量立即作废」。

把所有权转移放进接收者位置，直接解锁了两项编译期能力：

1. **零堆复制移交内部资源**：观察上面的 `into_string(self) -> String`。如果接收者写成 `&self`，由于不能从借用背后移走字段，就只能调用 `self.content.clone()` 在堆上重新分配并复制一份字符串；而写成按值接收的 **`self`**，`buf` 的所有权直接移入方法内部，`self.content` 可以原封不动地移交出去——只移动栈上 24 字节控制头，堆缓冲区一字节不抄。标准库的 `String::into_bytes(self) -> Vec<u8>` 能在零内存分配下把字符串直接拆成字节数组，靠的正是这一机制。
2. **编译期封死「终结后误用（Use-After-Close）」**：网络连接、文件写入器或事务句柄在调用 `close(self)`、`commit(self)` 终结使命时，按值接手 `self` 会让原变量在调用行之后立即失效；任何后续误调都会在编译期被直接拦截，无需在每个方法开头手写 `if (this.isClosed)` 运行时检查（后续在[`Typestate` 模式](/architecture/typestate-pattern/)中还会将它扩展为编译期状态机）。

## 点号调用的自动借用与解引用

既然方法本质上就是首个参数为 `Self`、`&Self` 或 `&mut Self` 的普通函数，而这三个类型又彼此独立，为什么拿着值 `v` 可以直接写 `v.push(4)`，拿着双层引用 `rr: &&Counter` 也能直接写 `rr.get()`，而不必每次手写 `(&mut v).push(4)` 或 `(**rr).get()`？

原因是编译器在**点号 `.` 操作符**处内置了双向语法糖：对照目标字段或方法接收者的签名，自动在点号左侧表达式上补齐所需的 **`&` / `&mut`（自动借用 Autoref）**或 **`*`（自动解引用 Autoderef）**，再还原为底层函数调用。

```text

```

拆开两个方向即可看清编译器生成的等价代码：

1. **自动借用（手里是值 `T`，方法要求 `&T` 或 `&mut T`）**：写下 `v.push(4)` 时，编译器查到 `Vec::push` 的接收者是 `&mut self`，自动补上 `&mut`，展开为等价的 `(&mut v).push(4)`，最终对应函数调用 **`Vec::push(&mut v, 4)`**。
2. **自动解引用（手里是单层或多层引用，需剥壳匹配）**：用引用访问字段 `r.count` 自动展开为 `(*r).count`；对双层引用调用 `rr.get()` 自动补一层 `*` 得到 `&Counter`，最终对应 **`Counter::get(*rr)`**。

正因为点号 `.` 同时具备双向适配能力，Rust 取消了 C / C++ 区分值访问（`.`）与指针访问（`->`）的两套运算符，无论手里持有值还是引用，统一使用 `.` 访问。

## 点号适配的安全边界

<span class="rr-keypoint">点号 `.` 只负责在语法层面代写 `&`、`&mut` 与 `*`，展开后的底层函数调用依然逐条接受所有权与借用检查器的审查。</span>判断任意一行 `x.method()` 能否编译，只需将它还原为 `Type::method(...)`：

### 不可变绑定借不出 `&mut self`

回到[可变与重新赋值](/memory/reassignment/)留下的问题：为什么 `let v: Vec<i32> = Vec::new();` 不加 `mut` 时，连修改内部数据的 `v.push(1)` 都不能调用？

<small class="code-source">源文件：<code>examples/types/methods/src/bin/missing-mut.rs</code></small>
<Code code={missingMut} lang="rust" />

<small class="code-source">编译器输出摘要（取消 missing-mut.rs 第 4 行注释后）</small>
```text
error[E0596]: cannot borrow `v` as mutable, as it is not declared as mutable
 --> types/methods/src/bin/missing-mut.rs:4:5
  |
3 |     let v: Vec<i32> = Vec::new();
  |         - help: consider changing this to be mutable: `mut v`
4 |     v.push(1);
  |     ^ cannot borrow as mutable
```

将调用还原后原因很直接：`v.len()` 展开为 `Vec::len(&v)`（只需只读借用 `&self`），而 `v.push(1)` 展开为 **`Vec::push(&mut v, 1)`**——`v` 未声明为 `let mut`，编译器拒绝从不可变绑定借出 `&mut v`。同理，在[动态数组 `Vec<T>`](/types/vectors/)中持有元素借用 `let first = &v[0];` 期间调用 `v.push(4)`，也是因为展开后的 `Vec::push(&mut v, 4)` 与活跃的只读借用 `first` 冲突而触发 `E0502`。

### 引用背后调不了消费型 `self`

若方法接收者是按值消费所有权的 **`self`**（如前面提到的 `String::into_bytes(self)`），而调用方手里只有共享引用 `r: &String`：

<small class="code-source">源文件：<code>examples/types/methods/src/bin/consume-through-ref.rs</code></small>
<Code code={consumeThroughRef} lang="rust" />

<small class="code-source">编译器输出摘要（取消 consume-through-ref.rs 第 6 行注释后）</small>
```text
error[E0507]: cannot move out of `*r` which is behind a shared reference
 --> types/methods/src/bin/consume-through-ref.rs:6:17
  |
6 |     let bytes = r.into_bytes();
  |                 ^ ------------ `r.into_bytes()` takes ownership of the receiver `self`, which moves `*r`
  |                 |
  |                 move occurs because `*r` has type `String`, which does not implement the `Copy` trait
```

点号自动解引用将 `r.into_bytes()` 还原为 **`String::into_bytes(*r)`**，试图从共享引用 `r` 背后把未实现 `Copy` 的 `String` 移走，直接被「引用不承担释放责任、禁止移出目标值」的规则拦截；唯有真正的所有者 `s` 才能调用 `s.into_bytes()` 移交底层字节缓冲区。

用下面这段检票代码检验还原规则：

```rust
struct Ticket { id: u32 }

impl Ticket {
    fn inspect(&self) -> u32 { self.id }
    fn redeem(self) -> u32 { self.id }
}

fn check(t: &Ticket) {
    println!("{}", t.inspect());
    // let id = t.redeem();
}
```

这里 `t.inspect()` 等价于 `Ticket::inspect(t)`，编译通过；而取消 `let id = t.redeem();` 的注释会报 `error[E0507]`——它等价于 `Ticket::redeem(*t)`，默认未实现 `Copy` 的 `Ticket` 不能从共享引用背后被移走。

把这里的 `*t` 与上一节的 `user.name`、上一章的 `names[0]` 放在一起对比：它们都指向内存里的一块已有数据，为什么 `user.name` 允许把值移走，而 `names[0]` 和 `*t` 却被拒绝？下一节将表达式拆分为「指明位置」与「算出新值」两类，把读写、借用与移动限制归入同一套规则。
