## 我们要解决的问题

第一篇我们一直在设计一门语言。到 1.7，它有了五条规则：每个值有一个所有者；同一时刻只有一个；所有者离开作用域时释放；借用必须比所有者短；共享不可变，可变不共享。

五条规则说的都是名字：名字离开作用域就释放，名字赋值就移动，名字借出引用。还有一件事没定：在这门语言里，名字怎么声明出来？

你熟悉的语言多半这样做：`int x;`、`var x = ...`，声明一个变量。变量像一个贴着名字的盒子，可以先造出来空着，里面的东西随时能换，拿到它的代码都能改。我们先照这个样子设计，逐条对一下规则。

## 第一版：变量是一个盒子

盒子模型有三个默认：

1. 盒子可以先造出来，里面暂时空着；
2. 里面的东西随时能换成别的；
3. 盒子默认可写。

### 空盒子离开作用域

规则 3 说：名字离开作用域时，释放它的值。

盒子若还空着，释放什么？C 的局部变量声明之后没赋值，里面装着这块栈空间上次留下的字节。按规则 3 去释放它，就是把一串随机字节当成堆地址还给系统。

我们的语言只能这样定：名字离开作用域时，编译器要知道它此刻有没有值。有，就释放；没有，就跳过。读取也一样：读一个名字之前，编译器要能证明它已经有值。

这条要求不禁止先声明、后赋值。只要每一条路径都赋了值，编译器就证明得出来。

### 移动之后，盒子空了

1.3 的移动让原来的名字失效。用刚才的说法再看一遍：`b = a` 之后，`a` 回到了没有值的状态。

编译器本来就要在每一行知道「这个名字此刻有没有值」。移动只是让答案又一次变成「没有」。所以读一个从没赋过值的名字，和读一个值已经被移走的名字，是同一种错误，由同一套跟踪挡住。

反过来也成立：移动之后再给这个名字赋一个新值，它又有了值，又能用了。

### 默认可写

1.4 说：可变引用同一时刻只能有一份，有它的时候不能再有别的引用。在这门语言里，写比读贵：读可以同时有很多份，写要独占。

盒子默认可写，每个名字就都可能被改、都可能借出 `&mut`。读代码的人看声明，分不出哪些名字会被改；编译器也要把每个名字都当作可能借出 `&mut` 来检查。

我们把默认反过来：名字默认只读。要重新赋值、要借出 `&mut`，在声明时写出来。贵的那一种，写在明处。

## 第二版：绑定

三处修改之后，名字已经不是盒子了：

- 名字连着一个值。在每一行，编译器都知道它此刻有没有值，没有值就不能读。
- 值被移走，名字回到没有值的状态；再赋一个值，又能用。
- 默认只读。要重新赋值、要借出 `&mut`，声明时写 `mut`。

名字和值的这种对应，这一课给它定名：**绑定（Binding）**。Rust 用 `let` 声明一个绑定。

  Java 的局部变量也要先赋值再读。字段不一样：没赋值的引用字段默认是 `null`。Rust 没有这种默认值，一个 `String` 类型的绑定要么有一个 `String`，要么编译器知道它没有。「可能没有」要写进类型，6.1 讲。
</Aside>

## 顿悟时刻

名字不是盒子，是绑定：使用前必须有值，移动之后等于没有值，默认只读。这三条都是第一篇的规则逼出来的。

还剩一个问题。编译器每遇到一次 `b = a`，都要按切割线判断复制还是移动。可切割线看的是运行时字节里有没有堆，编译器在编译期看不到运行时的字节。它凭什么判断？下一课从这里开始。
