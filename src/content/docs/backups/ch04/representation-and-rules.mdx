## 我们要解决的问题

上一课留下一个问题：每一次 `b = a`，编译器都要判断复制还是移动。切割线看的是字节里有没有要负责释放的堆，可编译期没有运行时的字节。

编译期手里有的，是每个名字的类型。类型能告诉编译器什么？

## 第一版：看布局

每个类型的布局在编译期就定了：占几个字节，每个字节是什么。`i32` 是 4 个字节的整数，`String` 是一个堆地址、一个长度、一个容量。

那就让编译器看布局：布局里有地址，说明指着一块堆，赋值时移动；没有地址，赋值时复制。这是切割线的编译期版本。`i32` 复制，`String` 移动，和上一课的结果一致。

拿更多的类型来试。

### 撞墙一：借来的地址

`&i32` 的布局里只有一个地址。按第一版，它该移动。

可 1.4 设计引用时说过：引用不负责释放。两个名字抄着同一个引用，谁离开作用域都不释放它指着的数据，释放时刻仍然唯一。它可以复制。

布局里都是一个地址。一个要负责释放，一个不负责，布局上看不出来。

### 撞墙二：可写的地址

`&mut i32` 的布局和 `&i32` 一模一样，也不负责释放。照撞墙一的修正，它该复制。

可 1.4 规定：可变引用同一时刻只能有一份。复制一份 `&mut i32`，就同时有了两份可写的引用，读写排他被打穿。它不能复制。

### 撞墙三：没有地址，也要唯一

<Code code={fileHandle} lang="rust" />

在 Linux 和 macOS 上，这个程序打印 `File: 4 bytes`。`File` 里只有操作系统给的一个编号，叫文件描述符，布局里没有地址。按第一版，它该复制。

文件用完要关闭，关闭只能做一次。两个名字都拿着这个编号，先离开作用域的那个关掉文件，另一个手里的编号就指着一个已经关闭的文件。这和 1.3 里两个名字抄同一个堆地址是同一种事故。它移动了：取消最后一行的注释，报 `error[E0382]`。

1.2 说过，堆和打开的文件一样，是用完必须归还的资源。切割线说「堆」，准确的说法是「要释放的资源」。资源不一定藏在一个地址后面。

<Aside type="note" title="补充基础">
  Windows 上 `File` 装的是一个句柄，大小和 Linux、macOS 不同。结论不变：布局里没有堆地址，赋值仍然移动。
</Aside>

### 撞墙四：布局一样，能装的不一样

`String` 和 `Vec<u8>` 都是 24 字节：地址、长度、容量，堆上都是一串字节。布局一模一样。

`String` 多一条约定：它的字节必须是合法的 UTF-8。`String::from_utf8` 收下一个 `Vec<u8>`，先检查，合法才交出一个 `String`。`0xff 0xfe` 不合法，`is_ok()` 打印 `false`。这次检查的结果是一个 `Result`，6.3 再讲。

布局相同，这两个类型能装的字节不同，能调的方法也不同。

## 第二版：类型带上规矩

四堵墙说的是同一件事：布局只回答「这段字节怎么读」，回答不了「这个值能拿来做什么、谁负责」。

编译器要的另一半，只能写进类型本身：

- 负不负责释放什么；
- 允不允许复制；
- 能不能沿着它写；
- 字节要满足什么约定。

类型因此有两半。**表示**回答这段字节怎么读：多大、怎么对齐、每一位什么意思。**规矩**回答对这个值能做什么、谁负责：权限、责任、寿命、约定。

| 类型 | 表示 | 规矩 |
| :--- | :--- | :--- |
| `&i32` | 一个机器字：地址 | 不负责释放；只读；可以复制 |
| `&mut i32` | 一个机器字：地址 | 不负责释放；可写；同一时刻只能有一份 |
| `File` | 一个编号 | 负责关闭文件；不能复制 |
| `Vec<u8>` | 地址、长度、容量 | 负责释放堆；里面是任意字节 |
| `String` | 地址、长度、容量 | 负责释放堆；里面必须是 UTF-8 |

前两行表示相同，后两行表示相同，差别全在规矩一列。编译器判断复制还是移动，查的是规矩，不是布局。

切割线也跟着修正两处。第一，要负责的是一切要释放的资源，不只是堆。第二，没有释放责任只是能复制的必要条件：`&mut i32` 满足它，仍然不能复制。允不允许复制，是类型的规矩。

<Aside type="tip" title="如果你来自 C 或 Java">
  C 的类型基本只有表示：`int *` 说这是一个地址，不说谁负责释放它、能不能写它指着的东西。Java 的类型说有哪些字段和方法，释放交给 GC，所以类型里没有「谁负责释放」「此刻能不能写」的写法。Rust 把这些都写进了类型，编译器才能在编译期检查它们。
</Aside>

## 「可写」写在哪

规矩里有一条是「能不能写」。它写在什么地方？

**只写在名字上。** 名字声明成 `mut`，就能改。可把 `&x` 交给一个函数，函数的形参拿到的只是一个地址，名字上的 `mut` 带不过去，函数不知道能不能沿着这个地址写。「能不能写」得跟着引用走，写进引用的类型：`&mut i32`。

**只写在引用的类型上。** 那所有者自己呢？`let x = 1; x = 2;` 没有经过任何引用，是在给绑定重新赋值。这件事还得写在绑定上。

所以 `mut` 有两个位置，各管一件事：

- **绑定上的 `mut`**：这个名字能不能重新赋值，能不能借出 `&mut`。
- **类型里的 `mut`**：沿着这个引用能不能写。

「这个变量是 `mut` 的，所以能改」这句话压着两件事。5.3 会看到，一次 `v.push(4)` 要把两件都凑齐。

## 规则写进了类型

回头看第一篇的五条规则，它们都落到了类型上：

| 第一篇的规则 | 在类型里写成 |
| :--- | :--- |
| 每个值有一个所有者，同一时刻只有一个 | 负责释放资源的类型不能复制，赋值就移动 |
| 离开作用域时释放 | 负责释放的类型，离开作用域时由编译器替它释放 |
| 借用必须比所有者短 | 引用的类型带着它能活多久，7.3 写出来 |
| 共享不可变，可变不共享 | `&T` 和 `&mut T` 是两个类型，后者不能复制 |

哪个名字负责释放、哪个引用能写，不再要你记在脑子里。它们写进了类型，编译器对每一次赋值、每一次调用核对。类型系统是第一篇规则的执行机构。

<Aside type="note" title="补充基础">
  规矩只在编译期存在。`&i32` 和 `&mut i32` 生成的机器码可以完全相同，运行时的内存里没有「这个引用可写」的标记。
</Aside>

## 类型是实体，不是标签

这一课的表格里还藏着一个判断。`&i32` 和 `&mut i32` 表示相同、规矩不同，是两个类型；`String` 和 `Vec<u8>` 表示相同、约定不同，也是两个类型。类型的身份（Identity）由两半一起决定——身份属于类型自己，不属于它贴着的那个值。

推到底就是：类型不是贴在值上的标签，是有身份的实体。`i32`、`&i32`、`&mut i32` 是三个类型，差别程度和 `String` 与 `Vec<u8>` 之间一样。这一篇会反复遇到这三个类型：5.3 看它们写进签名，7.3 看它们带上参数，7.4 看它们各自拥有实现。

如果你从 Java 来，这里多半站着你初学时的那堵墙。Java 的类型更像标签：回答「这个值有哪些字段和方法」；值一律通过引用访问，「值」和「指向值的引用」在类型上不分家。三个类型在那套读法里是重复——一个东西，三张标签。

所以初学时觉得 Rust 不讲道理，多半不是理解力的问题，是标签观在工作：那套模型里没有「权限」这根轴，这些规矩在旧模型里找不到对应物，读出来只能是武断。这一篇做的事是把标签换成实体——不是要记更多规则，是给类型补上身份这一半，让规矩有处可落。

## 顿悟时刻

编译器判断复制还是移动，查的不是字节长什么样，是类型的规矩。类型有两半：表示说字节怎么读，规矩说能做什么、谁负责。

规矩为什么这么多？设想一个程序，所有数据的大小和寿命都在编译期定死，全在栈上：作用域就够了，不需要所有者，也不需要移动。规矩是为「要到运行时才知道」的东西立的。下一课改一个条件：长度要到运行时才知道。
