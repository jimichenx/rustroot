## 我们要解决的问题

这一篇我们接着设计这门语言，一路设计出了绑定、切片、结构体、枚举、`Option`、`Result`、Trait、泛型、生命周期参数和闭包。

下一个需求来了，从哪里下手？这一课不推新规则，只回头看这一篇的设计，把它们排成一张可以查、可以推的图。

## 每一步都在回答三个问题

回头看，这一篇的每个设计都在回答下面三个问题中的一个。

**长度何时知道。** 编译期就知道，写进类型：`[T; N]`。运行时才知道，数据去堆，长度跟着句柄走：`Vec<T>`、`&[T]`。这是 5.1。

**谁负责释放，几个持有者，能不能写。** 拥有：`T`、`String`、`Vec<T>`。只读借：`&T`、`&[T]`、`&str`。可变借：`&mut T`。这是 4.1、4.2、5.3。

**方法何时定。** 编译期定：泛型和 `impl Trait`，单态化。这是 7.1、7.2。

每个问题是一根轴，轴上的每个类型是一格。另有两个设计横跨三根轴：`Option` 表示有没有，`Result` 表示成功还是失败，能套在任何一格外面，比如 `Option<&str>`、`Result<Vec<i32>, E>`。

## 别的语言替你答过了

你熟悉的语言也要回答这三个问题，只是在你写代码之前就答完了。Java 的答案是：长度放在对象头里，数据一律上堆，释放交给 GC，方法一律到运行时查表。

答案已经做进了语言，你拿到的是预制件：`int[]`、`ArrayList`、`interface`，拿来就用。账单预先付过了，付在运行时：GC 的停顿、每个对象的头、每次调用的查表。

Rust 不预付。它把三个问题的答案做成零件交还给你，每次组装都由你签单：不用的东西不付钱，用的东西自己选。

| 你熟悉的做法 | Rust 的组合 | 这一单付的是什么 |
| :--- | :--- | :--- |
| `ArrayList` | `Vec<T>` | 堆、增长权 |
| `substring`、借数组的一段 | `&str`、`&[T]` | 什么都不复制，受借用规则约束 |
| 函数收一个集合 | `&[T]`、`&str` | 给调用方开最宽的条件 |
| `null` | `Option<T>` | 必须 `match`，空值从事故变成义务 |
| 非受检异常 | `Result<T, E>` | 调用方必须签收失败 |
| `interface` 参数 | `impl Trait` | 编译期定方法，每个类型一份代码 |
| `new int[n]` | `Box<[T]>` | 拥有、定长，8.1 讲 |

表里每一行都不是规定，是这个场景下的默认答案。

## 四个问题

表不可能列全。遇到表里没有的需求，按顺序问：

1. 长度何时知道？
2. 谁负责释放？有几个持有者？
3. 只读还是要写？
4. 方法何时定？不涉及多种类型就跳过。

每问在一根轴上选一格，签名就出来了。

<Code code={assemble} lang="rust" />

**读一段文本，产生一段新文本。** 长度运行时才知道；函数只读，不负责释放；只读。参数是 `&str`。新文本由函数产生，交给调用方负责，返回 `String`。

**一个可能缺省的配置项。** 可能没有，套一层 `Option`；函数要拿走这个配置，参数是 `Option<String>`。

**解析一段文本里的所有数字。** 可能失败，失败要带原因，套一层 `Result`；数字个数运行时才知道，要拥有它们，里面是 `Vec<i32>`。函数体里用 `?` 把第一个失败交上去。

## 组装不出来的那一格

第四个需求：一棵家谱，一个孩子有两个父母，两个父母节点都要拿着这个孩子。

<Code code={twoParents} lang="rust" />

`left` 把 `child` 移进了自己的 `children`。取消注释，让 `right` 也拿着它，报 `error[E0382]`：`child` 已经被移动。

问到第二个问题，答案是「两个持有者」。这一篇的零件里，拥有只有一个所有者；借用又必须比所有者短，可两个父母谁先离开，要到运行时才知道。这一格空着。

这就是 1.6 留下的缺口：同一块数据要有多个所有者；数据何时不再使用，要等运行时才知道。

## 第一篇的规则，全是类型

1.6 把前几节的事实归纳成五条规则。4.2 说规则写进了类型，当时那张表并了行。现在五条全部到齐，一条一行：

| 第一篇的规则 | 类型事实 | 核对处 |
| :--- | :--- | :--- |
| 每一个值都有一个所有者 | 类型回答「这个值由谁负责」：`String` 拥有那块堆，`&String` 不拥有 | — |
| 任意时刻只有一个所有者 | 要负责释放的类型不能复制，赋值就移动 | E0382 |
| 所有者离开作用域，值被释放 | 要不要编入释放调用，由类型有没有 `Drop` 定 | `Drop` |
| 借用必须比所有者短 | 活多久写进类型：`&'a T`，7.3 | E0597 |
| 共享不可变，可变不共享 | `&T` 和 `&mut T` 是两个类型 | E0502 |

前两条由编译器替你执行，不单独报错——第一篇的这句话，在类型这边同样成立。这一篇你撞过的每个错误码，都是这张表某一行的核对处在响。

第三篇还会给这张表加一行：数据竞争不发生，`Send` 和 `Sync`——写在类型上的标记。

回头看第一篇：你先见到的是执法，错误码在行为层抓人；这一篇把法典翻开，每条法律的条文都是类型写的。所有权不是类型系统之外的另一个机制，它就是类型系统的形状。

## 所有权是动态性的账单

回头看，这一篇所有的规矩，都在为某样东西「要到运行时才知道」付账。

| | 编译期就知道 | 要到运行时才知道 |
| :--- | :--- | :--- |
| 数据放哪 | 栈 | 堆 |
| 长度放哪 | 类型里 | 句柄里 |
| 释放归谁 | 不用谁负责，复制就行 | 一个所有者，赋值就移动，别人只能借 |

4.2 末尾说过：所有数据的大小和寿命都在编译期定死，作用域就够了。所有者、移动、借用规则、生命周期，整套规矩是为左边那一列变成右边立起来的。

同一份账单，三种语言付法不同：

- Java 付在运行时：GC 替你扫描；
- C 付在纪律上：你自己记着释放；
- Rust 付在类型里：编译器替你记账，程序运行之前付清。

这一篇能在编译期付清的，都付清了：谁负责释放、引用活多久、调用哪个方法，都在编译期定下。所有者有几个、一次修改会不会和别人的读取重叠，要到运行时才知道的，编译期付不清。它们要到运行时付，用引用计数，用运行时的借用检查。这是第三篇。

还有一笔账记在类型自己身上。4.2 说类型是实体：身份、规矩、行为，全在编译期写定。可「这是哪个类型」也可能要到运行时才知道——同一个参数，这次收矩形，下次收圆形。身份要活到运行时，就得变成数据跟着值走：查一次表、带一个胖指针，都是它的付法，9.2 结这笔账。实体的身份，也不是免费的。

所有权是动态性的账单。

## 为什么感觉学不完

学到这里，你可能觉得 Rust 的东西又多又少：翻来覆去就是这几种类型和几个 Trait，可每到一个新地方，又会卡住。

规则没有变多。这一篇没有加一条所有权规则，只是把第一篇的五条写进了类型，推导链一步步变长。卡住的地方，是推论还没有变成反射。每次卡住时，把问题放回三根轴、问一遍四个问题，就是把推论收回来的办法。

## 顿悟时刻

这一篇的类型不是一张要背的清单，是这门语言对三个问题的回答：长度何时知道，谁负责释放，方法何时定。别的语言替你答过，Rust 把答案做成零件交还给你。

遇到新需求，问四个问题。组装不出「多个所有者」，就到了第三篇。
